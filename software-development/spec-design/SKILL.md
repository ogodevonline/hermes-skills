# Spec Design Skill

Послойное проектирование продукта/системы **в чате с пользователем**: от бизнес-слоя до плана реализации. Три отдельных артефакта, каждый со своим процессом: **спека ≠ план ≠ код**.

## When to Use

- Пользователь хочет построить продукт/систему (SaaS, Telegram-бот, платформа, сервис): «спроектируем», «распланируем», «обсудим архитектуру»
- Многослойный проект с модулями, БД, UI — где спека до кода экономит итерации
- НЕ для одноразовых задач (ответить, починить, собрать данные)

## Prerequisites

- Obsidian vault (пути ТОЛЬКО английские) — туда фиксируем спек
- Kanban и delegate_task для фаз планирования/реализации

## How to Run (общий ритм)

1. Проектируй **в чате**, не делегируй агентам. Задавай вопросы по каждому слою, предлагай варианты с рекомендацией, жди ответов.
2. Каждый согласованный слой сразу фиксируй в Obsidian (не жди конца).
3. После спеки пиши планы — можно параллельными планировщиками (delegate_task batch).
4. Проверяй планы ревьюерами (полнота vs спека), чини пробелы циклом.
5. Реализация — строгий TDD pipeline (см. test-driven-development).

## Quick Reference — слои сверху вниз

| Слой | Что решаем | Примеры вопросов |
|---|---|---|
| 0 Бизнес и границы | позиционирование, монетизация, пилот, что НЕ делаем | кто пользователи, кто платит, универсальность? |
| 1 Сценарии | потоки, статусы, роли, боты | как подтверждается запись? кто что видит? |
| 2 Функциональные требования | детали по каждому сценарию | структура услуг? гибкость настроек? |
| 3 Архитектура | стек, компоненты, event bus, DDD | один сервис? Postgres? очередь? |
| 4 Данные | схема БД, статусы, мультитенантность | таблицы, миграции, tenant_id |
| 5 UX | экраны, меню бота, чат | Mini App? экраны по ролям? |
| 6 План | этапы, сроки, зависимости | порядок, что параллельно |
| Тест-план | стратегия TDD, тесты по этапам | unit/api/bot/integration, покрытие |

## Procedure

### Фаза 1 — Спека в чате (слои 0→6 + тест-план)

- Начинай с ВЕРХА: слой 0 (бизнес). Не прыгай к архитектуре/БД, пока бизнес-слой не согласован.
- Один слой за раз: 3-5 вопросов + варианты («я бы...»), дождись ответов.
- Универсальность: если продукт для нескольких вертикалей — **ядро + модули** (модуль = свои таблицы + экраны + команды бота, ядро не трогается).
- После каждого согласованного слоя запиши в Obsidian (не в конце!).
- Параллельно можно задавать вопросы следующего слоя, чтобы не терять темп.

### Фаза 2 — Структура документации (ОБЯЗАТЕЛЬНО древовидная)

- **НЕ пиши все слои одним файлом** — пользователь это явно отвергает («беда», тяжело читать людям и агентам).
- `README.md` = индекс: дерево папки, таблица слоёв со ссылками, шорткат ключевых решений.
- Файл на слой: `00-overview.md`, `01-layer0-business.md`, ..., `08-test-plan.md`.
- Детали для исполнителей — в `plans/` (implementation plans) и `steps/` (файлы шагов).

### Фаза 3 — Планы (спека ≠ план!)

- Спека = ЧТО строим (слои, решения). План = КАК (bite-sized задачи с тестами, путями файлов, командами).
- После согласования спеки запусти планировщиков: delegate_task batch (до 3 параллельно), каждый планирует свой блок этапов, пишет в `plans/plan-XX.md`.
- Каждый планировщик: читает спеку + тест-план + навык writing-plans; обязан включить «Структуру файлов» с размером ≤150 строк на файл.

### Фаза 4 — Проверка планов (ревью)

- Запусти ревьюеров: каждый сверяет план со спекой по чек-листу, вердикты [OK]/[MISSING].
- Найденные пробелы исправь сам или верни на доработку; цикл до «блокеров нет».
- Типичные находки: забытые фичи из спеки, неверные пути файлов, отсутствующие миграции, тесты не привязаны к задачам.

### Фаза 5 — Реализация (TDD pipeline)

- Каркас проекта → для каждого этапа две раздельные задачи: «тесты» (красные, без production-кода) и «реализация по тестам» (зелёная, тесты не менять).
- Подробности: навык test-driven-development, раздел «TDD Pipeline через Kanban».

## Pitfalls

- Один файл на все слои → пользователь требует дерево с README-оглавлением.
- «Спека готова = можно кодить» → нет: сначала отдельные планы с тестами.
- Проектирование агентами вместо чата → пользователь хочет сам отвечать: «задавать кучу вопросов и предлагать как лучше».
- Забыть монетизацию/воронку продаж/анти-фрод в бизнес-слое → для коммерческих продуктов спрашивай про триал, тарифы, защиту от накрутки.
- Начать реализацию без тестов → запрещено (см. TDD pipeline).

## Verification

- Obsidian: README + файлы слоёв + plans/ + steps/ на месте, ссылки работают.
- Каждый слой помечен статусом согласования.
- Планы проверены ревьюерами (типично 2 раунда), пробелы закрыты.
- Kanban-задачи: каркас + пары «тесты/реализация» на каждый этап.
