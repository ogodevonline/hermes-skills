# Proxy Service — архитектура прокси-сервиса

## Когда загружать

- Пользователь проектирует или начинает писать сервис продажи прокси
- Нужна архитектура: роутер, бэкенды, балансировка, учёт трафика
- Выбор бизнес-модели: продажа IP vs продажа доступа к пулу
- Планирование масштабирования (10 → 500 клиентов)
- Пользователь ищет, где КУПИТЬ готовые прокси (страна + тип IP + цена) — см. «Покупка готовых прокси»
- Нужно понять, какой тип IP проходит на конкретный сайт-цель — см. `references/buying-proxies-ru.md`

---

## Архитектура (роутер-ориентированная)

Клиент получает **доступ к пулу серверов**, а не выделенный IPv4.

```
[Клиент] → socks5://client123.proxserv.ru:PORT
                ↓
[Router: asyncio SOCKS5/HTTP proxy]
  - принимает коннект
  - проверяет auth (JWT / IP whitelist)
  - проверяет лимиты трафика (Redis)
  - выбирает бэкенд (страна, load)
  - проксирует трафик
  - пишет метрики в Redis (incrby per-client)
                ↓
[Backend pool: Hetzner/Timeweb/Scaleway]
  - 3proxy / Squid
  - max 20 клиентов на сервер
  - heartbeat-агент (алив, load, CPU)
```

## Ключевые компоненты

### 1. SOCKS5/HTTP роутер (Python asyncio)
- Асинхронный TCP-прокси на asyncio
- Алгоритм: auth → лимиты → sticky/rotation → выбор бэкенда → прокси
- Каждому клиенту отдельный порт на роутере
- Режимы: sticky session (один бэкенд), per-request (каждый запрос — новый), rotate по API

### 2. FastAPI API (ядро)
- Auth (JWT + IP whitelist)
- Тарифы (CRUD)
- Платежи (CryptoCloud, RuKassa)
- Выдача прокси (после оплаты → Ansible → создать клиента)
- Сессии и трафик

### 3. Redis
- Реалтайм счётчики трафика (incrby client:traffic)
- Сессии (user → server mapping)
- Лимиты (время жизни = период тарифа)
- Асинхронный слив в PostgreSQL раз в час

### 4. PostgreSQL
- Clients, tariffs, payments, servers, sessions, logs
- SQLAlchemy ORM, Alembic миграции
- pg_dump раз в день → Telegram/S3

### 5. Heartbeat-агент (на каждом бэкенде)
- Каждые 30с: POST /agent/heartbeat {server_id, country, load, cpu, ram, alive}
- 90с тишины → сервер считается dead
- Клиенты с dead сервера → перевыдача на живой

### 6. Provider abstraction (с первого дня)
```python
class BaseProvider:
    def deploy_server(country: str) -> Server
    def remove_server(server_id: str)
    def get_load(server_id: str) -> dict
    def get_available_countries() -> list[str]
```
- HetznerProvider, TimewebProvider, ScalewayProvider
- API хостеров дёргаются через REST
- Позволяет автомасштабирование: слоты > 80% → API хостера → новый бэкенд

### 7. Telegram-бот (aiogram)
- /start — каталог тарифов по странам
- /buy — оплата → автовыдача прокси
- /my — список моих прокси, статус, трафик
- /rotate — сменить бэкенд
- /support — чат с поддержкой

### 8. React клиентский кабинет + админка
- Клиентский: список прокси, трафик, продление, API-ключи
- Админка: серверы (таблица с load/CPU/alive), клиенты (баны, смена тарифа), платёжки (история), тарифы (CRUD)

## Бизнес-модель

**Подход A (классика, дорого):** Каждому клиенту выделенный IPv4. Расход 150 ₽/IP/мес. При 500 клиентах = 75 000 ₽/мес на одни IP.

**Подход B (роутер, дёшево):** 1 IP роутера + N IP бэкендов (5-10 шт). Клиент покупает ДОСТУП. Расход на IP = ~1 500 ₽/мес при 500 клиентах. Дешевле в 50 раз.

**Тарифы (рекомендуемые):**
- Базовый: 1 страна, 50 GB, 300 ₽/мес
- Стандарт: 3 страны, ротация, 150 GB, 600 ₽/мес
- Про: все страны, per-request ротация, 500 GB, 1 200 ₽/мес

**Точка безубыточности:** 4 клиента при 600 ₽/мес (маржинальный доход 415 ₽, fixed 1 600 ₽)

## Масштабирование

| Этап | Клиентов | Архитектура |
|------|----------|------------|
| 0→10 | 1 роутер + 2-3 бэкенда | Всё на одном VPS |
| 10→50 | Роутер + DB отдельно | nginx reverse proxy |
| 50→200 | Asyncio SOCKS5 роутер | Redis для трафика |
| 200→500 | 2-3 роутера (разные ДЦ) | DNS-балансировка, кластер PG+Redis |

## Покупка готовых прокси (когда своё строить не надо)

**Первый шаг — не поиск, а 4 вопроса. Без них ответ мимо цели:**
1. Страна выхода — «прокси» без страны бессмысленно; РФ не подставляется по умолчанию на международных сайтах.
2. Тип IP: датацентр / ISP (провайдерский) / резидентский / мобильный. Разница в цене — 10–100×.
3. Целевой сайт — он определяет тип IP (таблица в `references/buying-proxies-ru.md`).
4. Сколько IP и на какой срок: цена за IP падает с объёмом, поэтому «дёшево» без объёма не сравнивается.
5. Откуда зовёшь: гео сервера-источника определяет, нужен ли прокси вообще. Проверяется до подбора провайдеров — шаг 0 ниже.

**Алгоритм проверки — по живым страницам, а не по выдаче:**
0. Сначала докажи, что гео-блок РЕАЛЕН: с того сервера, где будет работать клиент, проверь TCP-коннект к цели (`timeout 8 bash -c '</dev/tcp/<host>/443'`) и сравни с контрольными сайтами в том же прогоне. Таймаут на цели при живых контролях = блок по IP, прокси действительно нужен. Цель отвечает — прокси не нужен, не продавай себе решение. Метод и кейс РФ-API — в `references/buying-proxies-ru.md`.
1. `web-tools search` — только чтобы собрать список ПРЯМЫХ сайтов провайдеров: выдача забита агрегаторами «топ-10 прокси», объявлениями Авито и SEO-блогами.
2. Живость пачкой из python (ThreadPoolExecutor + subprocess): `curl -s -o /dev/null -w "%{http_code} %{time_total}s" -L --max-time 20 -A "<desktop UA>" <url>`. `000` = не отвечает, `403` = WAF, `503` = лежит.
3. Цены снимать со страниц провайдеров, а не из сниппетов: `curl` → снять теги → regex по `₽|руб|\$|€` и «от N за IP».
4. Прайс-таблицы на JS (proxy6.net, proxyline.net, proxymania.su) через `web-tools extract` не снимаются — в HTML цен нет. Рендерить бандл-хромом из Playwright-кэша, без CDP и браузерного харнесса: `~/.cache/ms-playwright/chromium_headless_shell-*/chrome-headless-shell-linux64/chrome-headless-shell --no-sandbox --disable-gpu --dump-dom --virtual-time-budget=10000 <url>` → снять теги → regex по `₽|руб|\$`. Так снимается вся матрица proxy6 (тип IP × объём × срок). Полный рецепт с разбором DOM и граблями — `references/js-page-rendering.md`.
5. Работоспособность купленного прокси проверять curl-ом: `curl -x socks5://user:pass@host:port https://2ip.ru/` или `http://ip-api.com/json/` → страна/AS/IP, потом сам целевой сайт.
6. Регистрация, оплата и тестовые прокси — только через аккаунт пользователя; сам не регистрируюсь и не плачу.
7. После покупки — довести до рабочего состояния, а не оставить ссылку: проверить прокси curl-ом (шаг 5), записать покупку в vault (`Areas/Profile/services.md`: провайдер, кабинет, зачем, тариф, креды, оплачено до, команды проверки) и предложить напоминание о продлении в Telegram. Напоминание — отдельным одноразовым джобом на дату через месяц-два: `cronjob_manage(action="create", schedule="<ISO МСК>", deliver="origin")` с самодостаточным промптом (провайдер, для чего покупались, путь заметки в vault) и обязательно проверкой `action="list"` (`enabled`, `next_run_at`). ⚠️ LLM-джоб без пиннинга пропускается молча, если глобальная модель сменилась после его создания (`drift_skip`) — предупредить пользователя и пересоздать джоб при смене модели. Креды и параметры в чате долго не живут — без записи следующий запрос «а какие у меня прокси?» начинается с нуля.

Провайдеры, проверенные цены и тип IP под конкретные сайты — `references/buying-proxies-ru.md`.

## Pitfalls

- **Не пытайся давать каждому клиенту выделенный IPv4** — это экономика масштаба работает против тебя. Роутер-ориентированная схема в 50 раз дешевле.
- **Сразу пиши Provider-абстракцию** — иначе привяжешься к одному хостингу и не сможешь легко добавить второй.
- **Redis для трафика — обязательно** — PostgreSQL не вывезет реалтайм-счётчики при 500 клиентах.
- **Health-check + перевыдача** — без этого клиенты будут писать «не работает» 24/7, а ты не будешь знать.
- **Ограничение трафика per-client на 3proxy** — `bandwidth limit` и `maxconn`. Иначе 1 клиент положит сервер на 19 others.
- **Не логируй содержимое соединений** — только суммарный трафик. Клиенты не хотят чтобы ты видел куда они ходят.
- **Playwright + SOCKS5**: встроенный `proxy=` не поддерживает SOCKS5. Используй `args=["--proxy-server=socks5://..."]` при launch. Детали и полный пример — в `references/scraping-proxy-pool.md`.
- **Датацентр-IP ≠ «рабочий прокси»** — у Wildberries, Ozon, Avito, CIAN, Auto.ru блэклисты ASN хостеров (включая Hetzner/AWS/GCloud). Для них нужен ISP/резидентский/мобильный, иначе парсер молча получает 404 или пустые цены.
- **«От N ₽» на странице провайдера — это самый дешёвый пакет/гео, а не цена под запрос** — перед сравнением фиксируй страну, объём и срок. Приводи цену **за 1 IP/мес** и минимальный заказ: у зарубежных «from $0.0x/IP» цифра действует только на крупных пакетах, и при заказе одного IP реальный минимум выше — иначе сравнение несравнимого, и пользователь отвечает «дороже намного».
- **На «дороже намного» — спроси ориентир пользователя (ссылку/цену) и проверь его живьём**, а не переискивай вслепую: у него уже есть конкретное предложение, и половина таких предложений — публичные списки или перепроданный shared, которые под API не годятся. Проверять — не спорить.
- **Не отдавай пользователю выдачу поиска как результат** — ники сайта без проверки `http_code`/цены = выброшенная сессия.
- **Отдавай проверенный шорт-лист первым ответом, а не после N-й итерации исследования.** Пользователь прерывает («ну и что?»), когда вместо результата идут новые tool-вызовы; правильный порядок — выдать то, что уже проверено, с пометками ✅ снято живьём / ⚠️ не проверено, и продолжить копать только после этого.
- **Собирай однотипные пробы в один прогон** (python-скрипт с ThreadPoolExecutor: живость + цены + TCP-тесты сразу) — иначе одна сессия уходит на десяток последовательных tool-вызовов вместо одного.
