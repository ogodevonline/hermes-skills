# Шаблон дерева спеки (проверен на booking-platform, 08.2026)

Пользователь дважды отверг однофайловую спеку («так нельзя, надо сразу на несколько файлов разбивать»).
Это рабочий формат, который читается и человеком, и агентами-исполнителями.

## Структура

```
<project>/
├── README.md                 ← содержание: дерево, таблица слоёв, шорткат решений
├── 00-overview.md            ← обзор + обязательная терминология (как называем сущности)
├── 01-layer0-business.md     ← Слой 0: бизнес, границы, монетизация, что НЕ делаем
├── 02-layer1-scenarios.md    ← Слой 1: сценарии, статусные схемы, боты
├── 03-layer2-functional.md   ← Слой 2: функциональные требования по сущностям
├── 04-layer3-architecture.md ← Слой 3: стек, компоненты, ключевые архитектурные решения
├── 05-layer4-data.md         ← Слой 4: схема БД (все таблицы, статусы, связи)
├── 06-layer5-ux.md           ← Слой 5: экраны, меню ботов, сообщения
├── 07-layer6-plan.md         ← Слой 6: таблица этапов со сроками и ссылками на steps/
├── 08-test-plan.md           ← План тестирования: стратегия, тесты по этапам, DoD
└── steps/                    ← файлы шагов для исполнителей
    ├── 01-foundation.md      ← цель, ссылки на слои, задачи, критерии приёмки
    └── ...
└── plans/                    ← ДЕТАЛЬНЫЕ implementation plans (после спеки, планировщиками)
    ├── plan-01-03-....md     ← bite-sized задачи, пути файлов, код, тесты
    └── ...
```

## Правила

1. **README = оглавление.** Дерево файлов + таблица слоёв со статусами + 5-10 ключевых решений шорткатом (чтобы не читать всё).
2. **Frontmatter у каждого файла:** `title`, `type` (spec-layer/step/test-plan/index), `project`, `status` (agreed-YYYY-MM-DD / draft).
3. **Каждый слой — отдельный файл**, одна ответственность. Относительные ссылки между файлами.
4. **Статусы согласования:** после каждого слоя, согласованного с пользователем, помечай `status: agreed-<дата>`.
5. **Терминология — отдельно (00-overview):** зафиксируй нейтральные названия, чтобы не скатываться в вертикаль пилота (пример: лид-платформа, а НЕ «клиника/врач/пациент»).
6. **steps/ vs plans/:** steps — что делаем (этапы, критерии); plans — как делаем (задачи, файлы, тесты, команды).
7. **Тест-план обязателен** до реализации: каждый тест = задача в implementation plan (TDD).

## Формат файла шага (steps/XX-*.md)

```markdown
---
title: Этап N — Название
type: step
project: <project>
depends_on: [01-...]
---

# Этап N — Название (срок)

## Цель
Что получаем.

## Ссылки
- Слой 3: ../04-layer3-architecture.md
- Тест-план: ../08-test-plan.md

## Задачи
1. Конкретная задача с путями файлов
2. ...

## Критерии приёмки
- Проверяемо: команда/поведение/тест
- Ни один файл > 150 строк (wc -l)
```

## Запуск параллельных планировщиков (после спеки)

```python
delegate_task(tasks=[
  {"goal": "Написать детальный implementation plan для этапов 1-3...",
   "context": "пути к спеке, тест-плану, шагам; требование загрузить writing-plans; лимиты; путь сохранения"},
  {"goal": "... этапы 4-5 ...", "context": "..."},
  {"goal": "... этапы 6-8 ...", "context": "..."},
])
```

Каждый планировщик: читает спеку → пишет bite-sized задачи → сохраняет в plans/ → возвращает резюме.
Проверяй результат: размер файлов ≤150 строк, тесты присутствуют, нет монолитов.
