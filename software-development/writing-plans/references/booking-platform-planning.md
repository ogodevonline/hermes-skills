# Booking Platform — workflow планирования этапов (проверен на этапах 4–5)

Многоэтапная лид-платформа записи к специалистам (FastAPI + aiogram 3 + Postgres + Telegram Mini App админка + React). Планы пишутся на РУССКОМ языке и сохраняются в Obsidian vault.

## Конвенции путей и языка

- Сохранение: `~/hermes-vault/Projects/Planning/YYYY-MM-DD/booking-platform/plans/plan-NN-MM-<короткое-имя>.md`
  - пример: `plan-04-05-admin-chat.md` (этапы 4–5, админка + чат)
- Папка `plans/` создаётся при необходимости (write_file создаёт директории сам).
- Один файл на этап или на группу связанных этапов (4–5 делались вместе, т.к. чат живёт в админке).
- Frontmatter обязателен (см. skill `vault-frontmatter`): `title`, `type: implementation-plan`, `project: booking-platform`, `status: draft`, `created`, `depends_on: [steps/NN-*.md]`.
- Язык: русский (пользователь Василий ведёт проект на русском).

## Обязательное чтение перед планом (в этом порядке)

1. `README.md` — индекс, шорткат ключевых решений, дерево документов
2. Слои: `04-layer3-architecture.md` (стек), `05-layer4-data.md` (схема БД), `06-layer5-ux.md` (экраны/чат), `03-layer2-functional.md` (роли, лиды — часто уточняет детали, которых нет в layer5)
3. `08-test-plan.md` — ТАБЛИЦЫ ТЕСТОВ ПО ЭТАПАМ: это источник задач
4. `steps/NN-*.md` — файл шага ЦЕЛЕВОГО этапа + файлы шагов ПРЕДЫДУЩИХ этапов (для раздела «Допущения»: какие модели/события/инфраструктура уже существуют)
5. `07-layer6-plan.md` — зависимости этапов

## Структура плана (проверенная, 784 строки / 35 задач на 2 этапа)

1. Frontmatter
2. Header: `> For Hermes:` + **Goal** / **Architecture** / **Tech Stack** / «ЖЁСТКИЙ ЛИМИТ» (≤150 строк на файл, включая React-компоненты и alembic-миграции)
3. «Допущения» — что готово после прошлых этапов (модели, deps, event bus, notifier'ы, helper рабочих часов) + оговорка «если пути отличаются — адаптируй, сохраняя интерфейсы»
4. На каждый этап:
   - цели
   - таблица прав/ролей ИЛИ модель данных (для чата)
   - «Структура файлов» — таблица: путь | роль | ожидаемый размер (~80–120) | интерфейс. ОТДЕЛЬНО для backend и frontend
   - задачи с TDD-циклами, привязанные к тестам из `08-test-plan.md`
   - критерии приёмки (из `steps/NN` + тест-плана, тесты по именам)
5. «Сквозные проверки»: `find ... wc -l | sort -rn | head -40` (нет файлов >150), `pytest -v`, `cd web && npm run build`
6. «Резюме для исполнителя»: число задач/файлов, порядок этапов, ключевые риски

## Маппинг тест-плана на задачи

- Каждая задача ссылается на точные имена тестов (`test_leads_filter` → задача 4.5) и точные файлы тестов (`tests/api/test_admin_clients.py`).
- Backend-задачи: полный TDD-цикл (красный тест → FAIL → реализация → PASS → commit). Формат шагов: Step 1 падающий тест (с кодом), Step 2 запуск→FAIL, Step 3 минимальная реализация (с кодом), Step 4 запуск→PASS, Step 5 commit.
- Frontend-задачи: тест-плана на фронт нет → проверка = `npm run build` + ручной smoke по критериям приёмки + commit (vitest не выдумывать).
- Каждая задача = отдельный git commit с сообщением `feat(scope): ...`.

## Питфоллы (из этапов 4–5)

- Ролевые фильтры — на сервере (`require_roles` + жёсткий scope в сервисе), НЕ только скрытие пунктов UI.
- Лимит 150 строк распространяется и на alembic-миграции (автогенерируемые — проверять и резать руками).
- Ночные/рабочее-время правила (эскалация, уведомления) тестировать ЧИСТЫМИ функциями (`should_notify(now, working_hours)` с now как параметром), а не временем системы — иначе ночной unit-тест недетерминирован.
- События домена публикует сервис; side-эффекты (уведомления клиенту/рабочему боту) — подписчики event bus (инфраструктура этапа 1) + APScheduler для крон-задач (этап 3).
- Клиентские каналы (бот) получают только упрощённый payload (`client_payload` без статусов «прочитано/доставлено») — разделять DTO для клиента и для staff.
- Чаты в Mini App без websocket: polling 5–10 сек.

## Первые этапы (1–3, foundation) — отличия от 4–5

Проверено: `plans/plan-01-03-foundation-booking.md` (3 этапа, 60 задач, 4546 строк, один документ на группу этапов).

- Вместо верхних «Допущений» (их не может быть — инфраструктуры ещё нет) — раздел «0. Общие правила»: repo init (`~/projects/booking-platform/`), venv + `pip install -e ".[dev]"`, docker compose (postgres + app с healthcheck), создание тестовой БД `booking_test` через `docker exec ... createdb`, конвенция коммитов.
- Тестовая БД: отдельная `booking_test`, схема через `Base.metadata.create_all` в session-scoped фикстуре + очистка таблиц между тестами; alembic проверяется отдельно (`alembic upgrade head`).
- «Структура файлов» — таблица на КАЖДЫЙ этап (Путь | Роль | ~строк | Интерфейс); ~66 файлов на 3 этапа.
- «Решения и допущения» (таблица № | решение | обоснование) — в КОНЦЕ плана: путь репо, test-DB, auth через initData в заголовке `X-Telegram-Init-Data` на каждый запрос (без JWT), enum статусов русскими значениями («новая»...), напоминания планируются на подтверждение, ночные переносятся на рабочее время (`next_working_time`), no-show ставит специалист кнопкой.
- Нумерация задач `Задача N.M` (1.10, 3.14) — кросс-ссылки «см. задачу 3.x» внутри плана.
- Закрывающая задача этапа: `wc -l` лимит + `pytest -v` + коммит `chore: stage N complete`.
- Питфолл: dataclass-события домена требуют `@dataclass(kw_only=True)` на базовом классе и каждом событии (дефолты в базе + обязательные поля в подклассе = TypeError).
- Очень большой план пишется частями в /tmp и склеивается (`cat /tmp/plan_part*.md > target && rm part*`); верификация склейки — `grep -c "^### Задача"` и проверка хвоста файла (`search_files` не ловит якорные regex).
