# Multi-tenant SaaS — проверенные паттерны (Booking Platform, 2026-08)

Конденсированные знания из проектирования лид-платформы записи (пилот — стоматология Рашида, Нукус).
Применимы к любому мультитенантному SaaS: booking, заказ услуг, запись к специалистам.

## Ядро + модули (вертикали)

- **Ядро** (всем бизнесам): клиенты, услуги, сотрудники/специалисты, расписание, записи со статусами,
  напоминания, догонялка, база лидов, админка.
- **Модули** (подключаются по вертикали): рабочие планы (клиники), абонементы (фитнес),
  депозиты/отзывы (салоны), каталог работ (барбер), ИИ-агент + RAG, онлайн-оплата.
- Модуль = свои таблицы + свои экраны админки + свои команды бота; ядро НЕ трогается.
  Изоляция через feature-flag (`PlansModule(enabled)`): выключение не ломает ядро, роутеры/меню исчезают.
- Защита от раздувания ядра: сначала проектируем ядро идеально, модули — отдельными спекуляциями.

## Мультитенантность

- `tenant_id` в КАЖДОЙ таблице (TenantMixin на моделях).
- Свой Telegram bot-токен на tenant (пациентский + рабочий); бот определяет tenant по токену.
- Настройки бизнеса — поля Tenant или JSONB settings: зазор записи, режим подтверждения,
  категории да/нет, тексты бота, уведомления.
- Валидация: один триал/подписка на аккаунт; тест изоляции `test_tenant_isolation` — данные tenant A
  не видны tenant B (обязательный тест).

## Домен записи (booking)

- Слоты = график специалиста − блокировки (schedule_overrides) − занятые − зазор (gap_minutes, настр.).
- Длительность слота привязывается к УСЛУГЕ (осмотр 15 мин, лечение 60 мин), не фиксированная.
- Гибкость ядра: выбор специалиста настраивается (1 специалист → бот не спрашивает);
  категории услуг опциональны; у услуги могут быть фото.
- Статусы записи: новая → подтверждена (авто через окно 4ч или кнопка ✅) → выполнена (АВТО по
  истечении времени; админ может поправить) / не пришёл / отменена / перенесена.
- Зазор: бот НЕ показывает слоты ближе настраиваемого зазора (4-6ч) — мастер успевает увидеть.
- Окно отмены: 4ч после создания — мастер может отменить/перенести без последствий; не отменил =
  запись подтверждена, ответственность на мастере/админе.
- Уведомления о новой записи — ВСЕМ (специалист + админ), с кнопками ✅/❌/перенос.
- Доп. статус специалиста (таблица specialist_notifications): не видел/видел/подтвердил/отменил/проигнорировал.
- Напоминания: за сутки + за 2-3ч, только тем кто открывал бота. Вне Telegram — ручные SMS/звонок
  с отметкой в админке.
- Догонялка: не пришёл → через час «Записаться заново?»; не ответил → МОЛЧИМ (не спамить), в базу лидов.
- Ретаргетинг «давно не был»: визит > N месяцев + услуга X → предложить записаться; анти-спам таблица
  retarget_sent (пишем один раз за 30 дней).
- Рабочие часы уведомлений: только в рабочее время бизнеса + 1ч после закрытия; ночью копятся →
  утром один пуш (pending_morning_push).
- Чат = тикет-система: conversations (открыт/требует ответа/завершён), messages в БД, internal_notes
  (клиент не видит), эскалация 30м→специалисту / 2ч→админу / 4ч→владельцу (только рабочее время).
  Клиент НЕ видит «прочитано/доставлено» (ноль раздражителей).

## Монетизация: триал + воронка продаж

- **Триал 7 дней максимум, НЕ 14.** 14 дней = вечный триал через пересоздание аккаунтов.
- После триала без оплаты: функционал режется (только чтение) + напоминания.
- Воронка: отдельный Telegram-бот для бизнесов (чат-онбординг: вопросы о бизнесе → автонастройка →
  триал → оплата) + лендинг с кнопкой «Затестировать» → ведёт в бота.
- Напоминания неоплатившим: через день «подключите тариф», через месяц «что не понравилось?» — опрос
  для улучшения платформы.
- Оплата для Узбекистана: Payme/Click/Uzum (НЕ Stripe по умолчанию).

## Анти-фрод для триалов

- **Жёсткий лимит: один триал на Telegram ID** — повтор → «у вас уже был триал».
- **Мягкий лимит на IP** (сигнал, НЕ бан): напр. 3 триала с одного IP. Жёсткий IP-бан НЕ делать —
  в Узбекистане динамические IP (мобильный интернет), отсечёшь реальных клиентов.
- Свежесозданные Telegram-аккаунты (младше X дней) — помечать, при подозрении просить телефон.
- Аномально быстрая регистрация (<30 сек) + свежий аккаунт = подозрение.
- Блок ТОЛЬКО по комбинации сигналов; одиночный сигнал = пометка, не бан.
- Логирование anti-fraud events для ручного разбора.
- Для своего пилота анти-фрод не нужен.

## Роли (универсальные, не привязаны к людям)

| Роль | Что видит/делает |
|---|---|
| Владелец | Статистика, доход, настройки |
| Специалист/мастер | Свои записи, уведомления ✅/❌, рабочие планы (выполнение) |
| Администратор | Всё: расписание, записи, планы, лиды, дозвон, ручные напоминания |

## ИИ-агент + RAG (function calling)

- Ручки агента: get_free_slots, create_appointment, cancel_appointment, reschedule_appointment, send_message.
- Промпт: НЕ ставить диагнозы → предложить консультацию; подтверждать у клиента перед записью
  (gate на create_appointment: выполняется только при явном «да/подтверждаю»).
- Контекст = история клиента (timeline) + RAG по базе знаний бизнеса; «не знаю» без галлюцинаций (порог similarity).
- Графы сценариев = ДАННЫЕ (JSON ноды/рёбра/тексты), не хардкод: типовые шаблоны + мастер-опрос
  админа генерирует граф из ответов (drag&drop конструктор — НЕ в MVP).
- Расход LLM: центовый уровень на диалог; замерять на тестовом диалоге.
