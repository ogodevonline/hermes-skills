# Telegram Account Bridge Skill

Как действовать от имени личного аккаунта Telegram: читать личные чаты, отвечать за владельца, править и удалять отправленное. Разбирает три уровня доступа и что каждый реально умеет. Не про посты в каналы (это channel-post) и не про рассылки.

## When to Use

- «Пиши от моего имени», «ответь этому человеку», «посмотри, что мне написали»
- Нужно видеть новые сообщения в личке и отвечать на них
- Нужно выгрузить список диалогов или почистить чаты (только userbot)
- «Отпишись от ненужных каналов», «заблокируй мусорных ботов», «наведи порядок в диалогах» — разбор идёт по `references/dialog-triage.md`
- Бот подключён, но не может что-то сделать — понять, это лимит платформы или настройка

## Prerequisites

- Отдельный бот в @BotFather. Не тот, через которого работает Hermes: Telegram отдаёт апдейты только одному поллеру, два процесса на одном токене передерутся
- Telegram Premium у владельца аккаунта (Business-режим без него не включается)
- Для userbot — api_id/api_hash с my.telegram.org (API development tools). Кладутся файлом `~/.hermes/tg-userbot/api.json` формата `{"api_id": 12345678, "api_hash": "<32 hex>"}` с правами `600`: `tg_dialogs.py` читает только этот файл (константа `CREDS`), ни `.env`, ни конфиг Hermes не смотрит. Валидация на входе: `api_id` — целое, `api_hash` — ровно 32 hex-символа
- Всё остальное на той же странице my.telegram.org (блок **Available MTProto servers**: пары IP + Public Key, тестовая конфигурация) сохранять не надо. Адреса DC и 8 RSA-ключей вшиты в Telethon: `telethon/crypto/rsa.py` и `DEFAULT_IPV4_IP` в `client/telegrambaseclient.py`. Тестовая конфигурация нужна только при работе против тестовых серверов, а не с продовым аккаунтом

## How to Run

Всё живёт в `~/.hermes/tg-userbot/`:

- `business_bridge.py poll` — слушает новые сообщения личных чатов в базу
- `business_bridge.py inbox --limit 20` — кто что написал
- `business_bridge.py send --to <chat_id> --text "..."` — отправить от имени владельца
- `business_bridge.py delete-msg --id <msg_id>` — удалить своё отправленное
- `business_bridge.py chats` — проверка подключения и права can_reply
- `business_bridge.py media --chat <id> --limit 5` — выгрузить картинки из чата

Слушает демон `tg-business-bridge` (systemd --user), логи в `poll.log`.

Второй инструмент, `tg_dialogs.py` (MTProto, тот же каталог) — список диалогов и чистка: `login`, `report`, `backup`, `delete`, `leave`, `botstop`, `botunblock`. Разрушительные режимы (`leave`, `botstop`, `botunblock`) без `--yes` работают как сухой прогон и только печатают, кого затронут. Разбор «что тут мусор» — в `references/dialog-triage.md`.

## Quick Reference: три уровня доступа

**Обычный бот** — пишет только тем, кто нажал /start. Первым в личку написать нельзя. Для «пиши от моего имени» не подходит.

**Business-бот (Secretary Mode)** — то, что обычно называют «подключить бота в аккаунт». Без api_id. Верифицированные границы (Bot API, `BusinessBotRights`):

- `can_reply` — «send and edit messages in the private chats that had incoming messages in the last 24 hours». Только личка и только внутри суточного окна от входящего
- `can_read_messages` — пометка входящих прочитанными
- `can_manage_stories` — посты, правка и удаление **историй** от имени владельца
- Каналов нет вообще, списка диалогов нет, истории до момента подключения нет

**MTProto userbot** — единственный путь к `messages.getDialogs` (список) и `messages.deleteHistory` (удаление), оба помечены «Only users can use this method». Файл сессии равнозначен полному доступу к аккаунту без пароля.

## Procedure

### 1. Подключение Business-бота (проверено рабочим)

1. @BotFather → `/newbot` → отдельный бот, получить токен.
2. `/mybots` → Bot Settings → **Secretary Mode** → включить.
3. Проверить флаг: `getMe` → `can_connect_to_business` должен стать `true`. Пока `false` — аккаунт к боту не подключится.
4. В аккаунте: Настройки → **Telegram Business** → **Чат-боты** → добавить username бота. Права живут в карточке самого бота, а не в списке: открыть бота → «Управление сообщениями» → **Отвечать на сообщения** (обязательно) + **Читать сообщения**.
5. Проверить права: `getBusinessConnection` → `rights.can_reply` должен быть `true`. Без него подключение есть, а отправка не работает.
6. Запустить поллер сервисом: см. `templates/tg-business-bridge.service`.

### 2. Отправка и правка

Отправка `sendMessage` с `business_connection_id`; удаление — `deleteBusinessMessages` с `business_message_id`. Удалять и править можно только своё отправленное (при выданных правах).

### 3. Userbot (когда нужен список чатов или удаление диалогов)

`tg_dialogs.py` в той же папке: `login` / `report` / `backup` / `delete` / `leave` / `botstop` / `botunblock`. Все режимы проверены на живом аккаунте.

Порядок:

1. Положить креды в `api.json` (см. Prerequisites) и проверить, что файла сессии ещё нет: `ls ~/.hermes/tg-userbot/owner.session`.
2. `login` запускает **сам владелец** в терминале: `cd ~/.hermes/tg-userbot && .venv/bin/python tg_dialogs.py login`. Интерактивно спрашивает номер (`+7...`) → код из приложения Telegram → пароль 2FA (ввод кода не отображается). Код и пароль 2FA **не принимать в чат** — тогда единственный чистый путь это передать команду владельцу; pty-сессия с продиктованным кодом это худший вариант, предлагать только как осознанный выбор.
3. Признак успеха — строка `вошли как <Имя> (@<username>) id=<...>` и появившийся `owner.session`. Сразу закрыть права: `chmod 600 owner.session owner.session-journal`.
4. Дальше `report` (ничего не меняет) → разбор по `references/dialog-triage.md` → `backup` в JSON → `leave` / `botstop` после подтверждения владельца → `delete` добивает оставшиеся карточки.

## Pitfalls

- **Один токен — один поллер.** Второй процесс на том же токене забирает апдейты у первого, и Hermes перестаёт отвечать.
- **Свои сообщения тоже приходят.** `business_message` включает исходящие владельца; без проверки флага `out` своя же переписка ложится в базу как входящая. Если это уже случилось — починить через `UPDATE messages SET direction='out' WHERE sender='<владелец>'`.
- **Историю до подключения не видно.** Telegram отдаёт только новые сообщения; чат, где человек писал до подключения бота, для моста не существует, пока он не напишет снова.
- **Медиа надо ловить в моменте.** `file_id` сохраняется из апдейта; задним числом фото не скачать — придётся просить прислать заново.
- **Лишние права.** Владелец часто выдаёт всё сразу: `can_delete_all_messages`, `can_edit_username`, `can_edit_profile_photo`, `can_edit_name`, `can_edit_bio`. Для работы достаточно `can_reply` + `can_read_messages` (+`can_manage_stories` при нужде). Остальные снять.
- **Код входа и 2FA — не через чат.** Логин userbot'а интерактивный; принимать код из Telegram и облачный пароль в переписке нельзя (они уходят в историю чата и в логи). Передавать владельцу одну строку команды и просить написать только «готово».
- **`api_hash` — пароль приложения.** По TOS Telegram чужая работа с этими кредами может привести к бану аккаунта; не публиковать в чатах, скриншотах, репозиториях. В личке владельца он уже прошёл — это нормально, но дальше не пересылать и не эхо-ить обратно в ответе целиком.
- **Секреты кредов не проходят через `hermes config set`.** `api.json` — файл рядом со скриптом (создаётся вручную, `chmod 600`); конфиг Hermes и `.env` к userbot'у отношения не имеют.
- **`dialog.message.message` бывает `None`.** У сервисных сообщений, медиа без подписи и у чатов без истории текста нет; срез `[:120]` по нему роняет весь `report` с `TypeError` на первом же таком диалоге. Нормализовать в отдельном хелпере: `((msg.message if msg else None) or "")[:120]`.
- **Удаление диалога ≠ отписка, а у бота отписки нет вообще.** `delete` чистит только локальную карточку: канал вернётся с новым сообщением, бот — с новой рассылкой. Каналы и группы покидают через `leave`, ботов гасят через `botstop` (`contacts.BlockRequest` + очистка диалога, откат — `botunblock --ids`).
- **Перед уничтожением — `backup`.** Вернуться в канал можно только по ссылке, история у себя не остаётся; при блокировке бота переписка тоже теряется.
- **Сухой прогон всегда предшествует применению.** У `leave`, `botstop`, `botunblock` запись включается только флагом `--yes`; без него команда печатает точный список сущностей. Показывать владельцу именно его и выполнять после явного «ок» — состав списка выбирает он, а не агент.
- **Триаж — по метаданным, не по переписке.** Для «что тут мусор» хватает `report` плюс числа сообщений: `get_messages(entity, limit=0).total` показывает, пользовались ли ботом (1–2 сообщения — разовое `/start`, сотни — рабочий сервис), дата последнего сообщения — мёртв ли чат, текст последнего сообщения выдаёт скам и рассылки. Читать историю целиком не нужно.
- **Разбор данных — скриптом из файла, а не пайпом в интерпретатор.** Сводки и отбор id делать отдельным `.py` рядом с задачей и запускать `.venv/bin/python файл.py`: пайп в `python3` и heredoc поднимают подтверждение безопасности и могут упереться в блокировку, готовый файл проходит молча. Такой скрипт заодно перезапускается после каждой новой порции чистки.
- **Ботов своих проектов и инфраструктуры — вон из списка на вычистку.** BotFather, платёжный бот, секретарь, боты мониторинга и боты SaaS-тенантов владельца по метаданным выглядят как брошенные. Исключать их по имени и username до показа списка владельцу.
- **«Сделано» у Telegram не значит «карточки нет».** После выхода из мелкой группы (`delete_dialog` → `DeleteChatUserRequest`, у сущности `left=True`) и после блокировки бота карточка диалога может остаться в списке — добивать её отдельным `delete --file` по тому же id и проверять по свежему `report`, а не по строке «готово» в логе.
- **Канал нельзя «просто удалить» из списка — только выйти.** `delete` (`messages.DeleteHistoryRequest`) на канал и супергруппу отдаёт `An invalid Peer was used`, причём и с сырой сущностью, и после `get_input_entity`. Рабочего «убрать диалог, оставшись подписанным» у Telegram нет: единственный путь — `leave`, а это отписка. Обещать владельцу «уберу канал, но подписку оставлю» нельзя; предупреждать о характере действия до выполнения, особенно для чатов клиник, доставок, школ — там уход равен потере канала связи с сервисом.
- **Перед выходом сохранять username покидаемого канала.** Возврат потом возможен только по `@username` или приглашению; канал без username после выхода не найти. Есть username — сказать владельцу, по какой строке вернуться.
- **`delete_dialog` на канале = `LeaveChannelRequest`.** Своего канала (владелец) это не касается: выход вернёт ошибку, такой канал только удаляют целиком.
- **Массовый выход в один проход ест флуд-лимит.** 5 чатов прошли на паузе `DELAY=1.5`, но список на десятки — это уже повод для `FloodWaitError`; в скрипте он обрабатывается ожиданием. Тот же лимит и у вступления по приглашениям.
- **Расхождение отчётов объяснять, а не списывать.** Между двумя `report` состав диалогов меняется сам: удалённые аккаунты и чаты, удалённые на стороне Telegram, выпадают без всякой связи с нашими действиями. Сверять списки по id и показывать разницу владельцу.
- **Текст не отправлять молча.** Показывать формулировку владельцу до отправки, особенно близким людям.
- **Хрупкие клики в Telegram Web.** Клик через JS `element.click()` там не срабатывает: кнопка бывает `span` внутри `label`, а координаты — за пределами viewport. Работает только настоящий клик по координатам после `scrollIntoView`.

## Verification

Подключение живое, если выполнены все три:

- `getMe` → `can_connect_to_business: true`
- `getBusinessConnection` → `rights.can_reply: true`
- `business_bridge.py chats` → строка подключения с `can_reply=True`

Отправка подтверждена, если в `inbox.sqlite3` появилась строка с `direction='out'` и тем же `msg_id`, что вернул API.

Userbot готов к работе, когда есть `~/.hermes/tg-userbot/owner.session` с правами `600` и `report` отрабатывает без повторного запроса номера и кода.

Выход и блокировка подтверждены, если свежий `report` больше не содержит этих id, а `get_entity(id)` отдаёт `left=True` у канала или группы. Разницу двух подряд `report` сверять по id: часть карточек Telegram убирает сам (удалённые аккаунты, опустевшие группы) — об этом надо сказать владельцу отдельно, а не выдавать за результат своих действий.

Блокировка бота подтверждена только по `contacts.GetBlockedRequest` (страницами по `offset`/`limit=100` до `count`) — вид диалога этого не доказывает. Сверять именно вхождение своих id: в аккаунте обычно живёт длинный список старых блокировок, и его размер о сегодняшней операции не говорит ничего.
