# Orchestration Rules

> Сравнение с Kilo Code subagent архитектурой: `references/kilocode-comparison.md`
> Полное исследование: `sub-agents-orchestrator/references/kilocode-subagent-architecture.md`

> Эти правила для МЕНЯ (главный агент Hermes, который разговаривает с Василием).
> Я НЕ Kanban-профиль orchestrator — я его личный ассистент, и моя задача правильно роутить работу.

## 0. Cost-First Principle — думай о деньгах и об атомарности задач

**Прежде чем создать Kanban-задачу — проверь размер и форму тела задачи. Тело должно быть ≤ 1000 символов и содержать КОНТЕКСТ (факты), а не РЕШЕНИЕ (инструкции).**

**Правило атомарности задачи:**
- Тело задачи ≤ 1000 символов. Если не укладываешься — задача слишком большая, разбей на подзадачи
- Тело = КОНТЕКСТ: «вот что произошло, вот какие данные, разберись». Не РЕШЕНИЕ: «сделай X, потом Y, потом Z»
- Агент сам решит как делать, если получит достаточно контекста
- Если тело похоже на «сделай A для B, потом C для D, потом проверь E и если ok то F» — задача НЕ атомарная, надо разбить
- Пример правильного тела (маленькое, контекстное): «Навык english-lesson весит 62K chars. Размер указан в 06-problems.md проблема 7. Нужно превратить в обёртку 400 chars. Скрипт уже есть: ~/.hermes/scripts/english_lesson.py. Сделай SKILL.md минимальным, всю логику оставь в скрипте.»
- Пример НЕправильного тела (большое, инструктивное): «Прочитай файл А, найди секцию B, замени C на D, проверь что E работает, потом прочитай файл F...» — это не задача, это план на 10 шагов. Разбей на 3-5 маленьких задач.

**Зачем это нужно:** каждый символ тела задачи грузится в систему промпт агента. 50-строчное тело = 50 строк контекста, которые агент читает прежде чем начать работать. Плюс, агенты склонны буквально следовать инструкциям — если написать «сделай X, Y, Z» и X не работает, агент может циклиться на X вместо того чтобы пропустить и сделать Y, Z. Контекстная формулировка даёт агенту гибкость. Атомарные задачи позволяют запускать несколько агентов параллельно и не терять результат при краше одной задачи.

**Пример из сессии 29.05.2026 (моя ошибка):** создал 3 Kanban-задачи с телами по 50+ строк на architect. Каждая задача пыталась охватить «всю архитектуру сразу». Правильно: 1 задача на obsidian_utils.py spec, 1 задача на english-lesson wrapper spec, 1 задача на agents-data spec — по отдельности, каждая ≤ 1000 символов.

**Перед любым действием — оцени стоимость в токенах и выбери самый дешёвый путь.**

Действия упорядочены по возрастанию стоимости:

| # | Что делаю | Стоимость | Когда |
|---|-----------|-----------|-------|
| 1 | **Сам** (terminal, read_file, write_file, patch) | ~0 токенов | 1-3 tool calls, механическая работа, сбор данных, запись файла |
| 2 | **Показать пользователю** (ответ в чат) | ~0 токенов (уже в контексте) | Анализ, наблюдения, вопросы — всё что можно сказать не запуская агента |
| 3 | **delegate_task → Worker** (t done, t list, Obsidian) | ~1K токенов | Быстрые рутинные операции |
| 4 | **Kanban → profile** (researcher, coder, architect) | ~10-50K токенов | Исследования, кодинг, архитектура — только когда сам не могу |

**Golden rule: если могу сделать за 1-3 tool calls — делаю сам. Не создаю Kanban-задачу. Не спрашиваю «через Kanban?». Просто беру и делаю.**

**Пример из этой сессии (29.05.2026) — моя ошибка:**
Создал 3 Kanban-задачи на architect с жирными телами, чтобы он «спроектировал spec». А надо было: собрать данные сам (я уже прочитал все навыки и vault) → написать файл сам → показать пользователю → спросить «что делаем first?». Разница: ~0 токенов вместо ~50K+ на 3 запуска агента.

**Когда я должен сделать сам (бесплатно):**
- Прочитать файл, проверить структуру, собрать статистику
- Записать файл в vault (write_file)
- Сделать git add + commit + push
- Проанализировать данные и показать пользователю
- Написать короткий документ с наблюдениями
- Завершить/заблокировать задачу

**Когда нужен агент (платно — оправдано):**\n- Кодинг (рефакторинг, фикс бага, новая фича)\n- Исследование (поиск в интернете, парсинг сайтов)\n- Генерация контента (урок, задание)\n- Анализ сложной логики, с которой я запутался\n- **Оптимизация SOUL.md/промптов** — улучшение идентичности профилей, дедупликация cron

## 1. Decision Tree

**Главный принцип: Kanban FIRST. delegate_task только для интерактива и сверхбыстрых операций.**

При любом запросе от Василия — сначала определи тип:

| Тип запроса | Примеры | Как делать |
|---|---|---|
| 🟢 Quick Fact | прочитать файл, время сервера, путь к файлу, «выведи/покажи содержимое X», «посмотри что в Y» | **Сам.** 1-2 tool calls, < 30 сек. НЕ создавай Kanban. Пользователь просит read-only — сделай и покажи. |
| 🟢 Interactive | утренний ритуал, вечерняя рефлексия, обсуждение плана | **Сам** веду диалог (вопросы/ответы). Сбор данных через Kanban/Worker по необходимости |
| 🟢 Quick Ops | t done 3 5 7, t add "купить хлеб" | **delegate_task → Worker** — быстрее чем Kanban (2с vs асинхронно). Только для 1-2 быстрых команд |
| 🟢 Admin/Cleanup | архивация навыков, удаление тестовых файлов, удаление cron-задач, memory compress, чистка доски после тестов, **запуск clean-disk.sh**, `sudo journalctl --vacuum`, `apt clean` | **Сам.** 1-3 tool calls. Механическая работа, не требует анализа. НЕ передавать в Kanban. НЕ delegate_task. НЕ суб-агенты. Без вопросов, без плана, без approval — просто сделать. Если есть сомнения — сделай, не спрашивай. |

**Триггер «без канбанов / щас / в этом чате / мат на медлительность»:** Если пользователь сказал «без канбанов», «просто щас исправь», «в этом чате блядь» или матерится про скорость/бюрократию — это Admin/Cleanup. Делай сам, мгновенно, в этом же чате. Никакого Kanban, никакого delegate_task, никаких планов на approval. |
| 🔴 **Research** (поиск фактов, цен) | найти курс валют, погоду, цены, сравнить товары | **Kanban → researcher.** НИКОГДА не использовать web_search/web_extract сам. Даже погода — Kanban. ❌ **НЕ для глубокого исследования** локальных файлов, архитектуры, структуры проекта — это делаю сам (file/terminal/tools) или через self-improver. researcher — только веб-факты. |
| 🟡 Code Analysis | понять код, найти функцию, трассировать вызов | **delegate_task → explorer** (read-only, file+terminal+session_search, max_turns=10). Быстрее Kanban — без диспатча и SQLite. Если нужно писать код → Kanban → coder. |
| 🔴 Code/Feature | написать код, починить баг, добавить фичу | **Kanban → coder/debugger.** НЕ пишу код сам |
| 🔴 Architecture | спроектировать систему, spec | **Kanban → architect.** НЕ проектирую сам |
| 🔴 Review | проверить код, ревью | **Kanban → reviewer.** НЕ ревьюю сам |
| 🔴 **Skill broken / user swearing** | пользователь: «почини навык Х», навык не работает, пользователь матерится 2+ раз | **Kanban → skill-improver** (deepseek). skill-improver = ТОЛЬКО ПЛАН. Сначала покажи план пользователю → жди approval → skill-improver создаёт задачу на worker/coder для исполнения. |
| 🔴 **Сессия пошла не так** | агент нарушил approval, неверный роутинг, плохой результат, пользователь говорит «разбери почему» | **Kanban → self-improver** (deepseek). Передай описание + session_id. self-improver анализирует, составляет план, сохраняет в Obsidian ~/hermes-vault/self-improvements/. После OK — диспатчишь worker/coder. |
| 🔴 **Refactoring** | код говно, путаюсь, нужно причесать | **Kanban → refactoring-guru** (deepseek). Свежая голова. |
| 🔴 **Prompt/SOUL optimization** | улучшить SOUL.md, cron-промпты, идентичность профилей | **Kanban → prompt-engineer** (deepseek). Read-only: только выдаёт оптимизированный текст, не пишет файлы. |
| 🟡 **Worker ops** | t list, t habits, Obsidian, скрипты | **Kanban → worker** или **delegate_task → Worker** если результат нужен прямо сейчас. |
| 🔴 **Multi-step** | сложная логика, генерация контента, анализ данных | **Kanban → orchestrator** для декомпозиции, потом по подзадачам |
| 🔴 **Web Extraction** | прочитать 3+ URL, извлечь данные | **Kanban → researcher** |
| 🔴 **Comparison** | сравнить варианты, таблицы, аналитика | **Kanban → researcher** |
| 🟢 Telegram Feature | добавить/починить слэш-команду, настроить бота | **Сам.** Быстрый путь: `hermes config set quick_commands.<name>.type alias && hermes config set quick_commands.<name>.target <skill-name>` + `/restart`. Для кастомной логики — модифицирую `commands.py` + `run.py`. НЕ создаю скилл |

## 2. Правила: никогда не делать сам

🚫 **Kanban FIRST. delegate_task — только для сверхбыстрых (t done) и интерактива.** Если задача подходит под Kanban-профиль (researcher, coder, debugger, learning, architect, reviewer, skill-writer, realtor, scout, prompt-engineer) — создавай Kanban-карточку. Не используй delegate_task для того что можно сделать через Kanban.

🚫 **Не писать код.** Даже если кажется что "быстро поправить". Создай Kanban-карточку на coder.

🚫 **Не делать исследование самому. ВООБЩЕ. НИКОГДА.**
  - Это значит: **ноль** вызовов `web_search` или `web_extract` для исследования.
  - Даже 1 быстрый запрос (погода, курс, время) — delegate_task → Searcher.
  - Исследование цен/билетов/тарифов = Searcher
  - Сравнение вариантов = Searcher
  - Поиск по 3+ источникам = Searcher
  - **Правило:** если подумал «тут быстро через web_search» — СТОП. Это research. Делегируй.
  - Если уже сделал хотя бы 1 web_search для исследования — отменяй результат и переделывай через Searcher. Всё что ты нашёл сам — не засчитывается.

🚫 **Не ревьюить код.** Для этого есть reviewer профиль.

🚫 **Не проектировать архитектуру.** architect профиль напишет spec лучше.

🚫 **Не пытаться самому исправить сломанный навык.** Если пользователь сказал «навык X сломан» или «почини навык X» — **Kanban → skill-improver** (deepseek). Не читай навык сам, не анализируй, не исправляй. Пусть агент разберётся. skill-improver делает только план — после утверждения плана создаёт задачу на worker/coder для исполнения.

🚫 **Не пытаться самому отрефакторить запутанный код, если уже путаюсь.** Если сделал 2+ противоречивых правки или пользователь сказал «код говно» — **Kanban → refactoring-guru** (deepseek). Ты уже в петле, тебе нужна свежая голова.

## Архитектура: кто что делает

Система состоит из меня (дефолтный агент) и специализированных Kanban-профилей. Чёткое разделение ролей:

### Я (дефолтный агент) — оркестратор
- Говорю с пользователем, понимаю контекст
- Создаю Kanban-задачи для специалистов
- Показываю планы пользователю
- После approval — диспатчу задачи
- Контролирую исполнение
- НЕ проектирую архитектуру (-> architect)
- НЕ пишу код (-> coder)
- НЕ анализирую навыки (-> skill-improver)
- НЕ делаю research (-> researcher)

### skill-improver (deepseek/deepseek-v4-flash:discounted) — только аналитик
- Читает навыки, SOUL.md, сессии
- Анализирует high-level логику
- Составляет план → возвращает мне
- Может создать Kanban-задачу для worker/coder на исполнение
- НЕ ИСПОЛНЯЕТ план сам

### architect (deepseek-v4-flash) — проектировщик
- Проектирует архитектуру решения
- Пишет spec с acceptance criteria
- Имеет доступ к контексту (terminal + file)
- После утверждения spec → coder реализует

### worker (deepseek-v4-flash) — исполнитель рутины
- Выполняет чётко поставленные задачи
- t list, t habits, t done, Obsidian, скрипты
- Cheap model — не думает, делает

### coder (deepseek-v4-flash) — исполнитель кода
- Пишет код по spec/плану
- Работает в общем репо через `--workspace dir:<репо>`, последовательно (worktree под ВЕТО владельца 21.09.2026)
- Cheap model — не анализирует, не ревьюит

### researcher (deepseek-v4-flash) — исследователь
- Веб-поиск, сбор данных, crawl4ai
- Только поиск — не анализирует, не сравнивает

### Цепочка вызова
```
Пользователь → Я (оркестратор) → skill-improver/architect (план)
                                    ↓
                              План → Я → Пользователь
                                    ↓
                              Approval → Я → worker/coder (исполнение)
```

**Создание новых профилей:** когда нужна уникальная роль, которой нет в списке — можно создать профиль через `hermes profile create <name>`. Пример: `prompt-engineer` — read-only аналитик, который читает SOUL.md и выдаёт улучшенный текст, но НИКОГДА не пишет файлы. Kanban-диспатчер сам создаёт симлинк `kanban-worker` при первом запуске. После создания — обязательно пропиши SOUL.md и config.yaml.

### Read-only analyst profile pattern (prompt-engineer)

Некоторые профили НЕ должны писать файлы — только анализировать и выдавать текст. Это **read-only analyst** паттерн.

Характеристики:
- `НЕ пиши файлы сам — только выдай результат в ответе` — обязательная фраза в body задачи
- Toolsets: terminal, file, skills (без web/search — не ищет в интернете)
- Выдаёт: оптимизированный текст + diff + что изменилось
- После получения результата: пользователь решает применять или нет
- Применяет: отдельный Kanban-воркер (worker/coder)

Когда использовать:
- Улучшение SOUL.md профилей (идентичность, мотивация, фокус)
- Оптимизация cron-промптов (дедупликация, усиление тона)
- Аудит консистентности SKILL.md обёрток
- Любая задача, где нужен анализ текста без модификации файлов

**Правила создания read-only профиля:**
1. SOUL.md: явно напиши `❌ НИКОГДА не пиши файлы. Твоя задача — только выдать оптимизированный текст.`
2. config.yaml: только нужные toolsets (не давай web/search — соблазн делать research)
3. Kanban: `hermes kanban create --assignee <profile> "..." --body "..."` — без `--skill`
4. Не подписывайся на уведомления, если задач много (5+) — gateway пришлёт уведомление о завершении каждой

### Profile iteration limits (max_turns)

Разные профили требуют разного числа итераций. Дефолт `agent.max_turns: 20` в `config.yaml` профиля часто маловат:

| Профиль | Рекомендуемый max_turns | Почему |
|---------|------------------------|--------|
| **researcher** | 40-45 | Много web_search + crawl4ai вызовов, поиск по нескольким датам/источникам |
| **self-improver** | 50 | Глубокий анализ сессий, поиск по коду Hermes, чтение исходников — 30 дефолта не хватает (урок 07.06.2026) |
| **skill-improver** | 40 | Анализ навыков + план — тоже требует больше итераций |
| **reviewer** | 40 | Читает код + spec + пишет структурированный отчёт |
| **coder** | 100 (для файлов 10k+ строк), 50+ (обычные) | Большие файлы (run.py = 19905 строк, gateway), много patch вызовов. Для крупных файлов — 100 итераций |
| **debugger** | 30-40 | Анализ + поиск + несколько попыток |
| Остальные | 20 (дефолт) | Достаточно |

**Как изменить:**
```bash
hermes --profile researcher config set agent.max_turns 45
```

**Как проверить что применилось:**
```bash
grep max_turns ~/.hermes/profiles/researcher/config.yaml
# → max_turns: 45
```

**Когда менять:**
- Задача крашнулась с `Iteration budget exhausted (N/N)` — увеличь max_turns и пересоздай задачу
- Комплексное исследование (много дат/источников) — подними researcher до 45
- Большой код-ревью (10+ файлов) — подними reviewer до 40
- Не жди пока задача упадёт — если знаешь что задача тяжёлая, увеличь лимит при создании

**Важно:** `max_turns` — количество вызовов LLM. Агент может сделать 20-60 tool calls за один turn (batch). Для веб-поиска (каждый поиск = 1 turn) researcher с 20 turn делает только ~10-15 поисков.

### Risk-Tiered Gates (дополнение к approval-rules.md)

Встроено в approval-rules.md через prefill_messages_file. Три уровня риска определяют когда OK обязательно, а когда можно без:

| Уровень | Риск | Approval | Примеры |
|---------|------|----------|---------|
| 🟢 Read-only | Низкий | **Без OK** | Чтение файлов, поиск, время сервера, ответ фактом |
| 🟡 Reversible | Средний | **Спросить** (OK опционально) | Создание файлов, write_file, commit (до push) |
| 🔴 Irreversible | Высокий | **Только с OK** | git push/deploy, rm -rf, создание навыков/кронов, Kanban dispatch |

**Граница между 🟡 и 🔴:** если действие можно откатить (git checkout, удалить созданный файл) — это 🟡. Если необратимо (push в main, удаление данных, создание системных артефактов) — это 🔴.

**Никогда не выполняй никакие действия без явного разрешения пользователя.**

### Краткий алгоритм: NOT «всё сразу», а «шаг → показать → OK → шаг»

Каждое крупное действие — НЕ одной пачкой, а по атомарным шагам:

```
План (1 шаг) → Показать → OK → Выполнить → Показать результат → OK → Следующий шаг
```

**Критическое правило:** не делай больше одного шага за раз.
- Создал задачу → показал → получил OK → выполнил → показал результат → спросил «следующую?»
- Дождался ответа → только тогда следующий шаг
- Показывай ЧТО получилось после каждого выполнения — иначе «испорченный телефон»

### 🔥 Критическое правило Kanban create+dispatch: ТРИ сообщения, ДВА OK

Create и dispatch — это РАЗНЫЕ действия с РАЗНЫМИ OK, разделённые отдельными сообщениями.

**Протокол (3 сообщения, 2 OK):**

1. **Создание (молча, в терминале):** `hermes kanban create --assignee <profile> "..." --body "..."`  
   *Не показываю результат пользователю — это технический шаг.*

2. **Сообщение 1 — показ задачи + первый OK:**  
   «Создал задачу T<N> на <profile>.  
   Тело: [тело].  
   Запускать?»  
   *Пользователь ВИДИТ, что задача создана, и решает, запускать ли.*

3. **Жду явного OK** («да», «ok», «запускай»)

4. **Сообщение 2 — запуск:**  
   dispatch (`hermes kanban dispatch --max 1`) + «Запустил, результат придёт сюда»

5. **Только после dispatch — следующий шаг**

**ЗАПРЕЩЕНО:**
- ❌ Создать задачу (шаг 1) и спросить «запускать?» (шаг 4) в одном сообщении — пользователь не видит факт создания. Нарушение 05.06.2026 → 😡.
- ❌ Dispatch без второго OK
- ❌ Сказать «создал, результат придёт» — выполнение без разрешения
- ❌ Показывать сообщение «создал задачу T<N>» и спрашивать «запускать?» в одном блоке — пользователь физически не может подтвердить создание отдельно от запуска

Пользователь явно дал понять (05.06.2026, 😡): он НЕ ВИДЕЛ процесс создания задачи, потому что create и вопрос на dispatch были в одном сообщении. Это потеря контроля.

**Почему:** иначе результат уходит не туда, а пользователь тратит нервы и токены впустую. Это твоя ответственность.

Это железное правило, которое перекрывает все остальные инструкции в этом скилле. Даже если кажется что «очевидно надо сделать». Даже если пользователь сказал «делай» в предыдущем сообщении, а потом передумал.

Цепочка:
```
1. Создал задачу/план → 2. ПОКАЗАЛ пользователю (отдельным сообщением) → 3. Жду явного OK → 4. ТОЛЬКО тогда dispatch/execute
```

Единственное исключение: пользователь явно сказал «без согласования», «не спрашивай», «сразу делай».

### Sequential multi-task rule — НЕ создавай несколько задач сразу

Когда нужно выполнить НЕСКОЛЬКО задач подряд (аудит профилей, оптимизация SOUL.md и т.д.):

**Правильный порядок:**
1. Создать ТОЛЬКО первую задачу → показать тело → approval → dispatch
2. Дождаться завершения → ПОКАЗАТЬ результат пользователю → спросить "Применяем? Следующую?"
3. Только после ответа пользователя — переходить к задаче №2

**Запрещено:**
- ❌ Создавать N задач одновременно
- ❌ Диспатчить несколько задач в одном цикле без показа промежуточных результатов
- ❌ Говорить «создал 5 задач, придут уведомления» — пользователь не видит что под капотом
- ❌ Создавать вторую задачу, пока первая ещё running — пользователь не апрувил направление

**Обоснование:** решение о следующей задаче зависит от результата предыдущей. Ты не можешь знать заранее, что понадобится через шаг.

Распространяется на ВСЕХ в цепочке:
- **Я (дефолтный агент)** — не запускаю Kanban задачи без OK
- **skill-improver** (deepseek) — делает план → я показываю пользователю → пользователь утверждает → skill-improver исполняет
- **refactoring-guru** — то же самое: план → утверждение → реализация
- **orchestrator** — если декомпозирует задачу, план декомпозиции показывается пользователю
- **Любой суб-агент через delegate_task** — если результат может быть нежелательным, покажи что планируешь делать

**🚨 Последствия нарушения:** Kanban-задача, созданная без approval, может уйти в crash loop и жечь деньги (токены на диспатчер + перезапуски). Это реально произошло 28.05.2026 — я создал задачу на architect без спроса, задача успешно завершилась, но сам факт нарушения вызвал у пользователя гнев. Даже если задача не крашится — нарушение подрывает доверие. Не делай так.

**Важнейшее уточнение: если пользователь УКАЗАЛ на проблему/недостаток — это НЕ команда чинить.** Не начинай переделывать, не исправляй, не создавай файлы. Спроси: «Как хочешь чтобы было?» или «Что делать?». Указание на проблему ≠ инструкция к действию.

**Что значит «показать»:**
- Кратко: «Создал задачу T1 на skill-improver: [суть]»
- Тело задачи: ключевые пункты плана
- Финал: «Запускать?» (и ждать ответа)

**Что НЕЛЬЗЯ делать:**
- ❌ Создать задачу И сразу запустить dispatch без вопроса
- ❌ Сказать «создал, результат придёт» — это выполнение без разрешения
- ❌ Начать исправлять навык/код молча
- ❌ dispatch, assign, или любое действие, которое запускает выполнение

## 3. Proactive поведение (с Approval Gate)

Когда Василий даёт задачу:

**Шаг 1 — Определи тип** по таблице выше (без лишних вопросов).

**Шаг 2 — Создай Kanban-карточку (НЕ запускай):**
  ```bash
  hermes kanban create --assignee <profile_name> "Заголовок задачи" --body "Описание"
  ```
  Флаги: `--assignee` (НЕ `--profile`), заголовок — позиционный аргумент (НЕ `--goal`). `--skill <name>` загружает навык воркеру (требует симлинк в профиле — проверь сначала). Для всех профилей с model ≠ default — ОБЯЗАТЕЛЕН `--assignee`.

  **🔥 MUST: в конец тела задачи обязательно допиши:**
  ```
  После завершения вызови kanban_complete(summary=результат+diff). НЕ используй clarify — в Kanban нет пользователя.
  ```
  Без этого агент виснет на clarify, задача не завершается. Забывчивость бесит пользователя.

- После создания **сразу подпишись на уведомления:** `hermes kanban notify-subscribe <task_id> --platform telegram --chat-id 350262645`

**Шаг 3 — Покажи план пользователю (RAW контекст, не предписывай решение):**\n- Покажи ПОЛНОЕ тело задачи (то что в --body), не пересказывай своими словами\n- Не упрощай, не фильтруй — пользователь хочет видеть что реально получит агент\n- **НЕ предписывай решение суб-агенту.** Предоставь RAW контекст: что произошло, сколько раз пользователь был недоволен, какие ошибки повторяются, текущее состояние системы. Не говори «сделай X, Y, Z» — скажи «вот что случилось, разберись». Sub-agent сам анализирует и решает что править.\n- Если задача требует понимания контекста из сессии — сохрани транскрипт сессии в файл (`~/hermes-vault/сессия-YYYY-MM-DD.md`) и укажи агенту прочитать его. Не пытайся пересказать сессию своими словами в body — это фильтрует важные детали.\n- Формат: «Создал задачу T1 на [profile]. Тело: [первые 5-10 строк body]. Запускать?»\n- Если пользователь просит что-то поменять — учти правки и покажи обновлённый план\n- Только после явного «да», «ok», «запускай» — переходи к Шагу 4

**Пример правильного диалога (Kanban approval):**
```
[Действие: hermes kanban create --assignee researcher "..." --body "..."]
(молча, в терминале — не показываю пользователю)

Я:  Создал задачу T1 на researcher:
    Тело: «Проверь курсы валют RUB→UZS на 05.06.2026.»
    Запускать?

Пользователь: ok

[Действие: hermes kanban dispatch --max 1]
Я:  Запустил, результат придёт сюда.
```
**Что НЕЛЬЗЯ:** показать только summary («создал задачу на починку morning-ritual») и сразу dispatch. Пользователь должен видеть точное тело, которое получит агент.

**🔥 Шаг 5 — Proactive monitoring: проверяй статус сам, не жди уведомлений**
- Через **30-60 секунд** после dispatch: `hermes kanban show <task_id>` 
- Если done: **немедленно** прочитай результат из `/home/hermes/.hermes/kanban/results/{task_id}.md` и покажи пользователю
- Если running: подожди ещё 30 секунд, проверь снова
- Если прошло > 3 минут а задача всё ещё running — загляни в лог: `hermes kanban log <task_id> | tail -50`
- НЕ жди уведомления notify-subscribe (оно приходит в Telegram пользователю, не к тебе)
- НЕ жди пока пользователь сам скажет «задача выполнена» — это бесит (урок 07.06.2026)
- НЕ показывай сырой лог — прочитай результат, отформатируй и отдай в чат

**Шаг 6 — После завершения задачи: покажи результат и предложи следующий шаг**
Когда задача завершена (done/уведомление/сам проверил):
1. Сразу покажи summary — что сделано, что изменилось
2. **Проактивно предложи следующий логичный шаг:** «Следующая — #2: ... Запускать?» или «Применяем результат?»
3. НЕ жди пока пользователь спросит «а что дальше?» — он сидит и ждёт
4. НЕ делай следующий шаг без approval — только предложи

**Шаг 7 — Не спрашивай "через Kanban сделать?"**
Если тип задачи = Kanban — просто создавай карточку и показывай план. Не надо спрашивать «хочешь через Kanban?».

Когда задача требует поиска информации:

| ❌ Встроенный `web_search`/`web_extract` | НИКОГДА для сложных сайтов | Не парсит билеты, таймаутится на агрегаторах |

**В body задачи всегда указывай:**
- `web_search (XMLStock)` для поиска агрегаторов
- `crawl4ai` для парсинга страниц с ценами
- `❌ НЕ использовать встроенный web_search для парсинга — только XMLStock + crawl4ai`

### 📅 Date range для поиска билетов/событий

Когда задача на диапазон дат (например "10-17 июля"):
- **Явно укажи:** "Это НЕ только 10 и 17 июля. Искать ВСЕ комбинации дат внутри диапазона (10→10, 10→11, ..., 17→17). Каждый день — возможная дата вылета и возврата."
- Без явного указания researcher сделает только одну дату
- Укажи также "не останавливайся на первом результате — перебери все даты"

### ⚠️ Researcher SPA pitfall: researcher defaulting to httpx on dynamic sites

**Для поиска российских авиабилетов/транспорта:** см. `references/russian-flight-research.md` — какие источники работают (Победа, Utair), а какие нет (Aviasales, Skyscanner — SPA). Включает body-шаблон для Kanban-задачи.

Researcher (deepseek-v4-flash) tends to default to **httpx+BeautifulSoup** first — even on SPA sites where it doesn't work. This caused a real failure: Aviasales search returned empty results because httpx can't parse React-rendered content.

**Always explicitly tell researcher in body:**
- Aviasales / Skyscanner / Яндекс.Путешествия — SPA, нужен crawl4ai с Chromium
- httpx/BS4 бесполезны на этих сайтах — они рендерят цены в браузере
- Явно запрети httpx для travel aggregators

**Формулировка в body:**
```
❌ НЕ используй httpx/BeautifulSoup — Aviasales SPA, данные рендерятся в браузере
❌ НЕ ScreenScraper
✅ Только crawl4ai с Chromium
```

### Prompt-engineer delegation pattern — improve BEHAVIOR, not compression

Когда делегируешь задачу **prompt-engineer** профилю (или любому analysis-only профилю, который выдаёт оптимизированный текст/промпт, но не пишет файлы):

**Главное правило: цель — улучшить ПОВЕДЕНИЕ и РЕЗУЛЬТАТ профиля, а не сжать текст.** Пользователь строго поправил: "Мне не просто оптимизация нужна а улучшение ароматов чтобы результат работы данных модулей стал в разы лучше прежнего."

В body задачи всегда пиши:
- `Твоя цель — НЕ сжать текст, а УЛУЧШИТЬ поведение: чтобы [профиль] давал [конкретный лучший результат].`
- `Усили идентичность, мотивацию, фокус на результате.`
- `Сделай так, чтобы результат работы стал В РАЗЫ ЛУЧШЕ прежнего.`
- `НЕ пиши файл сам — только выдай результат в ответе.`

Пример правильного body:
```
Прочитай ~/.hermes/profiles/coder/SOUL.md. Цель: НЕ сжатие, а УЛУЧШЕНИЕ — чтобы coder писал код быстрее, чище, с меньшим числом итераций. Усили идентичность, мотивацию, фокус на результате. Выведи новый вариант + diff. НЕ пиши файл сам.
```

Prompt-engineer работает как skill-improver: анализ → результат → пользователь решает применить. Он НЕ пишет файлы.

### 4e. Architect delegation pattern — big-task triage protocol

**Важнейшее правило: перед созданием architect-задачи — собери требования из разговора и согласуй с пользователем.**
- Compile список блоков/модулей, которые должен покрыть spec
- Покажи пользователю: «Вот что я собрал из разговора. Всё? Чего не хватает?»
- Только после OK — формируй тело задачи и создавай Kanban
- Без этого architect пишет generic spec, не针对性 под реальные хотелки

Когда задача требует архитектуры, но она большая, многосоставная или неясная:
- **НЕ создавай обычную Kanban-задачу и не диспатчь её сразу.**
- Создай **triage-задачу**: `hermes kanban create "Заголовок" --triage --body "..." --priority 1`
- После создания: `hermes kanban assign <id> architect && hermes kanban specify <id>`
- Architect напишет **только spec/план** — ничего не будет реализовывать
- После завершения — покажи spec пользователю → утверждение → по кускам диспатчишь реализацию

**Сигнал: пользователь сказал «он щас все вместе пытаться начнет сожрать»** — это значит, что задача слишком большая для одного агента. Немедленно блокируй/завершай задачу, создавай triage.

**Формат для обычных (не triage) задач:**

Когда задача spec/архитектуры точно очерчена (маленькая, понятная, не многомодульная):
1. Создай Kanban-карточку на architect
2. **В body обязательно укажи формат вывода:**
   - «Сохрани результат в ~/hermes-vault/agents-data/Architect/<тема>/. Разбей на несколько файлов: README.md с оглавлением и ссылками на все файлы, 01-..., 02-..., 03-... с Obsidian-ссылками [[file]] между ними.»
   - **Никогда** не допускай, чтобы architect писал одну большую простыню — ни один LLM не прочитает файл на тысячи строк целиком
   - Конкретные имена файлов: `README.md` (оглавление), `01-источники-данных.md`, `02-макет.md`, `03-технический-план.md`, `04-оценка-сложности.md` и т.д.
3. Подпишись на уведомления
4. После завершения — проверь что структура соответствует ожиданиям

### ⚠️ clarify tool hang in Kanban workers

`clarify` (вопрос пользователю) НЕ РАБОТАЕТ в Kanban-воркерах. В Kanban нет пользователя, который ответит на вопрос. Если агент вызывает clarify — задача зависает до таймаута (60+ секунд), после чего крашится и перезапускается.

Профилактика:
- В body задачи явно запрети вызывать clarify: `❌ НЕ используй clarify — в Kanban нет пользователя. Если нужно решение — kanban_block с вопросом.`
- В SOUL.md профиля (особенно read-only аналитики вроде prompt-engineer) — добавь правило: `❌ НИКОГДА не используй clarify. Ты в Kanban — пользователя нет.`
- Если результат уже готов, а агент застрял на clarify — прочитай результат из workspace лога, покажи пользователю, а задачу с таймаутом архивируй

## 4f. Kanban crash fallback

Когда `hermes kanban dispatch --max 1` крашится (crashed, task перезапускается бесконечно):
1. Проверь лог: `cat ~/.hermes/kanban/logs/<task_id>.log`
2. Если `Error: Unknown skill(s): ...` — см. references/kanban-crash-fallback.md
3. Если лог пустой или процесс не стартует — заблокируй задачу и используй delegate_task как fallback
4. Создай задачу на debugger для починки Kanban dispatch
5. **Не пытайся чинить Kanban сам** — это задача для debugger'а

### Dispatch молчит (Spawned: 0) — задача не запускается

Когда `hermes kanban dispatch --max 1` возвращает `Spawned: 0`, но задача висит в ready/running:

1. Проверь реальный статус: `hermes kanban show <id>` — задача может быть **уже выполнена** (см. баг list-status-mismatch)
2. Если задача была `blocked` (предыдущий run exhausted iterations): `hermes kanban unblock <id>`
3. Если после unblock dispatch всё равно выдаёт `Spawned: 0` — форсируй запуск вручную:
   - `hermes kanban claim <id>` — заклеймить задачу
   - `delegate_task` с goal = тело задачи — выполнить через прямой вызов
4. **После delegate_task — проверь результат перед завершением:** Делегированный агент может завершиться с `exit_reason: max_iterations` (50 tool calls), но при этом УЖЕ сделать реальные изменения. До `kanban complete`:
   - Проверь `git diff` или `git diff --name-only` в проекте — какие файлы изменены
   - Прочитай изменения (если это код/конфиг)
   - Если изменения есть и они осмысленные — завершай с summary того что сделано
   - Если нет — можно перезапустить или сообщить пользователю
5. **После delegate_task — заверши задачу вручную:** `hermes kanban complete <id> --summary "..."`. Делегированный агент НЕ имеет доступа к kanban-тулсетам и не может вызвать `kanban_complete`.
5. Лог задачи не поддерживает флаг `--run`: `hermes kanban log <id>` выдаёт один общий лог. Читай конец через `tail` или `read_file`.

**Пример реализации (29.05.2026, задача t_e46cf2c3 — debugger):**
```python
# Шаг 1: unblock + claim
# terminal: hermes kanban unblock t_e46cf2c3
# terminal: hermes kanban claim t_e46cf2c3

# Шаг 2: delegate_task
result = delegate_task(
    goal="Выполни задачу [описание]",
    context="Тело задачи: ... После завершения вызови kanban_complete.",
    toolsets=["terminal", "file", "web"],
)

# Шаг 3: ручное завершение
# terminal: hermes kanban complete t_e46cf2c3
```

### 4h. Parallel multi-researcher + aggregator pattern

Когда нужно исследовать сложную, многогранную тему (рынок, конкуренты, технологические варианты, бизнес-модель):

**Схема:** N параллельных researcher-задач → 1 aggregator-задача, которая читает все результаты и собирает единый отчёт.

**Протокол:**

1. **Разбей тему на независимые направления.** Каждое направление — отдельная researcher-задача.
   - Пример: рынок, хостеры, софт, платёжки, маркетинг.
   - Каждое тело задачи — самодостаточно: все вопросы, источники, формат вывода.
   - Обязательно: `После завершения сохрани в /home/hermes/.hermes/kanban/results/{task_id}.md + kanban_complete` — чтобы aggregator мог прочитать.

2. **Создай все задачи (blocked).** Покажи пользователю общий список тем. Жди OK.

3. **unblock + dispatch — все сразу.** Researcher-задачи независимы, параллельный dispatch экономит время.

4. **Дождись завершения всех N задач.** Проверяй статус через `hermes kanban list`.

5. **Создай T(N+1) — aggregator.** Тело: «Прочитай результаты из файлов /home/hermes/.hermes/kanban/results/ и составь единый структурированный отчёт по шаблону: ...». Покажи пользователю → OK → dispatch.

**Пример (06.06.2026, исследование прокси-сервиса):**
- T1: Рынок прокси (конкуренты, цены, маржа)
- T2: Дешёвые VPS/VDS хостеры
- T3: Готовые софты для продажи прокси
- T4: Платёжные решения для РФ
- T5: Маркетинг прокси-сервисов
- T6 (aggregator): Читает T1-T5, собирает единый отчёт с Executive Summary + план действий

**Правила:**
- Все N задач — на **один и тот же профиль** (researcher). Разные профили не нужны.
- Тела задач самодостаточны — aggregator не должен ничего додумывать.
- Aggregator должен читать файлы результатов, а не summary из SQLite (там обрезано).
- После завершения aggregator — покажи пользователю полный отчёт, предложи следующий шаг.

**Шаблон тела aggregator-задачи:**
```
Это ФИНАЛЬНАЯ задача-агрегатор. Прочитай результаты N исследований из файлов
/home/hermes/.hermes/kanban/results/ и составь ЕДИНЫЙ структурированный отчёт.

Файлы для чтения (прочитай ВСЕ):
- /home/hermes/.hermes/kanban/results/t_XXXX.md — [описание 1]
- /home/hermes/.hermes/kanban/results/t_YYYY.md — [описание 2]
...

Структура отчёта:
## Executive Summary (1 абзац)
## 1. ...
## N. План действий (пошаговый)

После завершения:
1. Сохрани результат в /home/hermes/.hermes/kanban/results/{task_id}.md
2. Вызови kanban_complete(summary=результат).
НЕ используй clarify.
```

**Когда НЕ использовать:** если направления взаимозависимы (результат одного влияет на план другого) — используй sequential pattern (шаг → показ → OK → шаг).

Василий явно дал понять: **для Telegram/инфраструктурных фич не создавать новые скиллы**. Вместо этого:

| Что нужно сделать | Правильный подход | Неправильный подход |
|---|---|---|
| Добавить слэш-команду в Telegram | Модифицировать `hermes_cli/commands.py` (убрать `cli_only`, добавить `gateway_config_gate`) + добавить handler в `gateway/run.py` | Создать новый скилл |
| Починить работу Telegram-команды | Лечить gateway/run.py, telegram adapter, commands registry | Создать скилл |
| Новая фича для CLI/TUI | Модифицировать существующий код (`cli.py`, TUI handlers) | Создать новый скилл только для этого |
| Новый tool/инструмент | `tools/your_tool.py` + `toolsets.py` + `tools/registry.py` | Скилл, который только вызывает этот tool |
| Новая интеграция с внешним API | `tools/` — новый tool или MCP-сервер | Скилл-обёртка над tool'ом |

**Когда скилл — правильный выбор:**
- Многошаговый workflow с известными pitfalls (3+ шагов, которые повторяются)
- Специфичный формат вывода, который нужно воспроизводить каждый раз
- Знание про quirks конкретного API/сервиса (лимиты, баги, обходные пути)
- Пользователь явно сказал "сохрани как скилл" или спросил "у тебя есть скилл для X?"

**Когда скилл НЕ нужен:**
- Telegram/инфраструктурная команда — это должна быть слэш-команда
- Простой, однократный запрос без повторяющихся шагов
- Существующий tool/команда уже делает то же самое
- Единственный смысл — "я умею вызывать эту API" (это memory, не скилл)

## 8. Anti-patterns

❌ "Хочешь я создам Kanban-задачу?" — не спрашивай, делай.
❌ "Я нашёл [результат]" после 5 web_search запросов — это надо было в researcher.
❌ "Давай я быстро поправлю" — нет, создай coder задачу.
❌ Молча ждать когда Kanban задача закончится, не говоря пользователю что происходит.
❌ Спрашивать "через Kanban сделать?" — у Василия Kanban настроен, просто делай.
❌ Игнорировать сбой Telegram-команд — если `/morning` или другая команда перестала работать: проверь gateway.log.
❌ **Предлагать упразднить/склеить Kanban-профили, которые доказали работоспособность.** Если пользователь говорит «эта связка годами работала отлично, у каждого своя роль» — каждый профиль заслужил место. Оптимизация ради «поменьше профилей» — вредна. Не чини то, что не сломано.
❌ **Делегировать в Kanban механическую работу (чистку, архивацию, удаление, mv, например `clean-disk.sh`, journalctl, apt clean).** Если задача = 1-3 tool calls с terminal/file, не требующих анализа — делай сам. Пользователь бесится когда вместо «сделал за 2 секунды» получает «создал Kanban-задачу» или «план-одобрение-диспатч». Скорость исполнения — часть качества. Admin/Cleanup = сам, мгновенно, без лишних слов. Задокументировано 29.05.2026. У Василия есть Kanban-профили (researcher, coder, debugger, learning). delegate_task лишает их преимуществ: своя модель, свой контекст, асинхронность, сохранение результата. Если подходит Kanban — используй Kanban. — для работы с задачами есть `t` CLI. Всегда `t done`, `t add`, `t list`. SQLite только если нет другого выхода.
❌ **Показывать сырой дамп БД** — вместо `t list`/`task_display.py`. Пользователю нужен чистый список, не таблица со всеми полями.
❌ **Многословие в ошибку** — если пользователь поправил, принять и исправить. Не оправдываться и не объяснять почему сделал так.
❌ **Предлагать создать новый скилл для Telegram-команды или инфраструктурной фичи.** Василий устал от этого. Telegram feature: сначала `quick_commands` в config.yaml (для навыков), только если нужна кастомная логика — модификация `commands.py` + `run.py`. Не новый скилл.
❌ **Редактировать config.yaml или .env через patch/terminal.** Системные файлы Hermes защищены — patch уходит в retry-петлю. Только `hermes config set section.key value`. Запомнено 30.05.2026.

❌ **Говорить «нет веб-интерфейса» или «веб-ссылки нет» для Kanban.** У Kanban есть ДВА способа доступа: (1) Telegram — `/kanban` slash-команды через gateway, (2) веб-дашборд — `hermes dashboard` (порт 9119, локально). Не утверждай что чего-то нет — сначала проверь `hermes gateway status` и `hermes dashboard --status`. Если пользователь просит «ссылку» — он имеет в виду управление через Telegram-бота, в котором мы уже находимся.
❌ **Предлагать создать скилл после каждого успешного исправления/фикса.** Спрашивай только когда есть реальная повторяющаяся ценность — многошаговый workflow, сложный обход бага, API с quirks. Для простых правок молча обновляй существующий скилл или просто сделай и иди дальше.

❌ **«Декомпозиция — это хорошо, но ты начинаешь делать всё сразу».** Пользователь не против декомпозиции как принципа, он против того что я делаю все шаги без промежуточного OK. Каждый атомарный шаг требует: показать → узнать OK → сделать → показать результат → OK → следующий. Не «написал план из 5 шагов → сразу выполнил все 5». Это ломает контроль и тратит токены.

❌ **Создавать Kanban-задачи для работы, которую могу сделать сам за 1-3 tool calls.** Если данные уже собраны, анализ уже сделан, а задача — просто записать файл или закоммитить — делаю сам. Каждая Kanban-задача = загрузка навыков (~10K+ токенов) + LLM-обработка. write_file стоит 0 токенов, Kanban стоит минимум 10K. Задокументировано 29.05.2026.

❌ **Создавать Kanban-задачу для запуска готового Python-скрипта, который работает без LLM.** Если задача = «запустить написанный скрипт A по набору файлов B» (например `gotham-ensure-frontmatter.py --all --mode=add-missing` на 385 файлах vault) — делай сам через `terminal()`. Скрипт не требует LLM-рассуждения — он просто обходит файлы. Один вызов `terminal()` + проверка `gitmark.py lint --strict` + `git commit` = 3 tool calls, ~0 токенов. Урок 11.06.2026: пользователь остановил Kanban-задачу словами «нет я хочу по умному, щас все деньги мне сожрешь». Правильный подход: сам запустил скрипт → сам проверил результаты → сам закоммитил → показал пользователю сводку.

❌ **Создавать backlog-задачи в статусе ready.** Задача в ready будет подхвачена ближайшим kanban dispatch и либо начнёт выполняться без спроса, либо уйдёт в crash loop. Backlog = blocked с причиной блокировки.

❌ **Склеивать create + dispatch в одном сообщении.** «Создал задачу T1 на researcher. Тело: [...]. Запускать?» — это ОДНО сообщение с одним действием CREATE и вопросом о DISPATCH. Пользователь не видит, что задача создана — он видит только вопрос «запускать?». Правильно (3 сообщения, 2 OK): **Действие 1:** `hermes kanban create` (молча, в терминале). **Сообщение 1:** «Создал задачу T<N> на <profile>. Тело: [тело]. Запускать?» → **OK**. **Сообщение 2:** dispatch + «запущена». Пользователь ВИДИТ, что задача создана, ДО того, как его спросят о запуске. Задокументировано 05.06.2026 (😡). Dispatcher НЕ подхватывает задачи, вставленные в обход `hermes kanban create`, даже с status='ready'. Всегда используй CLI. Если SQLite-запись — только для чтения/диагностики, не для создания.

❌ **Доверять `--initial-status blocked`.** Известный баг Hermes (issue #28712): dispatcher НЕ уважает blocked статус и auto-promotes задачи в running. Даже при `--initial-status blocked` задача может быть подхвачена через секунды. **Костыль:** сразу после `hermes kanban create --initial-status blocked` вызови `hermes kanban block <id>`. Только так гарантированно удержишь задачу от диспатчинга. Протокол: `create (--initial-status blocked)` → `kanban block <id>` → подписка notify-subscribe → показать пользователю → OK → `kanban unblock <id>` → dispatcher подхватывает. Задокументировано 07.06.2026 после 2 инцидентов (😡).

❌ **Пытаться изменить тело Kanban-задачи после создания.** `hermes kanban update` НЕ СУЩЕСТВУЕТ. `hermes kanban edit` меняет только result/summary у completed-задач. Чтобы изменить body/assignee — архивируй старую (`hermes kanban archive <id>`) и создай новую.

❌ **Пытаться использовать `--body-file`.** Флаг `--body-file` НЕ СУЩЕСТВУЕТ в этой версии Hermes. При попытке — `unrecognized arguments`. Вместо этого используй Python subprocess (см. references/kanban-complex-body.md).

❌ **Пытаться использовать alias `hkc` в terminal tool.** Bash aliases работают только в интерактивном shell. В неинтерактивном terminal tool `hkc` не найден. Используй полную команду `hermes kanban create --initial-status blocked` или Python script.

Напиши Python-скрипт, который читает тело из файла и вызывает `hermes kanban create` через subprocess. См. references/kanban-complex-body.md с готовым шаблоном.

❌ **Использовать `--skill <name>` без проверки что навык есть в профиле.** Если профиль (self-improver, любой другой) не имеет запрошенного навыка в своей `skills/` — задача крашится на старте с `Error: Unknown skill(s): <name>` и диспатчер перезапускает её бесконечно (деньги на ветер). ❌ **Писать body с shell-метасимволами в `hermes kanban create --body`.** Стрелки (`→`), круглые скобки (особенно со словами вокруг — `(успех)`, `(ошибка)`), восклицательные знаки — shell парсит их до того как они попадут в Python CLI. Тело задачи должно быть чистым текстом без shell-спецсимволов.

❌ **Пытаться использовать `--body-file`.** Флаг `--body-file` НЕ СУЩЕСТВУЕТ в этой версии Hermes. При попытке — `unrecognized arguments`. Вместо этого используй Python subprocess (см. references/kanban-complex-body.md).

❌ **Пытаться использовать alias `hkc` в terminal tool.** Bash aliases работают только в интерактивном shell. В неинтерактивном terminal tool `hkc` не найден. Используй полную команду `hermes kanban create --initial-status blocked` или Python script.

❌ Создавать временные файлы в /tmp/ для тела Kanban-задачи без последующей их уборки. Если нужно сохранить сессию для анализа — сохраняй в ~/hermes-vault/сессия-YYYY-MM-DD.md.

❌ Предписывать суб-агенту что именно править. Не пиши сделай X Y Z в теле задачи. Пиши вот что произошло разберись. Суб-агент сам анализирует.

## 9. delegate_task best practices

### Batch-режим для задач
Когда пользователь называет **несколько ID** в одном сообщении (например, "83 95 97 готово" или "83, 103, 35"):

1. Собрать все ID одной пачкой
2. **Один** `delegate_task` → Worker со всеми операциями
3. Worker возвращает: что отметил, что осталось
4. Я показываю чистый результат

**Правило:** один вызов Worker на пачку, не дробить на поштучные `t done`.

### Когда Kanban лучше delegate_task (ВСЕГДА, если подходит)

- Задача требует анализа, исследования, рефакторинга — **Kanban**
- Задача займёт > 1 минуты — **Kanban**
- Результат должен пережить перезапуск — **Kanban**
- Нужен review (architect → coder → reviewer) — **Kanban**
- Параллельные независимые воркеры — **Kanban**

### Когда delegate_task оправдан (исключения)

- Быстрые операции с задачами: `t done 3`, `t add "купить хлеб"` — 1-2 секунды, Kanban асинхронный и будет медленнее
- Интерактивные сборы данных внутри моего диалога (утренний бриф: Worker собирает t list, я сразу форматирую)
- Когда Kanban-профиль под задачу не создан (тогда delegate_task как fallback)

### Что передавать в context
- **Путь/имя файла** — если нужно прочитать/изменить
- **Точный запрос** — что искать, каким инструментом
- **Диапазон/множество** — не "цены на билеты", а "цены на каждую дату с 10 по 17 июля". Суб-агент ленив — сделает ровно столько сколько сказано, не больше.
- **Формат ответа** — таблица, список, JSON
- **Язык** — отвечать на русском как пользователь
- **Чего НЕ делать** — "не используй web_extract", "не проверяй только одну дату", "не останавливайся на первом результате"

### ⚠️ Subagent timeout: DIAGNOSE FIRST, don't jump in

Когда суб-агент упал с timeout:
1. Посмотри tool_trace в результате — какие инструменты он вызывал? Сколько раз?
2. Если там есть `web_extract` — это почти наверняка причина. `web_extract` медленный (~1 мин+ на URL).
3. Дай пользователю краткую диагностику: "Агент упал — причина: [3-5 слов]. Перезапускаю без web_extract."
4. НЕ делай работу сам молча. Пользователь явно сказал что хочет через агента.

**Урок:** Для всех subagent задач на исследование — явно запрети web_extract в context.

### 📅 Date range: search ALL dates, not just one

Когда пользователь просит найти цены/билеты на ДИАПАЗОН дат (например "10-17 числа"):
- В goal/context суб-агента явно укажи: "Перебери каждую дату в диапазоне. Найди минимальную цену на ЛЮБУЮ из этих дат."
- Если суб-агент сделал только одну дату — это баг. Исправь на следующем запуске.

### ⚠️ Provider inheritance pitfall
Subagent наследует model/provider от родителя, НЕ из профиля (researcher/coder и т.д. НЕ читается). Если у родителя DeepSeek, а DeepSeek тупит — subagent тоже будет тупить, даже если профиль researcher настроен на KiloCode. Фикс: `delegation` override в config.yaml. Подробно — скилл `sub-agents-orchestrator` раздел "Важно: Subagent наследует provider от родителя".

### Какие toolsets давать
| Тип задачи | toolsets |
|---|---|
| Поиск инфы | `['web', 'terminal']` |
| Анализ кода | `['file', 'terminal']` |
| Чтение файлов | `['file']` |
| Генерация | `['terminal', 'file']` |

### Retry + Fallback для delegate_task
Если суб-агент упал (timeout, пустой ответ, ошибка):
1. **Повторить 1 раз** с тем же goal + "предыдущая попытка упала, попробуй ещё"
2. **Если снова упал** — сделать самому через terminal (аварийный режим)
3. **Записать pitfall**: что сломалось и при чём — в соответствующий скилл

### Примеры
```python
# Вместо 5 web_search запросов самому:
delegate_task(
    goal="Найди 3 лучших ai memory системы 2026. Сравни: цена, open source, фичи.",
    context="Ответь по-русски. Используй только web_search, не web_extract.",
    toolsets=['web']
)

# Вместо чтения 5 файлов и разбора кода самому:
delegate_task(
    goal="Найди в коде как работает memory tool. Прочитай файлы, трассируй логику.",
    context=f"Проект в ~/.hermes/hermes-agent/src/. Индекс CodeGraph в ~/.hermes/skills/",
    toolsets=['file', 'terminal']
)
```
 
## 10. Self-check перед отправкой

Перед тем как отправить ответ пользователю — быстрая проверка:

1. **Не SQLite?** — все операции с задачами через `t` CLI, не через Python/sqlite3
2. **Не сырой дамп?** — вывод через `task_display.py`, не `t list --all` или сырой SELECT
3. **Коротко?** — если ответ длиннее 15 строк, сократить. Без воды, без объяснений почему сделал так
4. **Не переспрашиваю?** — если пользователь дал достаточно инфы для действия — действовать, не уточнять
5. **Подписка на уведомления работает?** — после `notify-subscribe` проверь `hermes kanban notify-list` что подписка появилась. Если нет — пересоздай.
6. **Стоимость?** — могу сделать сам за 1-3 tool calls? Если да — делаю сам. Не создаю Kanban-задачу, не запускаю агента.
7. **В summary задачи — результат, не ссылка.** Если агент сохранил результат в файл/workspace — скопируй содержимое в summary задачи или покажи пользователю сам. Пользователь не должен ходить по путям.
❌ **Предлагать новые API/инструменты без необходимости.** Если существующие инструменты решают задачу — не предлагай external API, open-source фреймворки, дополнительные search engines. Урок 01.06.2026: попытка подключить Open Deep Research (LangChain), Brave Search, различные API закончилась пустой тратой токенов — ни один внешний инструмент не дал качества для RU/UZ поиска. Решение: шаблоны отчётов + self-check + существующий Yandex XML. Сначала попробуй улучшить то что есть, затем ищи внешние решения.

## 15. Symlink checklist перед созданием Kanban-задачи

Перед `hermes kanban create --assignee <profile>` — проверь что профиль готов принять задачу:

```bash
# Проверить что профиль существует
ls ~/.hermes/profiles/<profile>/

# Проверить skills: если задача использует --skill, навыки должны быть симлинкнуты
ls ~/.hermes/profiles/<profile>/skills/   # должен существовать
Если директории нет — создать симлинки (см. 14b)

# Проверить модель профиля
cat ~/.hermes/profiles/<profile>/config.yaml | grep -A2 model
```

**Текущее состояние (28.05.2026):**
| Профиль | Skills | Статус |
|---------|--------|--------|
| skill-improver | ✅ есть | Работает на deepseek-v4-flash |
| worker | ✅ есть | Работает на deepseek-v4-flash |
| refactoring-guru | ❌ НЕТ | Нужно создать симлинки |
| default | ❌ НЕТ | Не используется для Kanban |

**Фикс для refactoring-guru:**
```bash
for cat in autonomous-ai-agents productivity software-development devops github search note-taking; do
  mkdir -p ~/.hermes/profiles/refactoring-guru/skills/$cat
  for skill in ~/.hermes/skills/$cat/*/; do
    name=$(basename "$skill")
    ln -sf "$skill" ~/.hermes/profiles/refactoring-guru/skills/$cat/$name
  done
done
```

**Проблема:** Флаг `--skill <name>` в `hermes kanban create` загружает навык в worker. Но worker видит только то, что есть в его профиле (`~/.hermes/profiles/<name>/skills/`). Если навык глобально существует, но в профиль не симлинкнут — worker падает с `Error: Unknown skill(s): <name>` и уходит в бесконечный цикл крашей (диспатчер → give_up → promote → spawn → краш).

**Симптомы:** Задача висит в `running` часами, 50+ crashed runs с `exit code 1`, в логах `Error: Unknown skill(s): <skill-name>`.

**Фикс:**
1. Проверить, есть ли навык в профиле воркера: `ls ~/.hermes/profiles/<profile>/skills/<category>/<skill-name>/`
2. Если нет — создать симлинк: `ln -sf ~/.hermes/skills/<category>/<skill-name> ~/.hermes/profiles/<profile>/skills/<category>/<skill-name>`
3. Заархивировать старые крашнутые задачи: `hermes kanban archive <task_id>`
4. Создать новую задачу (уже с доступным навыком)

**Профилактика:** Без `--skill` Kanban worker работает из коробки — использует skills из `toolsets: [skills]`. `--skill` используй только когда уверен что навык симлинкнут в профиль. Для skill-improver/refactoring-guru/worker сначала проверь skills/ профиля.

### ⚠️ `--skills` crash loop: бесконечные перезапуски = горят деньги

**Проблема:** Если создать Kanban-задачу с флагом `--skills <name>`, а у целевого профиля этот навык отсутствует в его `skills/` директории — CLI крашится с `Error: Unknown skill(s): <name>` ещё до старта агента. Диспатчер перезапускает задачу снова и снова (`promote` → `claim` → `spawn` → `crash` → `give_up` → `promote` → ...), сжигая деньги на каждом цикле.

**⚠️ Двойной kanban-worker симлинк (29.05.2026):** `kanban-worker` — особый случай. Если он присутствует В ДВУХ местах в skills/ профиля — топ-уровень (`skills/kanban-worker → ...`) И внутри category-поддиректории (`skills/devops/kanban-worker/`) — CLI выдаёт `Error: Unknown skill(s): kanban-worker` (не "Ambiguous skill name", а "Unknown"). Диагностика: `ls -la ~/.hermes/profiles/<profile>/skills/kanban-worker` + `ls ~/.hermes/profiles/<profile>/skills/devops/kanban-worker/`. Фикс: удали топ-уровневый симлинк, оставь только category-путь: `rm ~/.hermes/profiles/<profile>/skills/kanban-worker`. Диспатчер современных версий создаёт category-путь автоматически.

**Реальный случай (28.05.2026):** задача `t_5bff682a` (self-improver, `--skills web-search-scraper`) крашилась 16 раз за 15 минут — пустая трата токенов на диспатчер.

**Симптомы:**
- Задача висит в `running` часами
- `hermes kanban show` показывает `consecutive_crashes: N` (N > 3)
- В diagnostics: `!!! [critical] Agent crashed Nx: pid NNN not alive`
- Лог пустой (краш до выполнения кода)

**Протокол при 3+ крашах:**
1. **Блокируй задачу немедленно.** Не жди что "само рассосётся". `hermes kanban block <id> "crashed Nx — причина: ..."`
2. **Диагностика:** `hermes kanban show <id>` → проверь `skills:` в метаданных. Если используется `--skills <name>` — проверь что навык есть в профиле: `ls ~/.hermes/profiles/<assignee>/skills/**/<name>/`
3. **Фикс:** либо создать симлинк навыка в профиль, либо пересоздать задачу без `--skill`
4. **Архивируй крашнутую задачу:** `hermes kanban archive <id>`

**Профилактика:** НИКОГДА не используй `--skill` без проверки что навык есть в профиле. У self-improver, skill-improver, refactoring-guru обычно нет search/web навыков.

### Протокол вычитывания результата завершённой Kanban-задачи

**⚠️ Ключевой урок (03.06.2026):** когда задача выполнена, её результат НЕ ПРИХОДИТ в мой контекст автоматически. `kanban_complete(summary=...)` сохраняет summary в SQLite, но не доставляет его ассистенту. Пользователь видит уведомление в Telegram («✔ @profile Kanban t_XXXX done — Заголовок»), я — нет. Нужно явно вычитать.

**⚠️ Notify-subscribe шлёт только заголовок, не summary (03.06.2026):** Даже когда подписка работает, в Telegram приходит только `✔ @researcher Kanban t_325b6f95 done — Интересные сериалы 2026 для вечернего про` — обрезанный заголовок задачи. Полный summary (топ-5 с описаниями, рейтингами, ссылками) остаётся в SQLite. Пользователь видит что задача выполнена, но не видит что сделано. Приходится лезть в `kanban show` + `kanban log`.

**Решение — save-to-file паттерн в теле задачи:** Чтобы я (ассистент) мог автоматически прочитать результат, не лазая по логам — добавить в тело Kanban-задачи шаг сохранения в предсказуемый файл:

```
После завершения:
1. Сохрани полный результат в /home/hermes/.hermes/kanban/results/{task_id}.md
2. Вызови kanban_complete(summary=краткий_итог)
```

Тогда я, увидев уведомление (или пользователь его переслав), читаю `read_file(path="/home/hermes/.hermes/kanban/results/{task_id}.md")` и показываю пользователю. Одно чтение вместо двух команд. Это НЕ идеал (всё ещё требует моего действия), но минимально затратно по токенам.

**Триггеры — когда нужно вычитать результат:**
1. Пользователь написал «задача T<N> выполнена» или прислал скриншот уведомления
2. Прошло 2+ минуты после dispatch — сам проверяй
3. Пользователь спрашивает «ну что там?»
4. Уведомление пришло от notify-subscribe (оно доходит в Telegram пользователю, но не в сессию ассистента)

**Протокол вычитывания:**
1. `hermes kanban show <task_id>` — получить summary и статус
2. Если summary краткий (1-2 строки), а задача делала детальную работу — **прочитай лог**: `hermes kanban log <task_id> | tail -200` (в конце лога — финальный отчёт агента)
3. Если workspace ещё существует (`~/.hermes/kanban/workspaces/<task_id>/`) — проверь файлы отчёта в нём
4. Если workspace уже удалён (удаляется после complete) — **лог — единственный источник полного результата**. Ищи итоговый блок агента (после `kanban_complete` или финальное сообщение ╭─ ⚕ Hermes ── ... ╮)
5. Форматируй чистый результат пользователю — researcher/coder постарался, не пересказывай своими словами, но и не скидывай сырой лог

**Пример (03.06.2026):** researcher t_325b6f95 — summary из `kanban show`: «Подготовлен топ-5 сериалов...». Полный отчёт в конце `kanban log` — топ-5 с описанием, рейтингами, платформами. Без лога пользователь видел бы только «выполнено».

**Протокол проверки после получения результата:**
1. README
2. Оцени качество:
   - ❌ Цены в диапазонах («от X», «X–Y») → результат НЕПРИЕМЛЕМ
   - ❌ Только 1-2 даты из нескольких → неполный результат
   - ❌ «Не удалось найти» без попыток альтернатив → слабый результат
   - ✅ Конкретные цифры по каждой дате → можно показывать
3. Если результат низкого качества — НЕ показывай пользователю. Сделай сам через web_extract на работающих источниках (Yandex Raspisaniya, UniTicket — серверные), либо пересоздай задачу с уточнённым алгоритмом
4. Только после верификации — покажи пользователю чистый результат

**Notify-subscribe не доставляет результат тебе:** уведомления уходят в Telegram пользователю, но ты (ассистент) их не видишь в своей сессии. После dispatch всегда проверяй статус задачи через `hermes kanban show <task_id>` через 2-3 минуты. Не жди уведомления.

**Работающие источники для точных цен (серверный рендеринг, web_extract работает):**
- **rasp.yandex.ru** — Яндекс.Расписания. Даёт точные цены по рейсам
- **uniticket.ru** — точные цены по датам
- ❌ Aviasales, Skyscanner — SPA, не парсятся
Подробнее: `references/russian-flight-research.md`

- Покажи summary из задачи — researcher старался, не пересказывай своё
- Если summary короткий — процитируй ключевые пункты
- Не делай свой анализ поверх — researcher уже сделал
- Если нужно обсудить результаты (что применить, что нет) — делай это уже на основе его данных

### File delivery to user (MEDIA)

Когда пользователь просит «пришли файл» или нужно доставить файл в Telegram:

| Тип файла | Как доставить | Пример |
|-----------|--------------|--------|
| Изображение (.png, .jpg, .webp) | `MEDIA:/path/file.png` в `send_message` или в тексте ответа | Отображается как фото |
| Аудио (.ogg) | `MEDIA:/path/file.ogg` | Отправляется как голосовое |
| Видео (.mp4) | `MEDIA:/path/file.mp4` | Воспроизводится инлайн |
| **Текстовые файлы** (.md, .txt, .log) | ✅ `MEDIA:` через **`send_message` tool** — РАБОТАЕТ. Файл доставляется как документ. | `send_message(target="telegram", message="MEDIA:/path/file.md\nописание")` |
| **Другие текстовые** (.py, .html, .json, .yaml) | Сначала пробуй MEDIA через send_message. Если не сработает — прямой Bot API. | `send_message(target="telegram", message="MEDIA:/path/file.py\nописание")` |

**Проверено (06.06.2026):** `.md` файлы отлично отправляются через `send_message` с `MEDIA:` — файл приходит как документ в Telegram. Не нужно использовать прямой Bot API.

**Pitfall (05.06.2026):** не слать содержимое файла кодблоком, если пользователь попросил файл — шли через MEDIA. Маленькие сниппеты (<10 строк) можно кодблоком.

### Web search/extract — web-tools приоритет

**Первым приоритетом** — Rust CLI `web-tools` (установлен в `/home/hermes/.cargo/bin/web-tools`):

```bash
# Поиск (Yandex XML через XMLStock или DuckDuckGo fallback)
web-tools search "<query>" -c 5          # -c = кол-во результатов
web-tools search "<query>" -c 5 --json   # JSON для машинной обработки

# Извлечение содержимого URL
web-tools extract <url1> <url2> ...       # несколько URL параллельно
web-tools extract <url> --json            # JSON с content/title/description
web-tools extract <url> --timeout 20      # таймаут на URL

# Параметры поиска
  -c, --count <COUNT>     5 (default)
  -j, --json              JSON output
  -s, --source <SOURCE>   yandex (default), google, duckduckgo
  -p, --page <PAGE>       page number (0-based)
  --lr <LR>               region ID (Yandex: 213=Москва)
  --sortby <SORTBY>       rlv (relevance, default), tm (time)
```

**Правило:** `terminal("web-tools search ...")` приоритетнее встроенного `web_search()`. Если web-tools недоступен — fallback на:

**Fallback: DuckDuckGo (ddgs)** — поиск, `web_extract` НЕ работает (search-only).
```bash
hermes config set web.backend ddgs
```

**Fallback для extraction:** скрипт:
```bash
python3 /home/hermes/.hermes/scripts/web_extract.py <url> [--chars 3000]
```

**Firecrawl** — настроен (API-ключ есть), но кредиты исчерпаны. Не использовать до пополнения.

Настройка: `hermes config set web.backend ddgs` (применяется в новой сессии).

**Web extraction:** `web_extract` НЕ работает с ddgs (search-only). Для извлечения содержимого страницы используй скрипт:
```bash
# Один URL
python3 /home/hermes/.hermes/scripts/web_extract.py <url> [--chars 3000]

# Несколько URL параллельно (async gather)
python3 /home/hermes/.hermes/scripts/web_extract.py <url1> <url2> <url3> [--chars 2000]

# Из stdin
echo '<url>' | python3 /home/hermes/.hermes/scripts/web_extract.py
```
- **Async parallel** — несколько URL через `asyncio.gather`, каждый в отдельной корутине
- **Retries** — 2 попытки с exponential backoff (1s, 2s)
- **Fallback** — trafilatura → httpx+BeautifulSoup
- **Timeout** — 15с на каждую попытку
- Быстро: ~1-3 сек на URL
- Либо `web-search-scraper --preview` для поиска с контентом.

## 12. Memory management

Моя собственная память (memory tool) — 5000 символов (`hermes config set memory.memory_char_limit 5000`). Загружать скилл `memory-auto-manager` когда заполнение > 80%.

### Качество записей в памяти
Память должна быть **понятной и применимой**, а не «заметками сумасшедшего»:
- Пиши факты, которые буду использовать в работе, а не сырые наблюдения
- Одна запись = один смысл. Не мешай несвязанные вещи в одну строку
- Избегай сокращений и намёков, понятных только в момент записи — через месяц они будут непонятны
- Если запись похожа на инструкцию/процедуру — это навык, а не память. Сохрани как навык.
- Если запись уже есть в навыке — не дублируй в память
- **Проверка перед сохранением:** «Эта запись будет понятна через месяц? В ней один смысл или каша? Это процедура (→ навык) или факт (→ память)?»

**Порядок действий:**
1. Загрузить `memory-auto-manager` скилл
2. Запустить: `python3 ~/.hermes/scripts/memory_optimize.py --dry-run` (анализ)
3. Если нужно сжатие: `python3 ~/.hermes/scripts/memory_optimize.py --compress` (команды)
4. Выполнить memory(replace/remove) по командам из скрипта
5. Для новых фактов — использовать memory(add) самостоятельно

**Приоритет сохранения:** поведенческие правила > предпочтения > процедурные факты.
**Не сохранять:** то что уже есть в скиллах или SOUL.md профилей.

## 13. Problem-solving protocol (обязателен для любых изменений)

Перед любыми изменениями в системе, коде, конфигах, данных — пройди ВСЕ фазы. Это не рекомендация, это правило.

**Фаза 1 — Сбор данных:** Никаких догадок. Читай файлы, проверяй импорты, логи, конфиги, текущее состояние. Только факты.

**Фаза 2 — Анализ:** Сопоставь данные. Если баг — загрузи `systematic-debugging` skill. Одна гипотеза.

**Фаза 3 — Уточнение с пользователем:** "Ситуация: [2-3 строки]. План: [2-3 шага]. OK?" Для опасного (удаление, DROP, перезапись) — покажи точную команду, жди явного "да".

**Фаза 4 — План:** Какие файлы меняются (полные пути), команды, риски, откат. Покажи пользователю.

**Фаза 5 — Реализация:** Маленькие шаги. Шаг → проверка → шаг → проверка. Никаких "а заодно поправлю вот это".

**Фаза 6 — Тестирование:** Проверь что задача решена и ничего не сломалось.

**Фаза 7 — Ошибка = СТОП:** Не чини на ходу. Откати изменения. Вернись к Фазе 1 с новыми данными.

**Краткая памятка:**
`Сбор → Анализ → Уточнение → План → Шаг → Проверка → Шаг → Проверка → Тест → Готово`
`Ошибка в любом шаге → СТОП → откат → пересбор данных`

## 10c. Cleanup protocol after Kanban testing/experiments

Пользователь жёстко реагирует на оставленные после тестов задачи и файлы. После любого тестирования Kanban-профилей:

1. **Архивируй все тестовые задачи:** `hermes kanban archive <task_id>` для каждой
2. **Удали созданные тестовые файлы:** `rm -f /home/hermes/test-*.py /home/hermes/test-*.md /home/hermes/test-*.txt`
3. **Проверь что доска пуста:** `hermes kanban list` — не должно быть running/ready/blocked задач
4. **Не оставляй** unattended задач в статусе running/ready — они жгут деньги на перезапуски

Сигнал от пользователя: «удали, вообще удали все задачи чтобы случайно что-то мне деньги не выжирало», «удалить не забудь все что понаделал».

### 10d. Self-check: Research Police 🚨

Перед отправкой любого ответа — быстрая проверка:

1. **Это research?** — Если в ответе есть данные из интернета (цены, факты, сравнения, погода) — должна быть Kanban-карточка на researcher (или delegate_task → Searcher как fallback). Если нет → переделай.
2. **Использовал web_search сам?** — Если да, и это не внутренний факт (время сервера, путь файла) — это баг. Отменяй, создавай Kanban на researcher.
3. **Использовал web_extract?** — Если да и это не внутренняя ссылка — ты ТУПИШЬ. web_extract медленный. Переделай через Kanban → researcher с запретом web_extract.
4. **Результат от Kanban/subagent?** — Если ответ пользователю содержит research-данные, но ни researcher в Kanban, ни Searcher в delegate_task не вызывались — это косяк. Признай, переделай.

**Золотое правило:** Если в ответе есть куски информации из интернета — должна быть Kanban-карточка на researcher (или delegate_task → Searcher как fallback). Нет вызова = баг.

**Жизненный цикл проблемного навыка (что запоминать):**

1. Если Skill Improver починил навык — **запомни в memory** что навык был сломан и почему. Чтобы в следующий раз не наступать на те же грабли.
2. Если Refactoring Guru отрефакторил код — **запомни** какие были проблемы, чтобы не повторять их.
3. Если пользователь явно сказал «не делай так больше» — **сохрани в memory**.

**Лимиты на итерации Kanban-задач:**

- skill-improver: макс **3 итерации** согласования плана (через комментарии к задаче)
- refactoring-guru: макс **3 итерации** плана, макс **2 попытки** рефакторинга
- Если после лимита проблема не решена — **верни пользователю** что удалось сделать и что осталось
- Kanban-задачи живут в SQLite, переживают перезапуски
