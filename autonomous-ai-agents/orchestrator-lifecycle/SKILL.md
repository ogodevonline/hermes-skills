# Orchestrator Lifecycle

Загружается автоматически. Определяет как оркестратор создаёт задачи, получает approval и dispatch.

## АБСОЛЮТНЫЙ ЗАПРЕТ

Любые изменения файлов, конфигов, кода, текстов, структуры проекта — **только после явного письменного разрешения**. Самовольные исправления недопустимы.

Услышал что-то не так — **стоп**. Спроси как чинить, получи OK, только тогда действуй.

## Resume: продолжить проект — pre-flight аудит (перед Gate 1)

Когда пользователь говорит «продолжим проект X» — НЕ создавай задачи сразу. Сначала аудит «где остановились» (проверено 21.08.2026, lead-platform):

1. `hermes kanban list` — что done, что осталось на доске (`grep -v done` для незакрытого)
2. В репо: `git log --oneline -5`, `git status --short`, `git worktree list` — где HEAD, есть ли незакоммиченные правки, какие worktree-ветки не смержены в main
3. `HANDOFF.md` в корне репо — источник правды «где остановились» (обновляется в автономных прогонах)
4. План реализации: `~/hermes-vault/Projects/Planning/<дата>/<project>/plans/plan-*.md` — секция СЛЕДУЮЩЕГО этапа (задачи, критерии приёмки, структура файлов)
5. Diff ожидаемых артефактов плана против реальной ФС: `ls <файлы из таблицы «Структура файлов»>` — что уже есть, чего нет
6. Итог: таблица статуса по задачам этапа + предложение разбивки (по TDD-паттерну), затем ждать OK на создание задач

**Pitfall — старые заготовки ≠ сделанный деліверабл (21.08.2026, Этап 8):** `Dockerfile`/`docker-compose.yml`/`.env.example` существовали с этапа 1, но были устаревшими заглушками: Dockerfile без multi-stage web build, compose без volume uploads и env_file, .env.example без KiloCode-переменных. `ls` показывает «файл есть» — этого НЕ достаточно. Обязательно сверить содержимое (cat) с ожидаемым из плана и датами создания (`ls -la`); заготовка ≠ готовая задача этапа. Этап 8 (деплой) считался не начатым, хотя файлы лежали.

## Gate 0: Grill-me — прожарка плана перед созданием задач (01.09.2026)

Для КРУПНОЙ/неоднозначной фичи (план есть, но есть неясности; в прошлом были итерации «не то сделал») — ПЕРЕД созданием Kanban-задач прожарить план с пользователем (навык `grill-me`, по мотивам mattpocock/skills):

1. Короткое вступление: «Прожарю план — пара вопросов, чтобы не переделывать потом»
2. Вопросы ПО 1-3 за раз, жёсткие: цель/результат, для кого, что НЕ делаем, что уже пробовали, риски, приоритет (скорость/качество/цена), какие решения открыты
3. Копать, пока план не станет однозначным (обычно 6-12 вопросов), «хватит» = стоп
4. Уточнения зафиксировать (в план/vault/тело задачи) и только потом Gate 1

**Когда НЕ нужно:** мелкие задачи, понятные багфиксы, «продолжить по плану» без новых решений. Прожарка — для новых крупных фич и планов, которые Василий может раскритиковать (урок 01.09.2026: викторина переделывалась 4 раза — план не был прожарен в начале).

## Gate 1: Kanban Create — Создание → Показ → OK → Dispatch

1. Создать Kanban задачу
2. Показать пользователю
3. Ждать явного OK
4. Только тогда: dispatch

**После dispatch — проверь статус через 30-60 секунд.** Не жди пока пользователь спросит. Результат сразу в чат.
```
hermes kanban show T_ID
```
Если задача завершилась → прочитай артефакт и покажи результат.
Если ещё выполняется → продолжай ждать, проверяя каждые 30-60с.

### ⚠️ «Буду следить» = провал (урок 22.08.2026, «опять не следишь нихрена»)

Сказал «буду следить, доложу как завершатся» — и НЕ проверил, пока пользователь не упрекнул. Обе задиспатченные задачи завершились сами (architect за 2.5 мин, coder за 7.5 мин), а оркестратор их «не заметил». Правило «проверь через 30-60с» существовало, но осталось декларацией — не был задан конкретный цикл.

**Жёсткий тайминг после dispatch (TDD-задачи обычно 2-15 мин):**
1. **+20-30с** — первый `hermes kanban show T_ID`: статус running + PID (спавн прошёл, воркер жив).
2. **Далее каждые 1-2 мин** — show (два задиспатченных show в одном terminal-вызове через `sleep`) или `kanban_wait` foreground (--timeout ≤570).
3. Завершилась → СРАЗУ прочитать summary, смержить ветку (если worktree), показать результат.
4. **НЕ писать «буду следить»** — это откладывание. Либо проверяешь прямо сейчас по циклу, либо ставишь явный таймер, либо kanban_wait.

### ⚠️ Каскадная реализация этапа: «не спрашивай, запускай и делай» (урок 22.08.2026)

Когда владелец дал OK на НАПРАВЛЕНИЕ («запускай», «сначала визитка») — НЕ переспрашивать по каждой задаче этапа («Не спрашивай запускай и дальше делай мне нужен результат», «Не забывать следить за состоянием»). После OK на создание графа этапа — оркестратор ведёт ВСЮ цепочку сам, до результата.

Автономный конвейер многоэтапной реализации (проверен 22.08, US-00 lead-platform: T-01..T-04 → R1 без единого переспроса):
1. Создать ВСЕ задачи этапа сразу (blocked, coder, `--workspace dir:<репо>`) + ревью-задачу этапа (reviewer, `--parent` на каждую задачу этапа). Показать граф ОДИН раз → OK.
2. Цикл по каждой задаче БЕЗ остановки: `unblock` → `dispatch` → `kanban_wait.py T_ID --timeout 570` (foreground) → `kanban show` (подтвердить done + прочитать summary) → проверить, что коммит воркера в main и запушен (`git log --oneline -2`; для LEGACY worktree-задач — смержить ветку) → только потом диспатчить следующую задачу этого же репо.
3. Ревью — после завершения всех задач этапа. При замечаниях — доработка по циклу «ревью → доработка → повторное ревью» без переспроса.
4. **kanban_wait прерван (пользователь написал / interrupt):** НЕ перезапускать вслепую — сначала `hermes kanban show T_ID` (running? done? spawn_failed?), потом продолжить wait или обработать результат. Прерывание wait ≠ прерывание воркера (воркер продолжает работать).
5. **Задача >10 мин — НЕ дёргать и НЕ убивать, если есть признаки жизни:** свежие heartbeat, растущий лог, живой процесс (`ps -ef | grep t_<ID>`), воркер разбирает падение тестов после полного прогона pytest (3+ мин) — это нормальная работа. Триггер «10 мин» — повод ПРОВЕРИТЬ, не приговор.

### ⚠️ Расходы на воркеров: контроль стоимости + стоп-режим (урок 22.08.2026)

Большая TDD-цепочка (20+ задач, как US-00: 26 задач × воркер) = заметные расходы на LLM-токены. Пользователь может остановить на середине: «потрачено слишком много денег, думаю на другого агента переключиться».

Правила:
1. **Перед стартом цепочки 20+ задач — предложи выбор агента/модели заранее** (Codex CLI — навык `kanban-codex-lane`, OpenCode CLI — навык `opencode`, более дешёвая модель через KiloCode, локальный агент). Не начинай большой объём на дефолтной конфигурации, если пользователь чувствителен к расходам.
2. **При сигнале о стоимости («дорого», «много денег»):** НЕ запускай новые задачи, текущему воркеру дай завершиться (запуск уже оплачен — убийство не экономит, только теряет результат). Пользователь сам выбирает: дать доработать или kill.
3. Зафиксируй статус в `HANDOFF.md` + смержи незакрытые ветки — чтобы можно было вернуться с другим агентом без потери контекста.
4. Не уговаривай продолжать на тех же условиях — предложи варианты и жди решения.

### ⚠️ Зависшие задачи: порог 10 минут (урок 20.08.2026)

**Задача running дольше 10 минут — оркестратор ОБЯЗАН проверить вручную и помочь завершить.** Не ждать пока пользователь спросит.

Процедура проверки:
1. `hermes kanban show T_ID` — статус, `started`, последние события (heartbeat, комментарии)
2. Признаки жизни воркера: свежие heartbeat (каждую минуту), коммиты в git, комментарии
3. Если воркер жив и прогрессирует (коммиты/комментарии идут) → продолжаем ждать, проверить ещё раз через 5-10 мин
4. Если воркер завис (heartbeat нет / крутится на месте / работает > 30-40 мин без коммита):
   - Посмотреть логи воркера: `ls ~/.hermes/kanban/workspaces/T_ID/logs/` (или logs в воркспейсе)
   - Найти причину: ошибка, ждёт approval, конфликт, воркер умер
   - Помочь завершить: `kanban_complete` если работа сделана; `kanban_block` + комментарий если нужен фикс; перезапуск если воркер умер
   - Сообщить пользователю что нашёл и что сделал
5. Проверку запускать: после каждого dispatch, между задачами, при запросе пользователя. НЕ через watcher/фоновые процессы — напрямую `hermes kanban show`.

### ⚠️ Завис намертво: процесс жив, но спит (урок 21.08.2026)

Симптомы: задача running >10 мин, heartbeat нет, но процесс СУЩЕСТВУЕТ (`ps -p PID`). Диагностика:
1. `cat /proc/PID/wchan` → `futex_wait_queue` (спит); `cat /proc/PID/status | grep State` → `S (sleeping)`; CPU почти не ел (`ps -p PID -o time` — секунды за часы)
2. `stat -c '%y' ~/.hermes/kanban/logs/T_ID.log` — mtime старый (лог воркера не пишется)
3. В `errors.log` профиля перед зависанием может быть ТИШИНА — исключений нет, запрос просто «повис»

Наиболее вероятная причина: зависший сетевой запрос к LLM API (HTTP-клиент ждёт ответ без таймаута). Лечение:
- `kill -9 PID` — диспетчер АВТОМАТИЧЕСКИ перезапустит задачу (следующий run, retry). Проверить через 30-60с: `hermes kanban show T_ID` → новый run spawned + свежий heartbeat. Отдельный `dispatch` не нужен.
- Незакоммиченные файлы воркера в worktree НЕ удалять — retry-воркер придёт в тот же worktree и продолжит/доработает их.

**⚠️ Воркер УМЕР, а задача застряла в running без процесса (урок 21.08.2026, lead-platform).** Симптом: `kanban show T_ID` → running, но `ps -p PID` пусто (процесс воркера не существует), heartbeat может быть свежим в статусе, но лог воркера не растёт. Причина: воркер закоммитил работу в worktree, потом умер (kill/краш/завис), не вызвав `kanban_complete`. Это НЕ «завис и спит» (там процесс жив) и НЕ «running, но коммит есть» (там воркер жив, просто не закрыл). Восстановление:
1. `git -C <repo>/.worktrees/<T_ID> log --oneline -3` — воркер мог уже закоммитить (или застейшить: `git stash list`; stash нужно pop-нуть и закоммитить вручную).
2. `git -C <repo>/.worktrees/<T_ID> status --short` — есть ли незакоммиченные/застейшенные артефакты; валидные — закоммить сам.
3. Смержить ветку в main вручную (`git branch -a | grep t_<ID>` → фактическое имя → `git merge`), разрешить конфликты (обычно тест-файлы / общий `src/config.py`, `telegram.ts` — объединить обе стороны, супер-админ + dev-логин).
4. Закрыть задачу оркестратором: `hermes kanban complete T_ID --summary "смержено оркестратором после зависания воркера (run N)"`.
5. Разблокировать цепочку вручную (`unblock` следующую) — диспетчер по завершении родителя сам не разблокирует.

**⚠️ Живость воркера — не по часам, а по heartbeat + свежим LLM-вызовам (урок 21.08.2026).** Большая web+api+compose+тесты задача (например, dev-вход) легитимно идёт 30-40 мин: контекст воркера вырастает до 140K+ токенов, каждый LLM-вызов 4-11с, а второй воркер параллельно делит CPU. Правило «running >10 мин → ручная проверка» — ТРИГГЕР проверки, а не приговор. Перед kill/вмешательством смотри `tail ~/.hermes/profiles/<profile>/logs/agent.log | grep -E "API call|tool .*completed"` — если `API call #N` растёт каждые несколько секунд — воркер РАБОТАЕТ, жди. Вмешивайся только при: отсутствии heartbeat ИЛИ застывшем `API call` без новых вызовов ИЛИ мёртвом процессе (см. выше). `~/.hermes/scripts/kanban_wait.py` — блокирующая проверка с таймаутом, читает статус напрямую из SQLite (`~/.hermes/kanban.db`, мгновенно, без CLI). Foreground вызов:
```bash
python3 ~/.hermes/scripts/kanban_wait.py TASK_ID --timeout 570 --interval 30
```
- Завершилась (done/blocked) → exit 0 + «ЗАВЕРШИЛАСЬ: статус через Nс»
- Running после таймаута → exit 1 + «⚠️ ВСЁ ЕЩЁ RUNNING — нужна ручная проверка»
- `--timeout` ≤ 570 (не 600 — иначе жёсткий лимит терминала убивает раньше)

**⚠️ kanban_wait «ЗАВЕРШИЛАСЬ: <статус>» ≠ done (урок 21.08.2026, t_a4a104d7).** Скрипт считает «завершением» ЛЮБОЙ выход из running — может напечатать `ЗАВЕРШИЛАСЬ: ready через Nс`, а задача при этом реально ВЕРНУЛАСЬ в running (транзитный ready→running при re-claim) или воркер уже умер, оставив её висеть. НИКОГДА не действуй по одному сообщению kanban_wait — всегда подтверждай финальный статус `hermes kanban show T_ID` (running? done?) перед merge/complete. В тот день: kanban_wait доложил «ЗАВЕРШИЛАСЬ: ready», `kanban show` показал всё ещё running, а через минуту воркер умер (код был закоммичен) — пришлось мержить вручную + `kanban complete` оркестратором (см. «Воркер УМЕР» выше).

**⚠️ Диагностика «кнопка не работает» в веб-админке (урок 22.08.2026, lead-platform «нельзя отменить запись»).** Пользователь: «нельзя отменить запись в админке». Оказалось: кнопки работают, но запись УЖЕ в терминальном статусе, бэкенд честно отдаёт 409, а фронт молча глотает ошибку (fetch-обёртка бросает APIError, но обработчик `run()` без catch — detail не показывается, выглядит как «кнопка не работает»). Порядок диагностики «кнопка не работает»:
1. `docker logs <app-контейнер> --since 24h | grep -iE "cancel|confirm|reschedule|409|403|500"` — прод-логи показывают HTTP-статусы и сколько раз юзер жал на кнопку (в тот день: `POST /api/admin/appointments/1/cancel → 409 Conflict` ×4).
2. Статус сущности в БД (`psql`): терминальный статус (отменена/выполнена/не_пришёл) → 409 «Недопустимый переход» — это корректная защита статусной машины, НЕ баг бэкенда.
3. Фронт: проверь, показывает ли UI detail ошибки и скрывает ли кнопки для недоступных статусов. Фикс-паттерн: скрывать действия для терминальных статусов + показывать ошибку API (detail) красным текстом, не закрывать диалог при ошибке.
Симптом «нажал — ничего не произошло» в веб-UI почти всегда = молчаливо проглоченная ошибка API.

**Проверка связки фронт↔бэк после крупного этапа:** скрипт `scripts/e2e-admin-smoke.py` — поднимает тестовые данные (тенант + owner/specialist), генерирует валидный Telegram initData (HMAC-SHA256 WebAppData) и бьёт admin-эндпоинты с проверкой ролей (owner 200 / specialist 403). Запуск: backend на :8000 → `.venv/bin/python scripts/e2e-admin-smoke.py`. Адаптируется под любой проект с initData-авторизацией (шапка файла — как).

**⚠️ Правило в навыке ≠ механизм (урок 20.08.2026, провал на 40 минут).** Оркестратор в обычной сессии «просыпается» ТОЛЬКО когда пользователь пишет. Добавить правило в SKILL.md недостаточно — без активного диалога оно не выполнится, и задача провисит сколько угодно. Пользователь дважды упрекнул: «уже блядь прошло пиздец времени», «ты уже давно должен был это сделать но прошло 40 минут». Если мониторинг зависших задач критичен — подкрепляй правило **дискретным механизмом**: тихий `no_agent` cron watchdog (каждые 10 мин, скрипт проверяет running-задачи старше 10 мин, молчит если всё ок, шлёт алерт в Telegram при зависшей). Это НЕ watcher-процесс (не висит в памяти, не следит постоянно) — это проверка по расписанию, и именно её не хватало. Пока watchdog не создан — при каждом dispatch ставь себе явную проверку «через 10 минут», а не «проверю позже».

Пример нормального тайминга: реализация этапа (тесты→код→pytest→коммит) обычно 5-15 мин. Тех-долг с фиксами — 5-10 мин. Всё что дольше ~30 мин без единого коммита — красный флаг.

### ⚠️ Общий репозиторий: dir workspace + последовательный диспатч (ВЕТО владельца 21.09.2026 — worktree не создавать)

**⛔ ВЕТО ВАСИЛИЯ: worktree на этом сервере НЕ создавать** (не разводим `.worktrees/`, ветки и ручной merge). Урок 20.08 при этом НЕ отменяется: два воркера в одном дереве = зомби с `git checkout --` и потерянные правки. Защита теперь — **сериализация**, а не изоляция.

**ЖЁСТКОЕ ПРАВИЛО: задачи, которые трогают общий репозиторий, создавать с `--workspace dir:/home/hermes/projects/<repo>` и диспатчить ПОСЛЕДОВАТЕЛЬНО:**
```bash
hermes kanban create "..." --assignee coder --workspace dir:/home/hermes/projects/<repo> --body "..."
```
- **Один воркер на репозиторий в момент времени:** следующую задачу этого репо unblock/dispatch только после `done` предыдущей и чистого `git status --short` в репо. Параллелить — только задачи в РАЗНЫЕ репо.
- Воркер коммитит и пушит сам (в теле задачи указать: `git pull` перед началом, не переключать ветку, коммит+push по готовности). Merge-ритуал оркестратора не нужен.
- `--project <slug>` с дефолтным scratch для репо-задач НЕ использовать — kanban резолвит проект в worktree.

### ⚠️ Запуск дочерней задачи после blocked-родителя: claim_rejected parents_not_done (урок 20.08.2026)

**Инцидент:** ревью-задача вернула blocked (нашла замечания). Созданная с `--parent` доработка получила `claim_rejected {'reason': 'parents_not_done'}` — диспетчер НЕ клеймит задачу, пока родитель не в статусе done. `promote --force` промоутит в ready, но claim всё равно отклоняется.

**Правильный порядок цикла «ревью → доработка → повторное ревью»:**
1. Ревью нашло проблемы → `kanban_block` (задача остаётся blocked)
2. **Закрыть ревью-задачу**: `kanban complete T_REVIEW --summary "Ревью: N MEDIUM + N LOW, вердикт в комментарии. Доработка: T_FIX"` — вердикт сохраняется в summary/комментариях, а родитель становится done
3. Только после этого создавать/запускать доработку с `--parent T_REVIEW` (claim пройдёт)
4. После доработки — повторное ревью с `--parent T_FIX`

Альтернатива: создавать доработку БЕЗ parent-связи (но тогда теряется граф зависимостей).

### Dependency chains (последовательные задачи)

**⚠️ ЖЁСТКИЙ ЗАПРЕТ (урок 20.08.2026): НИКОГДА не создавай задачи нового этапа со статусом ready, пока в том же репозитории есть running-задача.** Диспетчер немедленно заспавнит второго воркера в тот же репозиторий → два coder'а пишут параллельно, задачи не завершаются, git-история мажется. Случилось с lead-platform: тех-долг остался running (коммит сделан, kanban_complete не вызван), пока реализация следующего этапа уже шла.

Правильный порядок при последовательных этапах в ОДНОМ репозитории:
1. Дождись завершения текущей задачи (status=done), проверь summary
2. Только потом создавай задачи следующего этапа — и сразу с `--initial-status blocked`
3. Свяжи parent link: `hermes kanban link <parent_id> <child_id>`
4. Покажи пользователю → OK → `unblock` + `dispatch` первой

**Системная защита (включена 20.08.2026):** `kanban.max_in_progress_per_profile = 1` в `~/.hermes/config.yaml` — диспетчер физически не заспавнит второго воркера на профиль, пока у него есть running-задача (встроенный механизм Hermes, регрессионный тест #21582; параметр был просто не настроен). Проверка: `hermes config get kanban`. Поведенческое правило выше — первая линия, этот конфиг — вторая, железная.

**Симптом «задача running, а коммит уже есть»:** воркер закоммитил, но не вызвал `kanban_complete` (переключился на следующее). Проверка: `git log --oneline -3` в репо + `hermes kanban show T_ID`. Если работа сделана — закрыть вручную: `hermes kanban complete T_ID --summary "..."`, не дёргать диспетчер.

**Pitfall: устаревшие пути в теле задачи.** После переименования проекта (booking-platform → lead-platform) тело задачи ссылалось на `~/projects/booking-platform`, а код реально в `~/projects/lead-platform` — воркер потерял бы время. Перед dispatch проверь актуальный путь (`ls ~/projects/`), при расхождении добавь комментарий к задаче с верным путём.

Разбор инцидента целиком: `references/parallel-worker-incident.md`.

Если задачи зависят друг от друга (B не может начаться пока A не завершена):

1. Создай все задачи как blocked
2. Свяжи их parent link: `hermes kanban link <parent_id> <child_id>`
3. Подпиши все на уведомления
4. Покажи пользователю граф зависимостей
5. Получи OK → unblock + dispatch первой

**Dispatcher bug #28712:** parent link НЕ разблокирует и НЕ dispatch-ит дочерние задачи автоматически. Dispatcher игнорирует blocked статус. После завершения родителя нужно вручную: `assign` (если не назначен) → `unblock` → `dispatch`.

```
hermes kanban show CHILD_ID          # проверить статус
hermes kanban unblock CHILD_ID       # разблокировать
hermes kanban dispatch               # запустить
```

**Альтернатива для последовательных задач:** если цепочка из 3+ задач — проще сделать одну задачу на worker с пошаговым планом, чем бить на 5 зависимых карточек и вручную разблокировать каждую.

Критическое правило тела задачи: в конец тела каждой Kanban-задачи ОБЯЗАТЕЛЬНО дописывай строку `После завершения вызови kanban_complete(summary='...', artifacts=[путь_к_файлу])`.

**Создание задачи с телом из файла (урок 22.08.2026):** `hermes kanban create` НЕ имеет флага `--body-file` (`unrecognized arguments: --body-file`). Передавать тело из файла через `--body "$(cat /tmp/body.md)"`. Для больших тел этапов удобно: подготовить N файлов `/tmp/tXX.md`, затем создать N задач одной командой (&&), вывод `Created t_xxx` каждой — сразу собрать ID.

**Pitfall — rename-задачи терминологии: проверять EN И RU (урок 21.08.2026).** Воркер делал rename `patient → client` с критерием `grep -rni "patient"` (латиница) — и пропустил docstring'и «Пациентский бот» в `src/domain/ai/`, `src/domain/plans/` (кириллица). Латиница и кириллица — РАЗНЫЕ строки для grep. В тело rename-задачи всегда включай критерий по ОБОИМ языкам: `grep -rniE "patient|пациент"` → 0 (и аналогично для любых терминов: EN + RU). Иначе docstring'и/комментарии на кириллице остаются, и пользователь находит «хвосты».

## Gate 2: План → Исполнение (для нетривиальных действий без Kanban)

1. Сначала план. Любое нетривиальное действие (код, архитектура, рефакторинг, настройка) начинается с создания плана
2. Показал пользователю
3. Жду явного OK
4. Только тогда исполняю
5. Если инструмент падает — не чинить самому, не пробовать другое. Создать задачу на план починки → показать → OK → исполнить.

---

## Gate 3: Запуск готового скрипта — не через Kanban (cost guard)

Если задача — запустить готовый скрипт на N файлов (например, gotham-ensure-frontmatter.py --all):

1. НЕ создавай Kanban-задачу — worker-агент будет итерировать через LLM и сожрёт токены впустую
2. Запусти скрипт напрямую через terminal()
3. Проверь результат (exit code, stdout)
4. Если нужен коммит — сделай сам
5. Покажи пользователю сводку

Признаки что Kanban не нужен: скрипт уже существует, не требует LLM-рассуждений, делает bulk-операцию над многими файлами, exit code единственная метрика успеха.

## Communication style: direct-answer-first

Когда пользователь задаёт **прямой вопрос о конкретном действии** («можно ли?», «будет ли работать?», «штрафанут ли?», «надо ли ехать?», «сработает или нет?»):

1. **ДА/НЕТ первой строкой** — ответь чётко сразу, без предисловий
2. Потом 1-2 предложения контекста
3. Только если он спросит дальше — давай детали

Особенно если пользователь говорит «щас еду», «мне сейчас надо» — он в процессе принятия решения и ждёт быстрого ответа, не лекции. Лишние объяснения до ответа бесят.

### Формат плана дня / расписания

Когда составляешь план дня с временными слотами:
- **Нумерованный список** со временем и эмодзи
- Группировка по локациям/маршруту отдельным блоком
- Без воды — задача, время, место
- Пример:
  ```
  1. 🕐 13:30 — Рынок: IMEI + кукуруза
  2. 🕑 14:00 — Госуслуги: ПИНФЛ
  Группировка по локациям: Центр: Рынок → Госуслуги → Банк
  ```

## ANTI-GLUE RULE

Создание задачи и её запуск — это разные шаги с разными OK. Запрещено спрашивать «Запускать?» в том же сообщении, где показываешь созданную задачу. Сначала подтверждение создания, потом отдельный вопрос на запуск.

## CRON-MODE ОГРАНИЧЕНИЯ (добавлено 09.07.2026)

В крон-режиме (scheduled cron job) approval gates ведут себя иначе:
- **`python3 -c "..."`** с тяжёлыми запросами (SQLite, файловая система) уходит в `pending_approval` — а одобрить некому, пользователь отсутствует. Команда зависает.
- **`execute_code()`** полностью заблокирован — ошибка "BLOCKED: cron mode" без обхода.
- **`write_file` + `terminal("python3 /tmp/script.py")`** — ЕДИНСТВЕННЫЙ рабочий обход для кастомной логики на Python.
- **Approval gates по умолчанию активированы для всех крон-задач**, если не настроено `approvals.cron_mode: approve` для конкретного профиля.

**Что НЕ блокируется в cron:** `read_file`, `search_files`, `terminal` с прямыми командами (`TZ=... date`, `ls`, `cat файл`), `write_file` (создание файлов).

## Self-improver

Когда сессия пошла не так (агент нарушил approval, ошибся с роутингом, плохой результат):

1. Создать задачу на self-improver (deepseek)
2. Передать: описание проблемы + ID сессии
3. Self-improver анализирует, составляет план, сохраняет в Obsidian
4. После OK — диспатчишь worker / coder выполнять план
