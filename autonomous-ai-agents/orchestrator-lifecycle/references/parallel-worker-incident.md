# Инцидент: параллельные воркеры в одном репозитории (20.08.2026)

## Симптом

В Kanban-пайплайне lead-platform (этапы 1-3, TDD) оркестратор создал задачи Этапа 3
(тесты → реализация → ревью) **со статусом ready**, пока тех-долг `t_37c38450` ещё был `running`.

Что произошло:
1. Диспетчер увидел ready-задачу и заспавнил **второго воркера coder** в тот же репозиторий `~/projects/lead-platform`
2. `ps aux | grep hermes` показал два живых coder-процесса (PID 1421518 старт 07:03, PID 1426775 старт 07:17)
3. `t_37c38450` остался `running` — коммит `cabf7ff` был сделан (07:20), но `kanban_complete` не вызван: воркер переключился дальше
4. Git-история осталась линейной только по удаче — воркеры не пересекались по файлам

Пользовательская реакция: «бля ну как бы это не хорошо пиздец как не хорошо», «We need to prevent such situations».

## Первопричина

Оркестратор нарушил порядок последовательных этапов: создал новые задачи до завершения текущей.
Диспетчер не знает про «один репозиторий» — он спавнит любую ready-задачу, ограничение на профиль не было настроено.

## Двухуровневый фикс

1. **Поведенческий (правило):** НИКОГДА не создавать задачи нового этапа со статусом ready, пока
   в том же репо есть running-задача. Новые задачи — с `--initial-status blocked`, разблокировать
   после завершения предыдущей. Записано в SKILL.md orchestrator-lifecycle → Dependency chains.
2. **Системный (железная защита):** `kanban.max_in_progress_per_profile = 1` в `~/.hermes/config.yaml`.
   Встроенный механизм Hermes (регрессионный тест #21582): диспетчер не заспавнит больше N воркеров
   на один профиль, даже если ready-задач много. Проверка: `hermes config get kanban`.
   Включено через `hermes config set kanban.max_in_progress_per_profile 1` (не ручной правкой config.yaml).

## Побочные уроки

- **Задача «running, а коммит есть»**: воркер может закоммитить и не завершить задачу.
  Проверка: `git log --oneline -3` в репо + `hermes kanban show T_ID`. Если работа сделана — закрыть вручную `hermes kanban complete`.
- **Устаревшие пути в теле задачи**: после переименования проекта (booking-platform → lead-platform)
  тело задачи ссылалось на несуществующий путь. Перед dispatch сверять `ls ~/projects/` и добавлять комментарий с верным путём.
- **Воркер сам фиксирует аномалию**: coder в summary тех-долга написал «в репо параллельно идёт реализация Этапа 3 — полный pytest падает на коллекции их тестов, не из-за моего коммита». Такие пометки — сигнал оркестратору, что что-то пошло не так.

## Диагностические команды

```bash
hermes kanban show T_ID                     # статус, started, события, summary
ps aux | grep -E "hermes.*-p (coder|reviewer)" | grep -v grep   # сколько воркеров профиля живо
git -C ~/projects/lead-platform log --oneline -5   # свежие коммиты
hermes config get kanban                    # max_in_progress_per_profile
```
