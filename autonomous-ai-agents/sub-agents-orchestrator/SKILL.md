# Sub-Agents Orchestrator

**⚠️ ВАЖНО: этот скилл — fallback для delegate_task. По умолчанию используй Kanban (см. orchestration-rules). delegate_task → Worker/Searcher/Education — только когда Kanban-профиль не подходит или задача сверхбыстрая.**

Схема делегирования: **я (Hermes) = оркестратор**, суб-агенты = исполнители.
## Правила

- Суб-агенты **не видят память** и **не могут говорить с пользователем**
- Всегда передавай **весь контекст** в goal: даты, имена, пути, формат вывода
- **ПОИСК (для всех суб-агентов):** Порядок — 1) `hms "запрос"` (FTS5 ~/.hermes) 2) `gms "запрос"` (FTS5 vault) 3) search_files/grep — только если пусто. hms индексирует и код hermes-agent тоже.
- **Goal должен быть хирургически точным:** суб-агент сделает ровно то что написано, ничего лишнего. Если goal "проверь цены" — проверит одно случайное число. Если "проверь цены на каждую дату с 10 по 17" — проверит все 8. Пиши явно: диапазоны, множества, запреты на stop после первого результата.
- Язык: если пользователь пишет по-русски — goal тоже на русском
- Результат суб-агента — **сырые данные**. Я форматирую и отдаю пользователю
- После делегирования — **проверяй результат**: суб-агент мог ошибиться

## Агент A: Worker (tasks, obsidian, hub, code-analysis, comparison)

**Роль:** сбор данных из локальных инструментов и анализ кода (быстро, без веба)

**Тулсет:** `terminal`, `file`
**Скиллы:** `personal-task-tracker`, `obsidian`, `hermes-hub`, `codegraph-cli`

**ПОИСК В КОДЕ/VALUES: использовать hms/gms, не search_files/grep.**
Порядок: 1) `hms "запрос"` — по ~/.hermes/ 2) `gms "запрос"` — по vault 3) search_files — только если пусто.

**Когда использовать:**
- Собрать задачи на сегодня (`t list`)
- Проверить привычки (`t habits`)
- Записать/прочитать заметку в Obsidian
- Собрать дашборд hermes-hub
- Запустить локальный скрипт (планирование, аналитика)

**Пример делегирования:**
```
delegate_task(
    goal="Собери все задачи на сегодня из SQLite-трекера. Команды: t list, t status. Верни список с приоритетами [H][M][L]. Ответь по-русски.",
    toolsets=["terminal", "file"]
)
```

**Питфолл:** у Worker нет `web` — не проси его искать в интернете.

## Агент B: Searcher (поиск в интернете)

**Роль:** поиск информации, сбор данных, анализ сайтов. **Единственный агент для ВСЕХ research-запросов.**

**Тулсет:** `web`, `terminal`, `file`
**Скиллы:** `web-search-scraper`, `crawl4ai`, `blogwatcher`

**Когда использовать (ВСЕГДА, без исключений):**
- Любой поиск информации (события, места, цены, новости, факты)
- Глубокий анализ сайта (OLX, Avito, маркетплейсы)
- Сбор данных с нескольких источников
- Даже 1 быстрый факт — через Searcher, не через web_search напрямую

### Типы задач и что использовать

| Тип | Инструмент | Когда |
|-----|-----------|-------|
| **Quick Fact** (погода, курс, время) | `web_search` (встроенная тулза) | 1 быстрый запрос, ответ в 1 строку |
| **Russian Search** (русскоязычный контент, СНГ) | `web-search-scraper` | Поиск по российским/узбекским сайтам. `cd search/web-search-scraper/scripts && uv run python search.py --query "..."` |
| **Deep Site** (анализ сайта, OLX, маркеты) | `crawl4ai` | Когда нужно пройти по страницам, собрать объявления, цены |
| **Feed Monitoring** | `blogwatcher` | RSS/Atom фиды (настроено в cron) |
| **Date Range** (диапазон дат) | `tasks=[]` с `web_search` | Проверить цены на каждую дату. Дробить на параллельные задачи |
| **Deep Research** (multi-source отчёт) | `open-deep-research` (LangChain) | Нужен структурированный отчёт с планом, параллельным поиском (до 5 агентов), верификацией и финальным синтезом. Для сложных тем с 5+ источниками. Международные запросы. **НЕ использовать** для RU/UZ-специфичных запросов (Tavily слаб на регионе). См. `references/odr-setup.md`. |

### ⚠️ ЖЁСТКИЕ ЗАПРЕТЫ (нарушение = агент тупит)

1. **НИКОГДА не использовать `web_extract`** — встроенная тулза медленная (1+ мин на URL). Если goal требует контента страницы — используй `web-search-scraper --preview` или `httpx + BeautifulSoup` для быстрого скрапа.
2. **НИКОГДА не пихать диапазон дат в один goal** — дробить через `tasks=[]`, макс 3 за раз.
3. **НИКОГДА не останавливаться на 1 результате** — если просили диапазон — перебрать КАЖДУЮ дату/страницу.
4. **Валюта = РУБЛИ** — цены в RUB. Пересчитывать сумы/доллары/евро по курсу.
5. **Ответ по-русски** — пользователь пишет по-русски, отвечай по-русски.

### Примеры делегирования

**Quick Fact (1 быстрый запрос):**
```
delegate_task(
    goal="Какая сейчас погода в Москве? Ответ: температура, облачно/ясно, ветер.",
    context="Используй web_search. НЕ используй web_extract.",
    toolsets=["web"]
)
```

**Russian Search (русскоязычный запрос с контентом):**
```
delegate_task(
    goal="Найди информацию о [тема]. Используй web-search-scraper: cd ~/.hermes/skills/search/web-search-scraper/scripts && uv run python search.py --query \"[запрос]\" --preview. Если нужно больше — добавь --lr 213 для Москвы. Верни 3-5 лучших результатов с кратким описанием каждого и ссылками.",
    context="Ответь по-русски. НЕ используй web_extract.",
    toolsets=["web", "terminal", "file"]
)
```

**Deep Site (анализ сайта через crawl4ai):**
```
delegate_task(
    goal="Проанализируй сайт [URL]. Используй crawl4ai: cd ~/.hermes/skills/search/crawl4ai/scripts && uv run python crawl.py --url \"[URL]\" --max-pages 3 --links-only. Верни список найденных объявлений: заголовок | цена | ссылка.",
    context="Ответь по-русски. Если httpx + BeautifulSoup справится быстрее — используй его вместо crawl4ai. НЕ используй web_extract.",
    toolsets=["web", "terminal", "file"]
)
```

**Date Range (диапазон дат — параллельно):**
```
# ❌ НЕПРАВИЛЬНО:
delegate_task(goal="Найди цены на билеты с 10 по 17 июля")

# ✅ ПРАВИЛЬНО — через tasks=[]:
dates = ["10", "11", "12", "13", "14", "15", "16", "17"]
tasks = []
for d in dates:
    tasks.append({
        "goal": f"Найди минимальную цену авиабилетов Победа Москва-Нукус на {d} июля 2026 на одного. Только web_search. НЕ web_extract. Ответ: ДАТА | ЦЕНА | ВРЕМЯ",
        "toolsets": ["web"]
    })
delegate_task(tasks=tasks)
# Первая волна: 3 запроса параллельно, потом следующие 3, и т.д.
```

**Сравнение N источников (параллельно):**
```
delegate_task(
    tasks=[
        {"goal": "Найди цену iPhone 16 Pro Max 256GB на [источник 1]. Только web_search. НЕ web_extract. Цена + ссылка.", "toolsets": ["web"]},
        {"goal": "Найди цену iPhone 16 Pro Max 256GB на [источник 2]. Только web_search. НЕ web_extract. Цена + ссылка.", "toolsets": ["web"]},
        {"goal": "Найди цену iPhone 16 Pro Max 256GB на [источник 3]. Только web_search. НЕ web_extract. Цена + ссылка.", "toolsets": ["web"]},
    ]
)
# Все 3 параллельно
```

### Goal должен быть хирургически точным И коротким

**Правило атомарности: goal ≤ 500 символов. Если не укладываешься — разбей на несколько задач через `tasks=[]`.**

Суб-агент сделает ровно то что написано, ничего лишнего. И чем больше goal — тем больше токенов жрётся на загрузку суб-агента.

```
❌ Плохо: один goal с 10 шагами
→ агент грузит 5K токенов на чтение, путается, делает половину

✅ Хорошо: 3 атомарных goal через tasks=[]
→ каждый ~300 символов, 3 агента параллельно, результат за 1/3 времени
```

Goal = КОНТЕКСТ (факты), не РЕШЕНИЕ (инструкции). Не пиши «сделай A, потом B, потом C» — напиши «вот что нужно получить, разберись как».

Суб-агент сделает ровно то что написано, ничего лишнего.

```
❌ Плохо: "найди цены на рейсы Победа Москва-Нукус на июль"
→ агент проверит одно случайное число, вернёт 1 цену

✅ Хорошо: "найди цены на рейсы Победа Москва-Нукус на КАЖДУЮ дату с 10 по 17 июля 2026.
   Сделай таблицу: дата | день недели | цена в рублях | время вылета/прилёта.
   Проверь ВСЕ 8 дат. Не останавливайся на одной."
```

**Правила точного goal:**
1. **Явно укажи диапазон/множество** — «с 10 по 17», «все модели», «3 лучших»
2. **Скажи что не stop на первом** — «проверь КАЖДУЮ дату», «не останавливайся»
3. **Укажи формат вывода** — таблица, список, JSON
4. **Запрети web_extract** — всегда добавляй «НЕ используй web_extract»
5. **Валюта** — всегда явно RUB, USD, UZS

### Питфоллы

1. **web_extract тормозит** — всегда запрещай в goal, используй `web-search-scraper --preview` для контента
2. **Суб-агент ленив** — если goal «проверь цены», проверит 1 цену. Пиши явно: «проверь ВСЕ даты/варианты»
3. **Валюта** — если источник в сумах, агент вернёт в сумах. Требуй рубли
4. **Provider** — subagent наследует provider родителя (сейчас deepseek/kiloCode). См. секцию "Важно" ниже.
5. **Суб-агенты упали → не откатывайся к web_extract.** Если все sub-agent'ы упали с таймаутом/HTTP 500, у агента (researcher/Searcher) должен быть fallback: использовать `web-search-scraper` напрямую с `--preview` (4 секунды, не минуты). Максимум 10 вызовов web_search суммарно. При лимите итераций — `kanban_block`, не продолжать циклиться. НЕЛЬЗЯ откатываться на сырой `web_extract` — это медленно (минута на URL) и жрёт итерации.
7. **skill-improver блокнулся без сохранения в Obsidian.** После анализа skill-improver должен сохранить план в Obsidian (`~/hermes-vault/Projects/Planning/YYYY-MM-DD/`), запушить в git, и только потом блокнуться на утверждение. Если он забыл — это баг workflow.
8. **Для анализа/оптимизации — профиль, а не навык.** Пользователь предпочитает отдельные профили (prompt-engineer) для reasoning-задач, не навыки. Тяжёлая аналитика = профиль, не SKILL.md.
9. **Read-only профили (prompt-engineer, reviewer) — явно запрещать запись файлов.** Правило #1 в SOUL.md: «❌ НИКОГДА не пиши файлы». Иначе агент может применить изменения без одобрения пользователя.

### Верификация данных и качество отчёта

После сбора данных — до финальной сдачи результата — исследовательский агент (researcher/Searcher) ОБЯЗАН:

**1. Точные данные — не диапазоны.** Цены, даты, рейсы — только конкретные значения с указанием источника. «7–12к» недопустимо. Если точных данных нет — напиши «не найдено» с объяснением.

**2. Верификация 2+ источников.** Любое числовое утверждение подтверди минимум двумя независимыми источниками. Одна ссылка = неподтверждённые данные. Если второй источник не найден — укажи «требуется верификация».

**3. Self-check чеклист (перед kanban_complete):**
- [ ] Все ли цены/даты конкретные (не диапазоны)?
- [ ] У каждой цифры есть ссылка на источник?
- [ ] На каждое числовое утверждение ≥2 источника?
- [ ] Что осталось непроверенным? Отмечено?
- [ ] Если «не найдено» — объяснено почему?

Если любой пункт НЕТ → `kanban_block` с указанием что доработать, не финализировать.

**4. Формат вывода:**\n- **Summary:** кратко, суть. Каждая цена → (источник).\n- **Details:** таблица/список со ссылками. Никаких «от 5000» — только «5 200 ₽ (источник)».\n- **Not verified:** отдельная секция для данных, которые не удалось проверить — «ТРЕБУЕТ ВЕРИФИКАЦИИ».\n\n**5. Сохранение в Obsidian:**\nПеред `kanban_complete` сохрани результат через `obsidian_save.py` (см. `kanban-worker` skill → `references/obsidian-save.md`).\n\n**6. Шаблоны отчётов:**\nДля финального форматирования загрузи навык `research-report-templates` и выбери шаблон под тип задачи: Price Report, Market Report, Fact Check, General Research.

## Агент C: Education (english-lesson, python-road, ielts-prep)

**Роль:** генерация учебных материалов (быстрые уроки через delegate_task)

**Тулсет:** `terminal`, `file`
**Скиллы:** `english-lesson`, `python-road`, `ielts-prep`

**Когда использовать (delegate_task):**
- Быстрый урок английского (1-2 минуты)
- Сгенерировать Python-упражнение для одного занятия
- Подготовить IELTS-задание

**Когда использовать Kanban → learning:**
- Долгая серия уроков (нужен прогресс-трекинг)
- Системное обучение с памятью уровня и тем
- Результат должен пережить перезапуск
- Нужно сохранять прогресс между занятиями

**Пример делегирования:**
```
delegate_task(
    goal="Создай урок английского на тему [тема] уровня A2. Сохрани в Obsidian: ~/hermes-vault/English/lessons/[название].md. Верни краткое описание урока. Ответь по-русски.",
    toolsets=["terminal", "file"]
```

## Агент D: Skill Improver (починка/улучшение навыков) — Kanban fallback

**⚠️ ОСНОВНОЙ ПУТЬ — Kanban → skill-improver (claude-sonnet-4.6). Этот раздел — fallback если Kanban недоступен или задача сверхбыстрая.**

**ВАЖНО: skill-improver = ТОЛЬКО ПЛАН. НИКОГДА НЕ ИСПОЛНЯЕТ.**
Задача skill-improver — high-level анализ, составление плана, и создание Kanban-задачи на worker/coder для исполнения. Исполняет всегда другой агент.

**Роль:** high-level анализ логики, составление плана исправлений навыков (SKILL.md)

**Тулсет:** `terminal`, `file`, `skills`
**Скиллы:** `hermes-agent-skill-authoring`, `requesting-code-review`

**Когда использовать (только Kanban, не delegate_task):**
- Пользователь сказал «навык X сломан» или «почини навык X»
- Пользователь матерится / недоволен / говорит «ты тупишь» — и проблема в навыке
- Я (Hermes) запутался в рассуждениях при работе с навыком
- Пользователь попросил улучшить/дополнить существующий навык
- Обновление навыка после обнаружения pitfall'ов

**ВАЖНО: НЕ ПРЕДПИСЫВАЙ РЕШЕНИЕ. Предоставь RAW-контекст.**
В теле задачи не пиши «сделай X, Y, Z». Пиши «вот что произошло, разберись»:
- Что произошло
- Сколько раз пользователь был недоволен
- Какие ошибки повторяются
- Текущее состояние системы (пути, профили, symlinks, SOUL.md)
- Если нужна сессия — сохрани транскрипт в ~/hermes-vault/сессия-YYYY-MM-DD.md и укажи прочитать

**Рабочий процесс (только план — ничего не исправляешь):**

### Фаза 1: Анализ + План
1. Прочитай проблемный навык: `skill_view(name=...)`
2. Определи что сломалось: устаревшие команды, неверные пути, пропущенные шаги, логические ошибки
3. Составь план исправлений: какие секции менять, что добавлять/удалять
4. **Сохрани план в Obsidian** — `~/hermes-vault/Projects/Planning/YYYY-MM-DD/<topic>-analysis.md`. Это обязательно: пользователь явно ждёт что результат анализа сохраняется в Obsidian и пушится на GitHub. После записи — `git add -A && git commit -m "..." && git push`.
5. **Верни РАЗВЁРНУТЫЙ план на утверждение** — перечисли что нашёл, что планируешь менять, какие файлы. НЕ ИСПРАВЛЯЙ. НЕ ПРИСТУПАЙ к исправлению.

### Фаза 2: Утверждение плана
— Жди ответа от родителя (пользователь смотрит план)
— Если пользователь (через родителя) предложил правки — учти их и **верни ОБНОВЛЁННЫЙ план**. Не начинай исправлять пока нет явного OK.
— Пользователь может отклонить план с доп. требованиями несколько раз — каждый раз возвращай обновлённый план.
— Максимум **3 итерации** согласования плана. После 3-й — принудительно переходи к Фазе 3 с лучшей версией

### Фаза 3: Передача исполнителю
1. После утверждения плана — **создай Kanban-задачу на worker или coder** для исполнения
2. В body задачи положи готовый план: какие файлы менять, какие изменения, команды
3. `hermes kanban create --assignee worker/coder "Исполнение: [описание]" --body "[план правок]"`
4. Worker/coder применяет изменения. Ты свою работу закончил.

**Лимиты:**
- Максимум **3 итерации** согласования плана (Фаза 2)
- Если пользователь молчит > 2 минут после плана — приступай по плану по умолчанию
- Если исправление сломалось (валидация не прошла) — попробуй 1 раз починить, затем верни ошибку

**Пример делегирования (только Kanban, не delegate_task):**
```
hermes kanban create --assignee skill-improver \\
  "Анализ: навык X — проблема" \\
  --body "Сессия: [контекст]. Прочитай навык, составь план. НЕ ИСПРАВЛЯЙ. Верни план. После approval создай задачу на worker для исполнения."
```

**⚠️ Питфоллы:**
- Subagent наследует provider родителя (deepseek/kiloCode). Для анализа сложных логических ошибок лучше обсуждение через родителя (я передаю вопросы пользователю)
- Не исправляй то что не просили — только заявленную проблему
- Если навык содержит ссылки на другие навыки — проверь что они тоже существуют и корректны
- Не удаляй секции без явного указания — только patch/edit
- После исправления — проверь `skill_view(name=...)` что навык загружается без ошибок

## Агент E: Refactoring Guru (рефакторинг, качество кода) — Kanban fallback

**⚠️ ОСНОВНОЙ ПУТЬ — Kanban → refactoring-guru (claude-sonnet-4.6). Этот раздел — fallback если Kanban недоступен или задача сверхбыстрая.**

**Роль:** чистка кода, рефакторинг, исправление логических ошибок

**Тулсет:** `terminal`, `file`
**Скиллы:** `codegraph-cli`, `requesting-code-review`, `test-driven-development`

**Когда использовать (DELEGATE СРАЗУ):**
- Я (Hermes) начал путаться в логике кода / выдавать противоречивые правки
- Пользователь сказал «код говно», «переделай», «это ужасно»
- Нужно отрефакторить существующий код без добавления новой функциональности
- Код содержит логические ошибки, дублирование, анти-паттерны
- Пользователь просит «причесать код» / «улучшить качество»

**Рабочий процесс (4 фазы, многошаговый):**

### Фаза 1: Разведка (Scope)
1. Определи область: какие файлы, какой функционал
2. Используй `codegraph context "описание области"` для понимания структуры и связей
3. Собери метрики: размер файлов, кол-во функций, дублирование
4. **Верни scope analysis** — что нашёл, что планируешь менять

### Фаза 2: План
1. Составь конкретный план: какие файлы меняются, какие изменения
2. Укажи риски: что может сломаться
3. Разбей на маленькие шаги (каждый шаг — 1-3 файла)
4. **Верни план на утверждение**

### Фаза 3: Утверждение
— Жди ответа от родителя (пользователь смотрит план)
— Учти правки, максимум **3 итерации**
— После утверждения — переходи к Фазе 4

### Фаза 4: Рефакторинг
1. Выполняй по шагам из плана
2. После каждого шага: `git diff` чтобы проверить что меняется
3. После каждого шага: запусти тесты (`pytest -q` или `git diff --stat`)
4. Если тесты упали — СТОП, откати последний шаг, исправь
5. После всех шагов — **итоговый diff** + результат тестов
6. Если тестов нет — хотя бы проверь что код импортируется/компилируется

**Лимиты:**
- Максимум **3 итерации** согласования плана
- Если после 2 попыток рефакторинг сломал код — откати все изменения (`git checkout -- .`) и верни ошибку
- Не трогай файлы вне области scope (scope creep)
- Не добавляй новую функциональность — только рефакторинг

**Пример делегирования:**
```
delegate_task(
    goal="[REFACTORING GURU] Отрефактори код в файлах X, Y. Составь план, жди одобрения, потом делай.",
    context=f"""
    ПРОБЛЕМА: [описание — дублирование, логические ошибки, качество]
    КОНТЕКСТ СЕССИИ: [краткое саммари]
    ФАЙЛЫ: [список файлов]
    
    СНАЧАЛА: проанализируй, составь план, покажи мне.
    ПОТОМ: жди approval.
    ТОЛЬКО ПОТОМ: рефакторинг.
    """,
    toolsets=["terminal", "file"]
)
```

**⚠️ Питфоллы:**
- Subagent наследует provider родителя — для анализа сложной логики в плане лучше делать через меня (родителя)
- Не меняй сигнатуры публичных API без явного разрешения
- После рефакторинга — проверь `git diff --stat` чтобы показать пользователю объём изменений
- Если в проекте нет гита — `git init` перед началом работы
- Если тестов нет — хотя бы запусти `python3 -c "import [модуль]"` для проверки импорта

## Kanban-профили (альтернатива delegate_task)

У Василия развёрнута система Kanban-профилей для долгоживущих и регулярных задач. В отличие от `delegate_task` (суб-агент на один запрос), Kanban-задачи живут в SQLite, переживают перезапуски и могут выполняться асинхронно.

| Kanban профиль | Роль | Модель | Когда использовать |
|----------------|------|-------|-------------------|
| **explorer** | Read-only codebase analyst | deepseek-v4-flash | Быстрый поиск по коду, grep, git log. Через delegate_task, НЕ Kanban. |
| **researcher** | Поиск в интернете | deepseek-v4-flash | Любой research. Асинхронно, переживает перезапуск. |
| **coder** | Написание кода | deepseek-v4-flash | Фичи, багфиксы, код в репо через `dir:` workspace (worktree под запретом с 21.09.2026). |
| **reviewer** | Ревью кода | deepseek-v4-flash | Формальная проверка с чеклистом. |
| **architect** | Проектирование | deepseek-v4-flash | Spec перед coder'ом. |
| **learning** | Обучение | deepseek-v4-flash | Асинхронные уроки с трекингом прогресса. |
| **orchestrator** | Декомпозиция | deepseek-v4-flash | Сложные задачи — разложить на подзадачи. |
| **worker** 🆕 | Рутина | deepseek-v4-flash | t list, t habits, Obsidian, скрипты. |
| **skill-improver** 🆕 | Анализ + ПЛАН (не исполняет) | **claude-sonnet-4.6** 🧠 | Анализ навыков/сессий → план → утверждение → создаёт Kanban-задачу worker/coder на исполнение |
| **refactoring-guru** 🆕 | Рефакторинг кода | **claude-sonnet-4.6** 🧠 | Чистка кода, логические ошибки, анти-паттерны. Сначала план→утверждение→реализация. |
| **prompt-engineer** 🆕 | Оптимизация промптов/SOUL.md/SKILL.md | deepseek-v4-flash | Анализ и сокращение токенов. Только выдача оптимизированного текста. НЕ пишет файлы. |

**Когда оставить delegate_task (только эти случаи):**
- Быстрые операции: `t done 3`, `t add "купить хлеб"` — 1-2 сек, Kanban будет медленнее
- Сбор данных внутри интерактивного диалога (утренний бриф: Worker собирает t list, я сразу форматирую)
- **Code analysis / explore** — быстрый поиск по коду через delegate_task → explorer
- Kanban-профиль под задачу не существует (fallback)
- Родитель делает анализ/план, суб-агент только реализует (паттерн A из provider-override-pattern.md)

**Когда переходить на Kanban (ПО УМОЛЧАНИЮ):**
- Любой research/поиск → researcher
- Код/фичи → coder, баги → debugger
- Архитектура → architect
- Ревью → reviewer
- Обучение → learning
- Недвижимость → realtor
- Мониторинг → scout
- Декомпозиция → orchestrator
- Написание навыков → skill-writer

## Batch Searcher (параллельный поиск по N запросам)

**Роль:** запускает несколько поисковых запросов ОДНОВРЕМЕННО, а не последовательно.

**Когда использовать:** когда нужно проверить цены на диапазон дат, собрать данные из N источников, сравнить N вариантов. Вместо одного goal "проверь 8 дат" (последовательно, 8×2с=16с) — запускай N суб-агентов параллельно через `tasks=[]`.

### Правила Batch Searcher:
1. **Дроби на отдельные задачи** — каждая задача = один запрос, одна дата, один источник
2. **Не больше 3 за раз** — лимит `max_concurrent_children: 3` (следующие начнутся когда первые закончат)
3. **В goal конкретная дата/страница** — не диапазон
4. **Запрети web_extract** — `Только web_search. НЕ используй web_extract.`
5. **Короткий формат ответа** — одна строка, чтобы не жрать контекст

### Пример: цены на диапазон дат

```python
dates = ["10", "11", "12", "13", "14", "15", "16", "17"]
tasks = []
for d in dates:
    tasks.append({
        "goal": f"Найди минимальную цену авиабилетов Победа Москва-Нукус на {d} июля 2026 на одного. Только web_search. НЕ web_extract. Ответ: ДАТА | ЦЕНА | ВРЕМЯ",
        "toolsets": ["web"]
    })
delegate_task(tasks=tasks)
# 8 запросов параллельно — готовы через ~2-3 секунды, не 16с
```

### Пример: сравнение N источников

```python
delegate_task(
    tasks=[
        {"goal": "Найди цену iPhone 16 Pro Max 256GB на OLX.uz. Цена + ссылка.", "toolsets": ["web"]},
        {"goal": "Найди цену iPhone 16 Pro Max 256GB на Uzum.market. Цена + ссылка.", "toolsets": ["web"]},
        {"goal": "Найди цену iPhone 16 Pro Max 256GB в Mediapark.uz. Цена + ссылка.", "toolsets": ["web"]},
    ]
)
# Все 3 параллельно
```

```bash
for p in refactoring-guru skill-improver worker; do
```

## Агент F: Explorer (read-only codebase analyst)

**Роль:** ответы на вопросы по коду — найти функцию, понять модуль, grep по файлам, git log/history. Read-only — ничего не меняет.

**Тулсет:** `file`, `terminal`, `session_search`
**max_turns:** 10 (быстрые задачи)

**ПОИСК В КОДЕ: использовать hms/gms, не search_files/grep.**
Порядок: 1) `hms "запрос"` — по ~/.hermes/ 2) `gms "запрос"` — по vault 3) search_files — только если пусто.

**Когда использовать (delegate_task, НЕ Kanban):**
- «Найди где используется функция X»
- «Покажи структуру модуля Y»
- «Найди файл по фрагменту имени»
- git blame/log/show по файлу
- Ответить на вопрос по архитектуре кода

**Когда НЕ использовать:**
- Нужно писать/менять код → Kanban → coder
- Нужно искать в интернете → Kanban → researcher
- Нужен глубокий анализ > 10 итераций → Kanban → coder

**Пример делегирования:**
```
delegate_task(
    goal="Найди все места где используется функция X в проекте Y.",
    context="Проект в /home/hermes/Y. Используй search_files, read_file, git log/grep.",
    toolsets=["file", "terminal"]
)
```

**Инструменты:**
- `hms "запрос"` — FTS5 поиск по ~/.hermes/ (skills, configs, scripts) — **в первую очередь**
- `gms "запрос"` — FTS5 поиск по vault (notes, journals, planning) — **во вторую**
- `search_files(target="files")` — glob-паттерны (*auth*, **/*.test.ts). **НЕ используй rg/fd в терминале — их нет на сервере.** search_files уже использует ripgrep внутри.
- `search_files(target="content")` — ripgrep (regex) по содержимому
- `read_file` — с offset/limit для точечного чтения
- `terminal` — только git: log, show, diff, blame. Для поиска — search_files.

**Web extraction (только для researcher, НЕ для explorer):**
Когда researcher-задаче нужно извлечь контент с веб-страницы, а `web_extract` не работает (ddgs search-only):
```bash
# Один URL
python3 /home/hermes/.hermes/scripts/web_extract.py <url> [--chars 3000]

# Несколько URL параллельно (async gather)
python3 /home/hermes/.hermes/scripts/web_extract.py <url1> <url2> <url3> [--chars 2000]

# Из stdin
echo '<url>' | python3 /home/hermes/.hermes/scripts/web_extract.py
```
Использует trafilatura + httpx+BeautifulSoup fallback. Async parallel с retries. Быстро (~1-3 сек на URL).

**⚠️ Питфоллы:**
- Нет `web` — не проси искать в интернете
- Нет write-тулз — не может редактировать файлы
- `rg`, `fd`, `fzf` не установлены на сервере — не используй в терминале
- Если задача требует > 10 итераций — переключись на Kanban → coder

## Ограничения

- Суб-агенты не могут делегировать дальше (`role="leaf"`, по умолчанию)
- Нет доступа к памяти пользователя — передавай всё в goal
- Суб-агенты не вызывают tools, которых нет в их toolsets
- Если суб-агент завис — будет timeout через 5 минут
- Результат суб-агента — **self-report**, проверяй его (файл создан? ссылка работает? цены на все даты?)
- **После возврата результата — проверь что покрытие полное.** Если просил 8 дат, а получил 1 цену — это косяк goal, а не суб-агента. Пиши точнее в следующий раз.

## Kilo Code Subagent Architecture (справка)

Сравнение архитектуры саб-агентов Kilo vs Hermes — см. `references/kilocode-subagent-architecture.md`.

**Ключевое отличие:** Kilo использует `task` tool для лёгкого spawn'а саб-агентов (inline, без Kanban). Это эквивалент нашего `delegate_task`. Kanban в Kilo нет — все агенты запускаются через `task`. Для нас это означает: для быстрых саб-агентов (исследовать код, найти функцию, быстрый поиск) — используй `delegate_task`, не Kanban. Kanban оставляй для долгих формальных задач (написать фичу, spec, ревью).

Также у Kilo есть встроенный **explore** саб-агент (read-only, только поиск по коду). У нас аналог — профиль **explorer** (read-only, file+terminal+session_search) с отдельным SOUL.md и конфигом. Запуск через delegate_task → explorer (быстрее Kanban для кодовых вопросов).

## ⚠️ Важно: Subagent наследует provider от родителя, НЕ из профиля

**Это частая причина «зависаний» исследовательских агентов.**

Логика `_build_child_agent()` в `delegate_tool.py`:
```python
effective_model = model or parent_agent.model
effective_provider = override_provider or getattr(parent_agent, "provider", None)
effective_base_url = override_base_url or parent_agent.base_url
effective_api_key = override_api_key or parent_api_key
```

**То есть:** subagent берёт model/provider/base_url из:
1. `delegation` секции текущего `config.yaml` (если указаны `model`/`provider`/`api_key`)
2. Если пусто — **наследует от родителя** (текущей сессии)

Профиль (researcher, coder и т.д.) **НЕ читается** — `_build_child_agent` не смотрит в `~/.hermes/profiles/researcher/config.yaml`.

### Симптомы
- Subagent настроен на быстрый провайдер через профиль (KiloCode) — но реально идёт через DeepSeek
- DeepSeek тупит (ReadTimeout 270с) → retry 3 раза → subagent timeout 600с → «молчаливая смерть»
- Пользователь ждёт 10 минут, получает error

### Фикс

Добавить override в `delegation` секцию `~/.hermes/config.yaml`:

```yaml
delegation:
  model: deepseek/deepseek-v4-flash
  provider: kilocode
  base_url: https://api.kilo.ai/api/gateway
  api_key: ${KILOCODE_API_KEY}
```

После этого все суб-агенты пойдут через KiloCode, независимо от провайдера родителя.

> **Практический патерн переключения провайдера** — см. `references/provider-override-pattern.md`. Там описаны 3 варианта: (A) родитель делает анализ, суб-агент реализует; (B) ручное переключение config.yaml; (C) профили. Рекомендуется вариант A для большинства случаев.
>
> **Модели KiloCode** — см. `references/kilocode-models.md`. Полный список доступных моделей через KiloCode (claude-sonnet-4.6, opus, deepseek, gemini, grok и др.) с ценами.
>
> **Сжатие навыков** — см. `references/skill-shrinking-technique.md`. Как превратить раздутый навык (~60K chars) в обёртку (~400 chars).

### Проверка работы subagent

После запуска subagent'а — **обязательно проверь что он реально выполнил задачу**, а не вернул пустой/частичный результат. Subagent'ы склонны делать минимум.

**Чеклист проверки:**
1. **Покрытие** — если goal просил 8 дат, а вернул 1-2 — это баг. Перезапусти с более точным goal
2. **Формат** — если просил таблицу, а вернул прозу — заверни, перезапусти
3. **Пустой ответ** — если subagent вернул пустую строку или ошибку — не говори "готово", сначала перезапусти с retry
4. **Web_extract detection** — если subagent использовал web_extract и завис — перезапусти с явным запретом
5. **Валюта** — если результат в сумах, а Василий в России — перезапусти с требованием рублей

**Правило:** не говори "готово" пока не проверил результат. Если результат неполный — перезапусти.
