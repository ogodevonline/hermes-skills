# Recovery: зависший/долгий воркер — ручное восстановление оркестратора

Уроки 21.08.2026, lead-platform (два воркера: dev-вход 35+ мин, супер-админ; один умер после коммитов, другой жив).

## «running > 10 мин» ≠ «kill -9 сразу»

Сначала отличи живого воркера от зависшего:
- Heartbeat свежий (`hermes kanban show T | grep heartbeat`, каждую минуту) + в логе профиля воркера (`~/.hermes/profiles/<p>/logs/agent.log`) идут `API call #N` каждые 5-10 сек → воркер ЖИВ, просто задача большая. Медленная модель (deepseek-v4-flash) + огромный контекст (140K+ токенов) + параллельные воркеры делят 4 vCPU → dev-вход (web+api+compose+тесты) честно шёл 35+ мин. Жди, не убивай.
- Процесс воркера умер (`ps -p PID` пусто), задача висит `running` → работа НЕ потеряна: проверь worktree:
  ```bash
  git -C .worktrees/<T> log --oneline -3      # воркер мог закоммитить
  git -C .worktrees/<T> status --short        # или оставить изменения
  git -C .worktrees/<T> stash list            # работа может быть в stash
  ```
  Stash — нормальный паттерн: воркер стешил, чтобы обновить ветку под свежий main, потом применит.

## Мёрж и закрытие зависшей задачи руками оркестратора

1. Точное имя ветки — из `hermes kanban show T` → `branch_name`. НЕ угадывать: `t_a4a104d7-start` может быть `t_a4a104d7-telegram-dev`.
2. **Проверь diff ветки на «запрещённые» включения перед мёржем** — воркер мог включить флаг, который оркестратор/пользователь требовал выключить. Реальный случай: dev-вход `VITE_DEV_LOGIN=1` + `DEV_LOGIN_ALLOWED=1` в compose — дыра «любой войдёт как owner», пользователь запретил. Проверка:
   ```bash
   git diff main..branch -- docker-compose.yml .env* src/config.py
   ```
   Выключить активацию отдельным коммитом в ветке, потом мёржить.
3. Конфликты при параллельных ветках (два воркера правили одни файлы: telegram.ts, config.py): `git merge --abort`, посмотреть `<<<<<<<` блоки, объединить ОБЕ версии (напр. super_admin из main + переименование константы из ветки), закоммитить мёрж.
4. Закрыть зависшую задачу после мёржа: `hermes kanban complete T --summary "..."` — оркестратор имеет право закрыть, если код смержен.
5. Разблокировать цепочку вручную: диспетчер НЕ всегда разблокирует дочерние задачи после done родителя. `hermes kanban unblock T_следующая` + `hermes kanban dispatch`.

## kanban_wait.py может врать

`python3 ~/.hermes/scripts/kanban_wait.py T --timeout 570` иногда выводит «ЗАВЕРШИЛАСЬ: ready через Nс» / «done через 90с», хотя `hermes kanban show T` показывает `running` — watcher ловит смену промежуточного статуса. Финальный источник истины — ТОЛЬКО `hermes kanban show T`. Не пересоздавай и не убивай воркера по одному лишь выводу watcher'а.

## Прочие уроки мёрж-фазы

- Незакоммиченные локальные правки оркестратора (Dockerfile, HANDOFF.md) блокируют merge (`Your local changes would be overwritten`) — закоммитить/застейшить перед мёржем.
- `.worktrees/` в репо — добавить в `.gitignore` (иначе `?? .worktrees/` мешает статусу).
- После мёржей сразу пересборка (`docker compose up -d --build`, background=true + notify) + `/health` + `grep -c Conflict` → 0 + сид; отдавать пользователю на тест немедленно, не копить цепочку.
