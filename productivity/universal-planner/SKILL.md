# Universal Planner

Универсальный ассистент планирования. Строит детальный, пригодный к исполнению план для любого выхода: поездка, выходные с партнёром, вечер, день рождения, спонтанная вылазка.

## Когда использовать

Пользователь просит:
- «Спланируй выходные / поездку / вечер / день»
- «Создай план на Х с учётом всего»
- «Что можно поделать в Y с бюджетом Z»
- Любой запрос, где нужно не просто перечислить, а **разложить по времени с контекстом**

## Рабочий процесс (6 шагов)

### Шаг 1 — Сбор контекста (ДИАЛОГ, а не дамп)

**СНАЧАЛА ПРОВЕРЬ ЧТО УЖЕ ЕСТЬ.** Прежде чем задавать вопросы:
- Загляни в `memory()` — там может быть контекст (страна, партнёр, статус, бюджет)
- Проверь Obsidian `Projects/` — может уже есть план по этой теме
- Если есть существующий план — начни с «У нас уже есть план, обновляем или с нуля?»

**ВАЖНО: задавать вопросы ПО ОДНОМУ.** Не вываливать список. Спросил → получил ответ → спросил следующий.

Каждый ответ может менять направление — реагируй на него, прежде чем переходить к следующему вопросу.

**ФОРМАТ ПЛАНА — В ВАЛЮТЕ ПОЛЬЗОВАТЕЛЯ.** Если пользователь хочет планировать в рублях — все цены, бюджет и раскладки только в рублях. Не мешать UZS, USD и RUB — это сбивает. Выбери одну валюту и придерживайся её. Курс конвертации укажи один раз в начале.

**БЮДЖЕТ — ALL-IN ПЕРВЫМ ДЕЛОМ.** Если бюджет ограничен (например, 1.6M на поездку+покупку) — покажи раскладку «сколько на что» сразу, а не в конце. Пользователь должен видеть: билеты ≈X, еда ≈Y, остаётся на цель ≈Z.

**ДУМАЙ ЗА ПОЛЬЗОВАТЕЛЯ.** Пользователь может не знать, что ему нужно. Твоя задача — не просто записать ответы, а:
- Предугадать что ещё может понадобиться (документы, справки, разрешения, прививки, страховка)
- Если факт влияет на план — сразу предложи следующий логичный шаг
- Если узнал что-то новое о пользователе (статус, отношения, документы) — сохрани в `memory()` с target='user'

**УТОЧНЯЙ, А НЕ ПЕРЕСПРАШИВАЙ.** Если контекст уже есть — не спрашивай «а куда едем?», скажи «план по Узбекистану у нас есть, что изменилось с мая? Даты те же?»

**Что выяснить (по порядку, один за другим):**

1. **Тип и длительность** — «На сколько планируем? День, выходные, неделя, месяц?»
2. **Проживание** — «Где будем жить? Отель, аренда, у родственников/знакомых?» — **не предполагать отель**
3. **Транспорт** — «Как передвигаемся? Своя машина, аренда, такси, общественный?» — **не предполагать такси**
4. **Участники** — «Один или с кем-то?» — если партнёр:
   - **Узнай чем вы любите заниматься вместе** — не угадывай с места. Спроси прямо: «Чем вы обычно любите заниматься вместе? Может, есть любимые занятия?»
   - **Питание партнёра** — если партнёр голодный → проблемы. Закладывай перекус/обед в середине дня, не оставляй еду на конец. Лучше спросить сразу: «Она голодная когда выходите? Где обычно перекусываете?» — чем получить «она злая когда голодная» в середине планирования.
   - **Проверь, не надоели ли места** — спроси: «Где вы уже много раз были, что НЕ хотите?» Пользователь может быть сыт по горло Зарядьем, ВДНХ и другими очевидными местами.
5. **Бюджет** — «Какой бюджет? Хочешь бесплатно/дёшево/комфортно? Или конкретная цифра?» — **если бюджет ограничен, покажи ALL-IN раскладку сразу**
6. **Пожелания и активности** — «Что конкретно хочется? Может, есть места которые уже присмотрел?» — если речь о покупке недвижимости, уточни: **«дом или квартира?»**
7. **Ограничения** — если всплыло из разговора (спина, алкоголь, время)

⚠️ **Pitfall: реагируй на отклонение.** Если пользователь отклонил 2-3 варианта подряд — ты застрял в одной колее. Не предлагай ещё 3 вариации той же темы. Остановись и спроси: «Ок, я не угадываю. Расскажи чем вы любите заниматься? Что вам нравится?» — полная смена подхода.

**Pitfall: проверяй на «надоело».** Прежде чем предлагать очевидные места (Зарядье, ВДНХ, Парк Горького), спроси «вы там уже много раз были? Не надоело?» Иначе получишь «100 раз там был, задолбал».

**Pitfall: еда в середине дня.** Если план с партнёром — не закладывай еду только на вечер. Перекус/обед в середине обязателен. Голодный партнёр = испорченный день. Если пользователь не упомянул питание — спроси.

**Pitfall: долой — значит долой.** Если пользователь сказал «не говори про Х на этой неделе» — заприметь и не возвращайся к Х. Вообще. В этой сессии.
⚠️ **Pitfall: думай на шаг вперёд.** Узнал что партнёр — гражданка Узбекистана? → сразу подумай про покупку жилья на неё, Vatandosh card, брак. Узнал что есть ВНЖ? → подумай про банки, регистрацию. Узнал новое → memory().
⚠️ **Pitfall: не переспрашивай.** Если факт уже есть в memory — используй его, не задавай вопрос снова.

### Шаг 2 — Исследование (Deep Research)

Исследование идёт **тема за темой**, с промежуточными отчётами пользователю.

**Приоритет инструментов (скорость — главное):**

1. **`web_search`** — самый быстрый. Для погоды, часов работы, адреса, маршрута, быстрых цен.
2. **`web-search-scraper`** — глубокий поиск мест/событий/ресторанов/квизов/анти-кафе:
   ```
   uv run ~/.hermes/skills/search/web-search-scraper/scripts/search.py --query "запрос" --preview
   ```
   Таймаут: ~8-10 сек. 20-25 результатов. Регион по умолч. Москва (lr=213). Для мирового поиска: `--no-region`.
3. **`crawl4ai`** — глубокий анализ одного сайта (OLX, Avito, маркетплейсы). Если нужно вытащить все объявления с конкретной категории:
   ```
   uv run ~/.hermes/skills/search/crawl4ai/scripts/crawl.py --url "..." --max-pages 3
   ```
4. **`web_extract`** — только для конкретных деталей с одной страницы (цены, расписание), если другие инструменты не дали ответа. НЕ ИСПОЛЬЗОВАТЬ для первичного поиска — он долгий (1+ мин).

**Pitfall: web_extract медленный.** Если пользователь жалуется на задержки — причина почти наверняка в web_extract. Используй его макс 1 раз за сессию. Основной пайплайн: web_search (быстро) → web-search-scraper (глубоко) → crawl4ai (классифайды) → web_extract (только если нужно вытащить конкретику с известной страницы).

**Процесс (тема за темой, отчитываясь):**

1. **Погода** — web_search → сразу сказать пользователю («Погода норм, +18, солнечно»)

2. **Локация пользователя** — если пользователь назвал район/станцию метро, учитывай близость. Не предлагай варианты за 1+ час езды, если есть достойные рядом.

3. **Места / события** — web-search-scraper → **показать найденное**. Думай сразу про два сценария: outdoor (солнечно → парки, набережные, музеи с прогулкой) и indoor (пасмурно/холодно → кино, квесты, стендап, антикафе, ТЦ, боулинг, бильярд, квизы). Под indoor ищи варианты с ценами:
   - Кино: ~400-600₽/чел
   - Стендап: от 950₽/чел
   - Квест: от 1500-2000₽ за двоих
   - Антикафе: ~300-500₽/час с человека
   - Бильярд/настольный теннис: ~500-800₽/час
   
4. **Рестораны / еда** — web-search-scraper или web_search → **показать топ-2/3 с ценами**:
   > 🍽️ Вариант А (средний чек 2000₽)
   > 🍽️ Вариант Б (бюджетный, 800₽)
   > Подходит?

5. **Маршрут / дорога** — web_search

**Итерации:** После каждого блока пользователь может уточнить / изменить направление. Не пытайся собрать всё за раз — сделай один блок, покажи, получи feedback.

**Формат отчёта:**
```
🔍 Ищу: [что ищу]
✅ Нашёл: X результатов за ~N сек

📍 [place/indoor] (2):
  - Музей Победы | Бесплатно 9-11 мая
  - Стендап Клуб на Трубной | Билеты от 950₽

🎪 [event] (3):
  - Московская музейная неделя | 11-17 мая, 40+ музеев

💰 Укладывается в бюджет? Да / Нет
🌤️ Учитывает погоду? Да (indoor при дожде)

Что думаешь? Копать глубже или переходим к еде?
```

**Pitfall:** Если web-search-scraper вернул пусто / мусор — не гоняй 5+ запросов подряд. Скажи «ничего не нашёл по такому запросу, попробуем по-другому?» и предложи уточнить формулировку. Переключись на `web_search`.

**Pitfall: Для delegated research — всегда запрещай web_extract.** subagent-исследователь может по умолчанию использовать web_extract, который висит по 1+ минуте на URL. Это гарантированный timeout при 3+ URL. Всегда пиши в context: "Используй ТОЛЬКО web_search. НЕ ИСПОЛЬЗУЙ web_extract."

**Pitfall: Date range — перебирай все даты.** Если пользователь просит "с 10 по 17 число", а не конкретную дату — НЕ выбирай одну дату. В goal суб-агента явно пропиши: "Перебери КАЖДУЮ дату в диапазоне. Найди минимальную цену на любую из этих дат."

**Pitfall: web_search — упоминай конкретные даты в запросах.** Когда ищешь "авиабилеты москва нукус 10 июля 2026" — поисковик может вернуть общую страницу направления без привязки к дате. Пиши максимально конкретно с датой в запросе.

**Pitfall: web-search-scraper обрывается с exit 130.** Если `uv run search.py --query "..."` упал — переключиться на `web_search`. web-search-scraper падает редко, но если случилось 2 раза подряд — больше не пробовать в этой сессии.

Шаблон отчёта: `templates/interim-report.md`

1. **Погода** — web_search → сразу сказать пользователю («Погода норм, +18, солнечно»)

2. **Места / события** — web-search-scraper → **показать найденное**. Думай сразу про два сценария
   > Нашёл несколько вариантов по музеям:
   > 📍 Музей Москвы — бесплатно 11 мая в рамках музейной недели
   > 📍 Музей Победы — работает 9-11 мая, праздничная программа

3. **Рестораны / еда** — web-search-scraper → **показать топ-3**:

   > 🍽️ Вариант А (средний чек 2000₽)
   > 🍽️ Вариант Б (бюджетный, 800₽)
   > Подходит? Или другой район?

4. **Залы / фитнес рядом** — web_search

5. **Маршрут / дорога** — web_search

**Итерации:** После каждого блока пользователь может уточнить / изменить направление. Не пытайся собрать всё за раз — сделай один блок, покажи, получи feedback.

**Формат отчёта:**
```
🔍 Ищу: [что ищу]
✅ Нашёл: X результатов за ~N сек

📍 [place] (2):
  - Музей Победы | Работает 9-11 мая, вход бесплатный
  - Музей Москвы | Бесплатно 11 мая, музейная неделя

🎪 [event] (3):
  - Московская музейная неделя | 11-17 мая, 40+ музеев

Что думаешь? Копать глубже или переходим к ресторанам?
```

### Шаг 3 — Размышление и анализ

После сбора информации по каждой теме — короткая рефлексия:
- Что нашёл, что пропустил
- Какие есть пересечения (например, музей рядом с рестораном)
- Где может быть проблема (закрыто, дорого, далеко)
- Что стоит уточнить у пользователя

Формат: 2-3 предложения, не философия. Просто «вот это выглядит круто, но вот это может быть проблема».

### Шаг 4 — Генерация таймлайна

Почасовой план с привязкой к локациям.

Категории цен помечать: 🆓 💵 💰

### Шаг 5 — Plan B

Как минимум 2 запасных сценария:
- **Погода**: если дождь → indoor-активности (музей, ТЦ, антикафе)
- **Закрыто/очередь**: альтернативное место рядом
- **Устали**: где отдохнуть, сокращённый маршрут
- **Бюджет**: если цены выше ожиданий

### Шаг 6 — Оформление

Чистый, компактный вывод в чат. Не превышать 2000-3000 символов для коротких планов. Для долгосрочных/релокационных планов — допустимо больше, но сохранять в Obsidian (см. Шаг 7), а в чат выдавать резюме.

### Шаг 7 — Для долгосрочных поездок / релокации (от 2+ недель)

Когда план — не вылазка, а переезд или длительное пребывание, меняется структура:

**Что добавить в план вместо таймлайна:**
- Банки / финансы: открытие счёта, перевод денег, местные карты
- Юридические вопросы: документы, регистрация, право собственности
- Поиск жилья на покупку/аренду — площадки, цены, риелторы
- Связь: местная SIM, интернет
- Бюджет не на день, а на месяц с разбивкой
- Чеклист «до вылета» и «сразу после прилёта»
- Plan B на случай, если что-то пошло не так

**Формат:** сохранять в Obsidian:
- `Projects/<Название-поездки>/plan.md` — для trip/relocation/project-планов
- `Journal/YYYY-MM-DD.md` (секция `# 🗓️ План`) — для коротких выходов/вечеров
В чат — сжатое резюме и ссылка на заметку. После записи — git commit + push vault.

**Инструменты для поиска:** `web_search` — быстрый поиск. `web-search-scraper` — глубокий поиск (рестораны, места, события). `crawl4ai` — анализ конкретного сайта. `web_extract` использовать только если нужна конкретная цена/расписание с одной страницы, не больше 1 раза за сессию.

## Связь с другими системами

- **Задачи**: создавать задачу в `t` на день плана (`t add "Выходные 11 мая" -d 2026-05-11`). Формат вывода задач — см. `references/task-display-format.md` (единый стандарт для всех брифингов).
- **Obsidian**: сохранять готовый план:
  - Короткие вылазки/выходные → `~/hermes-vault/Journal/YYYY-MM-DD.md` секция `# 🗓️ План`
  - Поездки/проекты/релокация → `~/hermes-vault/Projects/<Project-Name>/plan.md`
  После записи — `git add -A && git commit -m "..." && git push`
- **Календарь**: можно создать Google-события для каждого блока
- **Погода**: web_search или уже есть в morning-brief
- **Поиск**: web-search-scraper для глубокого исследования — рестораны, музеи, мероприятия, цены

## Pitfalls

1. **Незнакомое место** — не мучай поиск 5+ запросами. Спроси пользователя прямо: «Это не находится, может ММОМА / МАММ? Или другое название?»
2. **Паралич от выбора** — не предлагай 10 вариантов ресторанов. Дай 2-3: 🆓 💵 💰
3. **Размер плана** — не превышать 2000-3000 символов. План должен читаться за 30 секунд.
4. **Plan B обязателен** — без него план не полный. Хотя бы 2 альтернативы.
5. **Участники и согласование** — если план с Лимой, спросить «Лима в курсе? Нужно помочь написать ей?»
6. **Спина/алкоголь** — помнить про ограничения Василия (спина — щадящая растяжка, без нагрузки; алкоголь — 0)
7. **Бюджет реалистичный** — не занижать. Лучше сказать «от 3000₽» чем «1000₽» а по факту 5000₽
8. **web-search-scraper timeout** — установлен таймаут 120с (см. v1.2). Если не ответил за это время — прервать и сказать «поиск не дал результатов, попробуем иначе». Не ждать дольше.
9. **web-search-scraper exit 130** — если `uv run python -m service` упал с SIGINT дважды подряд — больше не пробовать в этой сессии. Переключиться на `web_search`. `web_extract` использовать только если нужна конкретика с одной страницы, и не больше 1 раза за сессию.
10. **Отчёт после каждой темы** — не собирай всю информацию молча. Покажи что нашёл, спроси feedback.
11. **Пустой результат** — не гонять 5+ запросов. Сказать «ничего не нашёл, попробуем иначе?»
12. **Размер плана** — короткие планы 2000-3000 символов. Релокационные планы могут быть больше — сохранять в Obsidian `Projects/`, в чат резюме.
13. **Obsidian — единственное хранилище планов.** Не сохранять планы в `~/.hermes/plans/`. Только в Obsidian vault. git push обязателен.
14. **Одна валюта в плане.** Не мешать RUB, USD, UZS. Выбрать одну валюту пользователя, курс указать один раз в начале.
15. **Тип недвижимости.** Если пользователь говорит «купить жильё» — уточнить «дом или квартира?». Не предполагать.
