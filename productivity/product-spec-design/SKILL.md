# Product Spec Design Skill

Проектирование продуктовых спеков для бизнес-проектов Василия (платформы,
сервисы, боты) — **в чате, послойно, сверху вниз**. Не делегируется агентам
без явного запроса. Каждый согласованный слой фиксируется в Obsidian.

## When to Use

- Василий просит «спроектировать», «накидать спек», «продумать продукт/платформу».
- Есть Kanban-задача на architect для спека — сначала проверить, не хочет ли
  Василий проектировать в чате (его предпочтение — чат, без агентов).
- Продолжение лид-платформы и подобных бизнес-проектов
  (текущее состояние — в `references/lead-platform-rashid.md`).

## Prerequisites

- Obsidian vault: `~/hermes-vault/` (единственный путь, НЕ `~/obsidian/`).
- Спеки класть в **древовидную структуру** (не одним файлом!):
  `~/hermes-vault/Projects/Planning/YYYY-MM-DD/<project>/`
  - `README.md` — содержание + дерево + ссылки
  - `NN-layerN-*.md` — файл на каждый слой (00-overview, 01-layer0-... ... 07-layer6-plan)
  - `08-test-plan.md` — план тестирования (отдельно от спеки!)
  - `steps/NN-*.md` — файл на каждый этап разработки (для исполнителей-агентов)
  Василий: «такие планы надо строить древовидной структурой с обязательным
  содержанием и со ссылкой на файлы плана по шагам — и человеку проще читать,
  и нейронки, которые потом будут идти по шагам и выполнять их».
- Контекст бизнес-проектов Василия — в memory.

## Procedure

1. **Формат**: работать в чате с Василием напрямую. Без `delegate_task` и без
   Kanban-агентов, если не было явного OK.
2. **Идти послойно сверху вниз** (не перескакивать):
   - Слой 0 — Бизнес и границы: цель, пользователи, потоки, что НЕ делаем, монетизация
   - Слой 1 — Сценарии: главные пользовательские потоки (запись, подтверждение, напоминание, …)
   - Слой 2 — Функциональные требования по каждому сценарию
   - Слой 3 — Архитектура: компоненты, связи, мультитенантность
   - Слой 4 — Данные: схема БД, статусы, сущности
   - Слой 5 — UX: экраны админки, сообщения бота
   - Слой 6 — План разработки по этапам
3. **Спека ≠ план разработки ≠ тест-план.** После согласования слоёв спеки
   НЕ переходить сразу к коду/задачам: сначала отдельный план разработки
   (поэтапный, с файлом шага на каждый этап) и отдельный тест-план (TDD:
   тесты описываются ДО реализации, красный → реализация → зелёный).
   Василий: «first of all we need to create tests and describe them in the planning».
4. **Вопросы**: задавать по пунктам (номер + вопрос), не вываливать всё сразу.
   К каждому решению предлагать 2-3 варианта с рекомендацией.
5. **Фиксация**: после согласования слоя записать в Obsidian
   (`~/hermes-vault/Projects/Planning/YYYY-MM-DD/...`), в чате коротко
   подтвердить. Если есть Kanban-задача — закомментировать
   «проектирование в чате, результат прикрепим».
6. **Темп**: Слой 0 закрыт → сразу переходить к следующему слою с вопросом,
   не ждать отдельной команды.
7. **Завершение**: после всех слоёв — kanban complete задачи
   (`hermes kanban complete T_ID --result "..."`, флага `--artifacts` НЕТ;
   артефакты — через `--metadata` JSON или просто ссылкой в --result).

## Quick Reference

- Слои: 0 бизнес → 1 сценарии → 2 функции → 3 архитектура → 4 данные → 5 UX → 6 план
- Структура: `~/hermes-vault/Projects/Planning/YYYY-MM-DD/<project>/` — README + файл на слой + steps/ + 08-test-plan.md (НЕ один файл)
- Универсальная платформа = ядро + модули-плагины (ядро не раздувать)
- Медицинский ИИ: только организационные ответы + запись, диагнозы НЕ ставит
- **Два бота**: пациентский (белый лейбл) + рабочий (мастера/админ: уведомления с кнопками ✅/❌, расписание)
- **Авто-подтверждение записи**: зазор (бот не показывает слоты ближе настраиваемого N ч) + окно отмены 4 ч — не отменил = подтверждено
- **Статусы записи**: новая → (4ч) → подтверждена → выполнена (АВТО по истечении времени приёма, админ/врач может поправить) / отменена / перенесена / не пришёл → догонялка
- **Админка = ВЕБ** (решение 03.09.2026 — отказ от Mini App; раннее решение Mini App пересмотрено): авторизация через Telegram initData, веб-SPA для админа/врачей/поддержки (роли внутри); владелец — только статистика/доход. Дизайн страницы клиента (умная таблица + единый таймлайн с авторами) и промпт для нейронки — в lead-platform `references/admin-client-page-design.md`
- **Стек (пилот)**: Python, FastAPI, aiogram 3, Postgres (сразу, не SQLite), ОДИН сервис, APScheduler (крон)
- **Карточка клиента**: timeline всех событий (написал боту, записался, статусы, звонки, комментарии); лиды = фильтр «нет подтверждённых записей» + статус дозвона
- **Несложные фичи, которые Василий одобряет**: ретаргетинг «давно не был» (крон), ручные сообщения из админки с подписью (Администратор/Доктор) — та же ручка для ИИ-агента
- **«Задать вопрос» в боте**: ДВА варианта — ИИ-консультант ИЛИ связаться с человеком (администратор/врач); техподдержку платформы не делать в MVP
- **Чат «клиент ↔ бизнес» = тикет-система**: все сообщения в БД (не личные чаты), у диалога статус открыт/требует ответа/завершён (клиент сам может «закрыть» финальным сообщением — админ ставит «завершён» вручную), внутренние комментарии (клиент НЕ видит), клиент НЕ видит «прочитано/доставлено» (ноль раздражителей)
- **Эскалация без ответа**: уведомления ТОЛЬКО в рабочее время +1 ч после закрытия (ночью/выходные — копятся, один пуш утром, не спамить); 30 мин → повторно специалисту, 2 ч → админу, 4 ч → владельцу; тайминги настраиваются
- **ИИ-ассистент = function calling (дёшево)**: LLM вызывается только на сообщение клиента, действия через те же REST-ручки ядра (get_free_slots → create_appointment → cancel), граф поведения в системном промпте: намерение → шаги → ручка. Уровни сценариев: 1) типовые из коробки (MVP), 2) JSON-граф в админке, 3) визуальные кубики (НЕ в MVP — отдельный продукт, недели разработки)
- **Роли универсальные**: владелец (статистика/доход), врач/мастер, администратор — НЕ привязывать к людям («администратор ≠ жена»)
- **Принцип гибкости**: всё настраивается в админке (категории услуг вкл/выкл, выбор специалиста, зазор, кому уведомления)
- **Длительность услуги настраиваемая** (урок 21.08.2026): дефолтная `duration_minutes` + пресеты вариантов (`duration_options`, напр. 120/240/360/480 мин — плетение кос/покраска 2-8ч); выбор длительности — ТОЛЬКО при записи админом/специалистом (клиент в боте — всегда дефолтная); слоты и занятость календаря считаются под ВЫБРАННУЮ длительность
- **Лимит активных записей на клиента** (урок 21.08.2026): настраиваемый в админке `max_active_appointments`, дефолт 4 — защита от переполнения расписания
- **Клиент автосоздаётся при первом /start** (урок 21.08.2026): имя из Telegram, роль CLIENT; повторный /start не дублирует — иначе каждый клиент требует ручного добавления админом и запись падает с «Аккаунт не найден»
- **Супер-админ по env при старте + ДВЕ роли** (урок 21.08.2026, требование Василия): `SUPER_ADMIN_TELEGRAM_ID` в env → при старте upsert User role=SUPER_ADMIN (создать/повысить, идемпотентно) — владелец ПЛАТФОРМЫ, видит все тенанты. НЕ «первый написавший» и НЕ dev-кнопки. При первом /start в worker-боте супер-админу — **онбординг компании** (название и т.п.) → создаётся тенант + юзер role=OWNER (владелец КОМПАНИИ, реальный tg_id супер-админа, привязанный к тенанту) → кнопка «Открыть админку» (Web App). Вход в админку — ТОЛЬКО через Telegram Mini App (initData по реальному telegram_id); dev-вход в проде запрещён
- **Напоминания клиенту** (решено 21.08.2026): за день и за 2 часа до записи; тайминги настраиваемые
- **Планы и статистика — в MVP** (решено 21.08.2026: Василий «оба нужны»), не понижать до «после пилота»
- **Управление командой (US-23, требование 21.08.2026)**: супер-админ/владелец ДОЛЖЕН добавлять специалистов, администраторов и техподдержку по telegram_id и менять роли (страница «Команда» в админке). Новая роль **SUPPORT** (техподдержка): видит расписание и чаты клиентов, отвечает клиентам, НЕ трогает настройки/команду. После добавления User role=SPECIALIST автоматически создаётся запись Specialist (виден в расписании). Нельзя менять роли супер-админа/owner (owner один; super_admin — только платформа). Раньше специалист добавлялся только из УЖЕ существующих пользователей (SpecialistIn.user_id) — это НЕ то же самое, что создание аккаунта персонала.
- **Роли команды — ОПЦИОНАЛЬНЫ и СОВМЕЩАЕМЫ (жёсткое требование 21.08.2026, Василий: «универсальное приложение лид-платформа — компанией может управлять как один человек, так и много»)**. Пустая команда (один супер-админ/owner, без специалистов/админов/поддержки) — ВАЛИДНА, ничего не должно падать. Супер-админ/owner может быть ОДНОВРЕМЕННО специалистом (владелец сам принимает клиентов: запись Specialist на его user_id, виден в расписании, подтверждает записи). При онбординге worker-бот СПРАШИВАЕТ «Кто будет принимать записи?» (Я сам / добавим позже / другие специалисты) и НЕ блокирует продолжение без ответа. НЕ делать роли обязательными к заполнению («если все обязательные — ничего работать не будет», слова Василия). Кнопка добавления «Назначить себя специалистом» — в админке для owner/super_admin.
- **Исследуй план, прежде чем реализовывать/спорить о фиче (урок 21.08.2026, Василий: «надо было просто взять и исследовать план»)**. Когда Василий говорит «мы это в планах описывали» / «это же было в планах» — СНАЧАЛА открой планы/спеки (vault `~/hermes-vault/Projects/Planning/...` + `docs/` репо + kanban) и найди, что там реально написано, потом предлагай реализацию. Не проектируй с нуля то, что уже согласовано, и не выдумывай альтернатив, противоречащих плану.
- **Канон-артефакт пользовательских историй**: `docs/user-stories.md` в репо — все истории по ролям (A–F), у каждой «Как… хочу… чтобы…» + нюансы + acceptance + статус (🟢/🟡/🔴/⏳/❓); глоссарий (зазор, окно отмены 4ч, авто-подтверждение, активная запись, пресеты длительности, лимит); приоритеты P0/P1/P2; открытые продуктовые вопросы закрываются явными решениями прямо в документе
- **US-00 — сайт-визитка с воронкой продаж + викторина (ГЛАВНАЯ история, добавлена 22.08.2026, Василий: «я никак не продам эту платформу если нету сайта визитки… никому не нужен будет»)**. Точка входа в продукт, P0 №1, номер 00 — с этого всё начинается. Контур: визитка бизнеса (генерируется из данных тенанта: услуги, цены, контакты, часы, фото — без ручной вёрстки) → CTA «Записаться» → клиентский бот (глубокая ссылка) + CTA «Для бизнеса» → worker-бот → викторина-онбординг (вопросы о бизнесе → автозаполнение админки: услуги, длительности, часы, зазор) → админка. Дизайн — МАКСИМАЛЬНО красивый/продающий (шаблоны, анимации, адаптив под телефон, продающие блоки: фото, отзывы, соцдоказательства). Результаты воронки/викторины сохраняются в БД по пользователю (лид-трекер: telegram_id, прогресс викторины, статус оплачено/не оплачено/триал) — супер-админ отслеживает в Telegram.
- **Оплата подписки платформы — PaymentProvider-абстракция (решено 22.08.2026)**: интерфейс один, провайдер плагином. **Stripe НЕ работает в Узбекистане напрямую** (46 стран, УЗ не входит; обход через юрлицо/посредника = серая зона, риск блокировки счёта) → в MVP закладывать локальные: **Payme / Uzum** (рекуррентные платежи для подписок), **Click** (массовый), Apelsin. Stripe — только если/когда появится легальный доступ.

## Pitfalls

- **Терминология платформы НЕ должна копировать пилотную вертикаль.** Василий
  явно поправил: «ты постоянно общаешься в контексте клиники/врачей, а это
  лид-платформа, она не завязана только на врачах». Для платформы говорить
  нейтрально: бизнес / специалист / клиент / рабочие планы — даже когда
  обсуждаем пилот (стоматология). Термины вертикали (клиника/врач/пациент/план
  лечения) допустимы только как пример, не как рамка.
- **Контент бизнеса — в шаблонах тенанта, не в коде платформы** (урок 21.08.2026):
  Василий: «это должно решаться не промптами а отдельными шаблонами для каждого
  бизнеса, мне нужна универсальность». В коде ядра НОЛЬ отраслевых слов
  (врач/диагноз/пациент/кариес — grep по src/ = 0). Промпты ИИ, правила ответов,
  маркеры «сложных вопросов», приветствие — per-tenant шаблон (в lead-platform:
  `tenant.ai_template` JSONB: rules/no_answer_reply/expert_markers/expert_reply/
  greeting + нейтральный DEFAULT_TEMPLATE с фолбэком). Сид пилота заполняет СВОЙ
  вертикальный шаблон как контент тенанта. Проверка после реализации:
  `grep -rniE "врач|диагноз|кариес|пациент" src/` → 0.
- **Разворот требований в середине** (напр. «сделать универсальным») — норма:
  вернуться к Слою 0, перепроектировать, не спорить.
- **Универсальность ≠ раздутое ядро**: общее для всех — в ядро,
  вертикальное — в модули.
- **Монетизация**: паттерн Василия «сначала пилот бесплатно, потом тарифы».
  В MVP закладывать заглушку (напр. страница прайсов с онлайн-оплатой).
- **Медицинские советы**: не давать из головы; в продукте ИИ ограничивать
  организационными вопросами (цены, услуги, подготовка) + предложение записи.
- **Не перескакивать слои**: без согласованного Слоя 0 не углубляться в БД/UX.
- **Не класть все слои в один файл**: Василий явно: «когда ты все семь слоёв
  кладёшь одним файлом — это беда». Сразу строить дерево: README-содержание +
  файл на слой + steps/ + тест-план. Один файл — боль и для человека, и для
  агентов, которые потом идут по шагам.
- **Спека ≠ план**: после спеки не начинать кодить — сначала план разработки
  (поэтапно, файл шага на этап) и тест-план (TDD, тесты до реализации).
- **Василий отвечает выборочно**: на блок из 3-4 вопросов может ответить только
  на часть. Пропущенные вопросы — переспросить отдельным коротким сообщением,
  не считать их решёнными и не выдумывать ответ.
- **«Да» на рекомендацию = принял её целиком** (напр. «1 - да» на вопрос про
  авто-подтверждение). Дальше детализировать последствия, а не переспрашивать.
- **Универсальность — движущая сила Василия**: если проект «для одного клиента»,
  он быстро решит сделать платформу для многих. Закладывать гибкость сразу:
  настройки вместо хардкода, роли не привязаны к людям, всё конфигурируемо.
- **Два отдельных бота** (пациентский + рабочий) — предпочтение Василия,
  не экономить на одном боте с ролями.
- **Kanban-задача на спек**: при переносе проектирования в чат — закомментировать
  задачу «проектирование в чате, результат прикрепим», а не удалять/архивировать.
- **Запись в vault**: если `write_file` падает с internal import error
  (напр. `resolve_task_overrides` из tools.terminal_tool) — fallback:
  `mkdir -p` + python3 heredoc с `open(path,'w')` через terminal.
  Рабочий паттерн, не застревать на ошибке инструмента.
- **Никаких auth-дыр в проде** (урок 21.08.2026, Василий: «любой желающий блядь в админку может зайти что за тупость мудак»): dev-вход / кнопки «войти как owner» / флаг `DEV_LOGIN_ALLOWED` в ПРОД-сборке — категорически нет, даже для пилота. Доступ к админке — только Telegram initData реального юзера (по telegram_id из БД). Пилотные/тестовые костыли аутентификации — только в dev-сборке, по умолчанию выключены. Роль владельца задаётся конфигом при старте (`SUPER_ADMIN_TELEGRAM_ID`), а не «первый обратившийся» и не ручным заведением через сид.
- **Фичи без зафиксированных user stories = «хуйня никому не нужная»** (урок 21.08.2026, Василий): когда проект уже строится, а единого документа историй нет — Василий требует СНАЧАЛА зафиксировать ВСЕ истории с нюансами (роли, глоссарий, acceptance, приоритеты P0/P1/P2) в репо (`docs/user-stories.md`), потом продолжать фичи. - **«Хочу увидеть как это работает / не хочу долго сидеть» = запрос самого быстрого демо (10.09).**
  В этом режиме нельзя предлагать «правильную» долгую архитектуру или новую UI-поверхность (мини-апп,
  отдельная страница) — предлагать минимальную достройку УЖЕ работающего пути до полного сценария.
  Ответ: короткий список «что уже есть → чего не хватает» + оценка в минутах + один вопрос на старт.
  Сложные клиентские флоу (викторины, многошаговые мастера) в таком режиме режутся как «долго и сложно» —
  закладывать только если Василий явно попросил.
- **Аудит пользовательских путей — три фазы, порядок задал Василий (10.09.2026, «жена не поняла демо»)**. Когда Василий говорит, что user path хуёво прописан: 1) восстановить ТЕКУЩИЙ путь по каждой роли ПО РЕАЛЬНОМУ КОДУ (обработчики ботов, навигация админки), а не по докам — доки отстают; 2) диагноз «почему не понятно» глазами нетехнического пользователя («тест жены»); 3) «как должно быть» — ОТДЕЛЬНО для каждой роли (владелец / клиент / сотрудник), максимально просто, в диалоге по одному слою. Типовые болезни, которые искать: нет первого шага после онбординга (человек падает в пустой экран); язык платформы вместо языка бизнеса («Очередь ответов», «Параметры», «лиды», «тенант»); несколько дверей в одно действие (запись и в боте, и через мини-апп); сервисные штуки платформы (подписка, ИИ-раздел, пикеры аккаунтов) в бизнес-интерфейсе владельца; нет моментального «вау» — демо-запись «попробуй сам» + «смотри, она в календаре» замыкает петлю за 2 минуты. Состояние путей на 10.09 — в `references/lead-platform-journeys.md`. **Живой показ-демо по телефону/звонку клиенту НЕ делать (решение 23.09 после провала первого показа, Василий: «звонок это проблема в сети всегда»)**: формат продажи = заранее записанное видео (4 действия, ~2 мин) + стипы-скриншоты; настройка — без участия клиента; домен продажи с `.online` менять на `.ru`/`.com` за Cloudflare; ЦА показов — где записи теряются.
